# 队长的一类契约错：把「落点」写在上层，而状态在别处（2026-10-16）

> **本会话【两次】同一形态,而两次都是实施方按纪律报出、队长认错。**

---

## 1. ★★★ 两次实例

### ① t87:`validateCreateTask` 被写成落点,而它是**纯函数**

```
★ 队长的契约说:「在 validateCreateTask 里加采集」
★★ 而实测:那个函数【返回 {ok:false,error} 而不抛】、无 await、无 node: import、无 ctx
⇒ ★★★ 它【结构上】无法采集（采集要 I/O）
★ 实施方的处置:报出,并指出【调用方】才是正确落点
   ——★ 而那个位置【更符合规格自己的原则】:「宿主在【既有】汇合点调用」
```

### ② t97(S1):`src/tools.ts` 被写成落点,而判决落盘在 `update-task.ts`

```
★ 队长的契约 inScope 列了 src/tools.ts
★★ 而实测:
   $ grep "task.verdict = " src/tools.ts            ⇒ ★ 空
   $ grep "task.verdict = " src/tools/update-task.ts ⇒ 1814
   $ grep "update-task" src/tools.ts                 ⇒ 92: import { register as ... }
⇒ ★★★ tools.ts 【只是 import 并 register】,看不到 args.verdict
★ 而实施方指出关键:S1 的语义要求「在判决落盘【那一刻】记」
   —— 否则事后读盘读到的是【另一批字节】
```

---

## 2. ★★★ 共同根因

```
★ 队长按【模块名】推落点（"tools 那条路"），而没有查【状态在哪里被改】
⇒ ★★ 而本仓的 tools.ts 是【注册聚合层】,真正的实现在 src/tools/*.ts 里
   （见 t70 的「sixteen tools stop sharing one file」）
```

★★ **而两次的共同表现是同一个:**
```
· 契约写了一个"看起来该在那儿"的位置
· 而那个位置【没有那个状态】，或者【结构上做不到那件事】
⇒ ★★★ 而实施方要么报出（t97）、要么被闸门拦下（t87 的 verify 断言本任务产出）
```

---

## 3. ★★ 而它与本会话那条主轴是同一族

```
★★ 「契约写的位置」与「状态实际在的位置」在契约里【同形】——
   都只是一行路径字符串
⇒ ★★★ 所以只有【当场 grep 一下】能把它们分开
```

★ **而本仓已有防御,只是我没有用它:**
```
★ 闸门 contract.task-atomicity / build-artifact-scope 会当场算产物
★★ 而它们【不检查"落点是否真的持有那个状态"】——
   因为那需要领域知识,不是纯文本可判的
⇒ ★ 所以这一格【只能靠人/agent 查】
```

---

## 4. ★ 处置（写进纪律）

```
★ 写契约时，凡指出"落点"的,必须先 grep 那个状态的改写点:
   例如 S1 ⇒ grep "task.verdict = " ⇒ 找到真实文件
★★ 若 grep 不到 ⇒ ★★ 那个落点【不存在】,不许照模块名推
```

★ **而本会话两次都是实施方替我做了这件事** ——
**那说明纪律有效,但它发生在【浪费了一轮之后】。**
