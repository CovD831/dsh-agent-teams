# 判决 → 判据：提案

> **来源**：2026-10-07 一晚的实测（19 个任务 + 8 条判决）。用户的要求是
> *"这些经验的沉淀，肯定不能只是通过 prompt 之类的形式，最好是能转化为某种机制沉淀下来。"*
>
> 而本文件回答一件事：**这 8 条判决里，哪几条真的能被机械化？**
>
> ★ 而"能被机械化"的判据是**窄的**：它必须【不问语义】就能判 ——
> 否则它只能是一条【诊断】（标记给人看），而诊断不能拦。

## 二、四条可机械化的判据（逐条给出形状）

### 判据 A（来自 j-0002）：**同一件工作的两种写法必须同裁**

```
形状：对每个"看起来能分开"的判据，构造【同一件工作的两种写法】的对照对，
      断言两者【同裁】。

而 t43 已经做过一次（尾斜杠对照对）：
  ['src/registry.ts','src/index.ts']         ⇒ ok
  ['src/registry.ts','src/index.ts','src/']  ⇒ blocked
  ⇒ ★ 两边工作【完全相同】⇒ 判据判的是写法。

★ 可机械化的部分：对照对的【同裁断言】是机械的。
★ 不可机械化的部分：**构造哪一对** —— 那需要理解判据在判什么。
⇒ 所以它的形态是【通用夹具 + 每个判据手工提供一对】，而不是全自动。
```

### 判据 B（来自 j-0004）：**派生文件必须有生成器**

```
形状：对每个"看起来是派生的"文件，断言【存在一条重新生成它的路径】。

★ 而它的判据可以窄到可机械判定：
  · 文件里有"生成于/regenerated/DO NOT EDIT"之类的标记 ⇒ 必须能找到生成器
  · 或：某个脚本的 --write 模式产出它

★ 而这正是 fe9de34 修的那件事（golden 快照没有重新生成路径）。
⇒ 它今天已经造成过一次冲突（t42），所以它不是假想的需求。
```

### 判据 C（来自 j-0007）：**措辞里的数字要能指出赋值来源**

```
形状：扫【面向人的措辞】（拒绝消息、日志、状态行）里的
      `${... ?? <字面量>}`，断言那个字面量【不是唯一的来源】。

★ 而这是本文件里【最窄、最可机械判定】的一条：
  · `?? 1` 出现在一句"扫了 N 个"里 ⇒ 可疑（它可能是兜底值伪装成读数）
  · 而它今天真的发生了（changed-paths.ts:255）

★★ 而它必须【三态不同形】，否则会误伤：
  · 该字段有赋值点 ⇒ 合格
  · 无赋值点、且兜底值是字面量 ⇒ blocked（这就是那个缺陷）
  · 无法判断（动态赋值）⇒ unmeasured
```

### 判据 D（来自 j-0008）：**搬运的底本必须是当前分支的祖先**

```
形状：搬运类任务（把代码从 A 搬到 B）在【收口时】断言：
      它的底本 commit 是【当前 HEAD 的祖先】。

★ 而它可机械判定：`git merge-base --is-ancestor <底本> HEAD` 就是一个布尔。
★ 而它今天真的丢了东西（t41 的接线被搬回旧版）。
```

## 四、两条只能诊断（标记给人，不拦）

### 诊断 F（来自 j-0003）：**代理读数候选**

```
扫夹具里"按位置/距离/缩进取块"的断言 ⇒ 标记为候选。
★ 为什么不拦：有些代理读数是【合理的】（例如断言某段代码在一个范围内）。
★ 而它的价值是：把候选列出来，而人在写的时候会自问
  「这个读数变化，是否只可能由我关心的事引起？」
```

### 诊断 G（来自 j-0006）：**未被任何夹具走到的路径/加载代码**

```
扫"路径拼接 / 动态加载 / 初始化"类代码，标记【没有被任何夹具走到】的。
★ 为什么不拦："没被走到"是一个覆盖率问题，而覆盖率不是判据。
★ 而它今天真的发生了两次（__dirname、层数抄错）。
```

## 八、★ 用户补的两条标准（2026-10-08，它比我原来那条更完整）

**用户原话**：

> 「如果可以机械化，那就自动加上去就好了。不过也要考虑到，这个东西
> 确实值得加上去，并且它不是只在某个特定场景下才起效，而是需要具备
> 一定的通用性。当然，也不是说在特定条件下起效的就不能加，
> 只是需要把这些特定条件顺便加上去。」

**⇒ 而我原来只用了"可机械化"这一条，于是把两类混成同一类**：

| | 可机械化 | 有通用性 |
|---|---|---|
| 该加 | ✅ | ✅ |
| 该加（附条件） | ✅ | 中 —— **把特定条件一起写上** |
| 只诊断 | △ | — |
| 只进纪律 | ✗ | — |

★ 关键补正：**"只在特定条件下起效"【不是】排除理由** ——
只要把那个条件一起写进判据。例：
  · j-0002（对照对）只在"有判据可对照"时适用 ⇒ 判据里写明这个前提
  · j-0008（搬运底本）只在"搬运类任务"上适用 ⇒ 判据里写明任务类型

> 「那个接缝的判定，我是认可的。你确实需要对每个模块去做一些规定和要求。

★ 而 2026-10-07 那天出现了 **5 次接缝**，而它们是**三种不同的形状** ——
⇒ 所以不是一条判据，而是三条。

### S1 供给必须有消费

```

  · t54：discriminatingFiles → newTestFiles，而它的门（r5）不再对 repair 生效
          ⇒ 那条证据被生产出来而没人消费

★ 判据形状：每一份【被生产出来的东西】，都要有一个【读它的地方】。
  而它是本队那句话的机械化：
    「一个没有调用方的产出，与没有那个产出在观测上完全相同。」
★ 可机械化：扫产出点 ⇒ 断言存在读取点。★ 通用性：高。
```

```
今天出现 1 次：

    ⇒ ★ 而那是"5 个 kind 的完工位置永远报 ok"的根因

★ 判据形状：每一层的裁决，都要能被【下一层读到】——
  而"没检查"与"检查了而通过"【不同形】。
★ 可机械化：断言位置级的裁决是判据层裁决的【函数】（而不是一个独立判断）。
★ 通用性：高 —— 任何多层裁决都适用。
```

### S3 接线要被钉住（而不是"那个函数存在"）

```
今天出现 1 次：
  · t39 拆 tools.ts 时，t41 的接线（a0f6504）被搬回旧版（9779c58）
    ⇒ ★ 而它静默了几个小时，直到 t56 的成员被那条拒绝挡住

★ 判据形状：断言【那个调用点】存在 —— 而不是断言那个函数存在。
  ★ 而这两者在"函数还在、而没人调用"时【同形】，而那是本队记账最久的形态。
★ 可机械化：断言某个位置调用了某个函数（按调用点断言，不按定义断言）。
★ 通用性：高。
```

## 十一、★ 用户裁定：**写域冲突就不派**（2026-10-08）

**用户原话**：

> 「写域冲突就先别派，虽然多 worktree 可以做冲突消解，但是会带来新的工作量和混乱。」

**⇒ 而它回答的是"并发怎么打满"这件事里最容易被做错的一格**：

```
★ 冲突检测报"重叠"之后，有两条路：
  ① 不派，等写域真空出来
  ② 派出去，靠多 worktree 做冲突消解

★ 而 ② 看着更"把并发打满"，实际是把【冲突】从"建任务时"推到"合并时"——
  而合并时的冲突更难解（两个成员各自改得有理，而合起来可能都不对）。
⇒ ★ 所以 ① 是【更省】的那条：
  它把冲突挡在【零成本】的时刻（建任务时），
  而不是让它变成一份真实的返工。
```

**★ 而这与本队那条纪律同源**：

```
「一个任务改的东西，应当是【它能独立论证】的那一个。」
⇒ 而两个任务改同一个文件时，那个"独立"就不成立了 ——
  无论它们各自多正确。
```

**★ 而它的代价也要如实说**：

```
★ 不派 ⇒ 成员会空闲，而并发数会下降。
★ 但那不是"调度没做好"—— 那是【真实的依赖】：
  写域重叠 = 两个任务在改同一件事的两端 ⇒ 并行会让两边都读不准。
⇒ ★ 所以"把并发打满"的正确含义是：
  **让每一条都在等一个真的必要的东西**，而不是"派尽可能多的任务"。
```

### 而由此产生的一条调度纪律

```
★ 当冲突检测报重叠时，captain 的动作是：
  ① 把那条任务记成【待办 + 被谁挡着】（而不是硬派，也不是忘掉）
  ② 在被挡住的情况下，去问【那个挡人的文件，能不能被拆开】——
     ★ 而那是一个【结构性问题】，不是"再等等"
  ③ 而若它【确实不能被拆】（例如它真的是一件事），那就等 —— 而那是正确的
```

**★ 而本仓库当前的实例**：

```
★ update-task.ts（868 行）挡着三条任务，因为它装着【三个插入点的接线】
  （contract / dispatch / completion）
★ 而那正是 t39 那条"冲突面 16 → 2"里的【那 2】——
  而今天它从"设计里标注的下一步"变成了【真实的瓶颈】。
```

## 十二、★ captain 的裁定：j-0003 那条分歧，划在【工具那一侧】（2026-10-08）

**背景**：t65 交付的分类工具跑了一遍，与 captain 手写的表比对得出
`7 agree, 1 disagree, 1 uncomparable`。而那个 disagree 是 **j-0003**：

```
工具判 gate      —— 断言【写出来之后】，它读的东西现成可取吗？
                     ⇒ j-0003 的断言会读「夹具里的距离/行号/缩进」⇒ 现成可取 ⇒ gate
表   判 diagnosis —— 【构造】这条断言需要理解语义吗？
                     ⇒ 找「哪个读数是代理」需要理解 ⇒ diagnosis
```

**⇒ 而 captain 裁定：【工具那一侧】，而表那一侧是错的。**

**理由一（执行者视角）**：

```
判据的执行者是【机器】，而机器只面对"写出来之后的断言"。
"构造它需要理解什么"是【作者】的事 —— 而那件事在判据跑起来之后就不存在了。
⇒ 按"构造"划，会把一个【关于作者】的性质，写进【关于判据】的读数里。
```

**理由二（可复核性）**：

```
"写出来之后读的东西现成可取吗" ⇒ 【可机械判定】（看它读什么）
"构造它需要理解吗"            ⇒ 不可机械判定
⇒ ★ 而那条工具【自己】已经把"需要理解"这一类判成 discipline 了 ——
  所以它不可能再用同一个标准去判 j-0003。
```

**理由三（最关键）**：

```
★ j-0003 的 counterexample 说得极清楚：
  「若那个代理读数【直接就是】它要测的东西（例如它读的是一个布尔字段），
    那它不会这样失效。」

⇒ ★ 也就是说：这条判决的断言是【可写的】——
  它读的东西（距离、行号、缩进）现成可取，
  而"是不是代理"由【那个读数的定义】决定，不由"构造者的理解"决定。
```

**★ 而表那一条错在哪里（如实记）**：

```
★ 我当时判"它只能诊断"，理由是「找哪个读数是代理需要理解」——
  而那说的是【这个判据怎么用】，不是【这条判决能不能写成断言】。
⇒ ★ 我把【使用的难度】读成了【可否机械化】。
```
