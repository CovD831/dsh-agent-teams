# 判据注册表：契约

> **这份文件是【接口】。** 判据的实现可以换，这份契约不换。
> 目的：让"加一条判据 / 换一条判据"不触碰编排层，也不触碰别的判据。

---

## 0. 它解决的是什么问题

上游 `dsh-agent-teams` 的判据全在**一个文件**里：

```
src/quality-gates.ts   1233 行 · 34 个导出平铺
```

⇒ 想加一条判据，必须改那个文件 ⇒ **它一升级就冲突**。
⇒ 而开发流程会变 ⇒ 冲突会反复发生。

**⇒ 把判据从"那个文件"里挪出来，放进一个注册表；编排层只认【插入点】，不认判据。**

---

## 1. 五个插入点（按流程位置，不按模块）

| # | 插入点 | 什么时候 | 上游对应函数 | 能拿到什么 |
|---|---|---|---|---|
| ① | `contract` | 建任务、改契约 | `validateCreateTask` / `amendTaskContract` | 团队状态 + 待建/待改的任务 |
| ② | `dispatch` | 派发前（成员开工）| *（上游没有）* | 团队状态 + 任务 + ★ **该成员的会话事件**（归属证据的来源）|
| ③ | `completion` | 成员汇报完成 | `evaluateQualityCompletion` | 任务 + 本次提交 |
| ④ | `delivery` | 团队宣布交付 | `canDeclareDelivery` | 团队状态 |
| ⑤ | `runtime` | 全程（跨步骤）| *（上游没有）* | 见 §5 |

**★ 五个是【位置】，不是【判据】**。一个位置可以挂零到多条判据。

**★ 为什么按位置分而不是按模块分**：位置是流程的形状（你说流程会变），
模块是实现的形状（换了实现位置不变）。**判据挂在位置上，换实现不影响接线。**

---

## 2. 判据的统一形状

**每条判据是一个函数，签名完全相同**：

```ts
type GateVerdict =
  | { ok: true }
  | { ok: false; blockers: string[] }        // 拒绝，且必须说清为什么
  | { ok: false; unmeasured: string }        // ★ 没能测量（§3.4：不得并进"测了是零"）

type Gate<P> = (context: P) => GateVerdict | Promise<GateVerdict>
```

### 三条不可协商的性质

| # | 性质 | 为什么 |
|---|---|---|
| **1** | **纯函数**（`runtime` 插入点例外，见 §5）| 上游 `quality-gates.ts` 是零 I/O 的，我们顺着它。**需要 I/O 的判据由调用方注入执行器**（今天的 `rerunVerifyCommands` 就是这么做的）|
| **2** | **判据之间不互相调用** | 否则删一条会连带删另一条 |
| **3** | **必须能表达"我没测"** | `unmeasured` 与 `blockers` 不同形 —— 空回复不是"没问题" |

### 为什么裁决有三个分支而不是两个

上游的裁决只有 `{ok:true}` / `{ok:false, error}` 两态。**而那正是我们今天验证过的漏洞的同源**：

```
成员的审查返回了空回复  ⇒  落进 "ok: true"  ⇒  读起来像"审查通过、没发现问题"
```

**⇒ 第三态 `unmeasured` 是判据必须能说的一句话：「我没能测量」。**

## 3. 注册表的形状

```ts
interface GateRegistration<P> {
  id: string                  // 稳定标识，用于替换/注销/控制台显示
  point: InsertionPoint       // 五个之一
  description: string         // 控制台显示用（一句话说清这条判据管什么）
  appliesTo?: (ctx: P) => boolean   // 可选：只对某些 kind 生效
  gate: Gate<P>
}
```

**注册表本身只做三件事**：

```ts
register(reg)                 // 加一条（重复 id ⇒ 报错，不静默覆盖）
evaluate(point, context)      // 跑该位置的全部判据，合并裁决
list()                        // 控制台读它
```

### 合并规则（★ 这是语义的一部分）

```
任何一条返回 unmeasured   ⇒  整体 unmeasured（★ 未测量优先于通过）
否则任何一条返回 blockers ⇒  整体 blockers（全部 blocker 都收集，不是只报第一条）
否则                      ⇒  ok
```

**★ 为什么 unmeasured 优先于 blockers**：

```
一条判据说"我发现问题"      ⇒  那是一个测量结果，可以据此行动
一条判据说"我没测成"        ⇒  那意味着【其余判据的通过也不可信】
⇒ 后者更严重
```

**★ 为什么收集全部 blocker 而不是第一条**：

上游 `evaluateQualityCompletion` 是**遇错即返回**（`return { ok:false, error }`）。
⇒ 修一个、再跑、又冒出一个 ⇒ **一轮只能发现一个问题**。
**而今天我们已经见过这个代价**：`grep -qx 7` 与「绝对路径」是两个独立问题，
串行发现花了三轮。

## 4. 一节一文件（防冲突的落点）

```
gates/
  registry.mjs          注册表本身（不加判据）
  contract/
    verify-command.mjs   · verify 命令写得对吗（今天踩两次的那条）
    objective.mjs        · 目标可判定吗
    scorer-reach.mjs     · 写域碰到判据文件了吗
  dispatch/
    changed-paths.mjs    · ★ 已生效（自报改动必须对得上真实写入）
  completion/
    verify-rerun.mjs     · ★ 已生效（verify 由判据层重跑）
    r5.mjs               · 红前绿后
    mutation.mjs         · 变异测试
  delivery/
    coverage.mjs         · 每个目标都有任务认领
    convergence.mjs      · idle ≠ converged
  runtime/
    with-timeout.mjs     · 有界等待
```

### ★ 归属证据：`dispatch` 位置能拿到什么（2026-10-05 落地）

`dispatch` 位置可以拿到**该成员的会话事件**，于是判据能问一个此前问不出的问题：
「自报的改动，真的是这个成员做的吗」。

```
dsh-tool-fs 给每次写入/编辑的 tool/result 挂 meta.diffs：
    meta.diffs: Array<{ path, oldText, newText }>
读它的入口：src/harness-compat.ts 的 observedChangedPaths(session)

★ 形状关键：undefined（没能观察）与 []（观察了，确实没写）必须不同形。
  前者 ⇒ unmeasured；后者 ⇒ 可以据此判定"虚报"。
  把这两件事混起来，一次读取失败就会伪装成一个关于工作的结论。
```

**★ 为什么这条重要**：它把"哪些文件是这个成员改的"从 git/cwd 里解放出来
（成员共用目录、cwd 又硬编码继承父会话）。

**★ 但它只解决【归属】，不解决【版本】** —— 两者别混：

```
会话事件回答      ：哪些文件是哪个成员改的          （completion 的变更审计）
会话事件【不能】回答：一个可 checkout 的父版本在哪    （R5 / 变异测试需要）
    meta.diffs 给的是 { path, oldText, newText } —— 一次编辑的前后文本，
    拼不出可信的父版本；父版本只能来自 git 历史。
⇒ 父版本由 src/worktree.ts 提供（每任务一个 detached worktree，
  `createTaskWorktree` 返回的 `base` 就是那个父版本 hash）。
⇒ R5 = 归属（§5.1 已解决）+ 版本（worktree 已落地，见 START-HERE §5.2）
```

**★ 一条判据一个文件**，理由：**两个判据改在同一个文件里，就是我们要消灭的那种冲突**。

## 5. `runtime` 插入点是特殊的

前四个是**裁决**（在流程的某一刻问"行不行"）。
`runtime` 是**跨步骤的过程约束**，所以它：

- **可以带状态**（例如：一个计时器）
- **不能拒绝任务**（它管的是"过程健不健康"，不是"这一步过不过"）
- **它的产物是【告警 + 证据】**，落进执行日志，供控制台与交付时判读

```
例：with-timeout
  · 在成员被派发时启动
  · 超时 ⇒ 产生一条"这个成员超时了"的记录
  · 它不直接拒任务（拒任务的该是 completion 位置上的一条判据，
    读这条记录 ⇒ "verify 是在一个已超时的成员上报的" ⇒ 拒绝）
```

**★ 这样分层，是为了让"过程"与"裁决"不搅在一起** ——
今天我们把超时和裁决混在一处（`finally` 里 dispose），就出了缺陷⑤。

## 6. 每条判据必须自带三臂夹具

**这是"证明加上去有用"的形式化**，也是今天验证有效的方法：

```
臂 1（伪造臂）：判据【应该拦住】的输入        ⇒ 期望 blockers / unmeasured
臂 2（违规臂）：边界但不是伪造（如契约写错）  ⇒ 期望它不误伤（或不拦）
臂 3（对照臂）：完全合法的输入                ⇒ 期望 ok
```

**★ 缺任何一臂，这条判据不算完成。**

理由：今天 t2 的教训 —— **我的契约写错了，而它与"判据抓到了伪造"在日志里同形**。
只有对照臂能区分「判据有效」与「判据在乱拒」。

## 7. 控制台读什么

控制台不需要新数据源。它读注册表 + 执行日志：

```
① 当前流程有哪几个插入点          ← registry.list() 按 point 分组
② 每个插入点挂了哪些判据          ← registry.list()
③ 每条判据这一轮跑没跑、结果是什么 ← 执行日志（每条裁决一条记录）
④ 替换某个插入点的判据            ← register/unregister（不改代码）
```

**★ 结论：控制台不是额外工作，是注册表的视图。**
**⇒ 所以注册表的数据形状要做成"可被直接渲染"的，而不是内部表示。**

## 8. 与上游的关系（可插拔的真正含义）

```
上游升级（它改自己的 quality-gates.ts）
  ⇒ 我们不碰它 ⇒ 零冲突

我们要换一条判据
  ⇒ 在我们自己的 gates/ 里换 ⇒ 不碰上游、不碰别的判据

上游要读我们的判据
  ⇒ 只通过 registry.evaluate(point, context) 这一个接口
  ⇒ 它不需要知道有哪些判据
```

**★ 唯一的耦合点是那五处调用**（`tools.ts` 4 处 + `state.ts` 3 处）。
**⇒ 那五处是我们要改上游的【全部】，而且只改一次。**

## 8.5 ★ 两条从本轮实战里长出来的规则（2026-10-06）

> 本轮把五个位置中的四个接满判据（`runtime` 位置已可达、等第一条判据），
> 过程中同一个毛病在**不同位置重演了五次**。这两条规则是从那五次里提炼的，
> 它们**约束未来的判据与接线**，不是对已发生事情的叙述。

### 规则一：「可判定的事实」不得写成「没能测量」—— **跨层规则**

```
unmeasured 的含义是「我没能测成」。它有一条容易被误用的性质：
它让门【永久关闭】（调用方读到 unmeasured 就拒绝）。

所以把下列东西写成 unmeasured 是错的：
  · 不适用          —— 如 kind=work 本就没有 inScope / verify 要求
  · 可判定的事实    —— 如成员从未 spawn（是「它没起来」，不是「我不知道」）
  · 空的测量结果    —— 测了，是零

它们各自有正确的表达：
  不适用          ⇒ ok（并且要与「测过了」不同形，带 skipped 之类的标记）
  可判定的事实    ⇒ blocked（说清成因）
  测了，是零      ⇒ ok 或 blocked（按结论）
```

**★ 这条不只约束判据 —— 两侧都会焊门，只是位置不同**：

| 侧 | 怎么焊门 | 本轮实例 |
|---|---|---|
| **判据侧** | 把可判定的事实归入 unmeasured | `convergence` 把「从未 spawn」当「没能测量」 |
| **调用方侧** | 在交出去之前把观察面整个丢掉 | `observeMemberConvergence` 的 `return undefined` |

**判据的缺省方向应当是【拒绝】，但「拒绝」不等于【unmeasured】。**
正确的分界不是「能不能读到那个东西」，而是「**这件事可不可判定**」。

### 规则二：没被突变抓住的修复，等于没修

```
每个 finding 修完，必须能用一次【定向突变】把它打红。
打不红，说明夹具没有覆盖它 —— 那么下一个接线会让同一个毛病静默退回。
```

**本轮实测**：`contract` 位置补上执行器注入后，删掉注入做突变检验，
原有 **25 条臂全绿** —— 也就是说**此前没有任何臂钉住那个 finding**。
补上守门臂之后，同一突变立刻变红。**「修好了」与「有人看着它不再退回」是两件事。**

### 规则三（checklist，不是叙述）：接线一轮之后逐项检查

**为什么是 checklist**：这五次分别发生在**五个不同的文件**里，
一条叙述性规则抓不住它 —— 而逐项检查能。

```
□ 有没有夹具把「当前数量 / 当前为空 / 当前形状」写成了不变量？
    （本轮 5 次：位置为空 → inScope 缺席 ×2 → 会话观察面 → 硬编码工具数）
□ 有没有既有 fixture 的输入形状，因新接线而【不再合法】？
    （本轮 4 次：contract 位置为空 / inScope 缺 lib ×2 / 会话缺 assistant 消息）
□ 每个 finding 的修复，能不能用一次定向突变打红它？（规则二）
□ 新判据的【输入面】接上了吗？——判据接进来 ≠ 它的输入接进来
    （本轮 3 次：inScope / verify / 执行器，同一张验收表上的三格）
```

**★ 规则三有个正面解释**：这四次「既有 fixture 不再合法」**全都是接线成功的信号**——
它们证明新判据在**真实路径**上真的会开火，而不只是在夹具里会开火。

## 9. 已知的边界（不假装它能做更多）

1. **插入点是固定的五个** —— 要加第六个位置，得改上游（那是流程形状的变化，不是判据的变化）。
   现已用上 `contract` / `dispatch` / `completion` / `delivery` 四个位置；
   **`runtime` 位置已有五个调用点（且证明可达），但还没有判据** ——
   它与"挂上去也永远不会跑"的空位置【不同形】。
2. **判据拿到的输入面由上游决定** —— 它不传的东西，判据拿不到。
   ★ 但**会话事件**是一个例外且很有用：插件能通过 `sessionOwnEvents()` 自己读到
   逐成员的历史（`tool/result` 的 `meta.diffs`），不必等上游传。
3. **`runtime` 的告警不能直接拒任务** —— 见 §5，这是刻意的
4. **注册表本身在上游之外** —— 但**接线点在它里面**，所以不是零耦合。
   ★ 接线点现有 6 处（`tools.ts` 的 update_task 里 `dispatch` + `completion` 各一次）。
