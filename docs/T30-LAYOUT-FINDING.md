# t30 的前置发现：成员行之间的空白（MEASURED 2026-10-11）

## 由来

用户看到侧边栏的团队面板"无法正常显示，好像有一定的放大和截断"，并且**点击看不到
成员内部情况**。用户还反馈**打不开浏览器控制台**，所以队长改为**自己探查**。

**这份文档的存在理由**：t30 在失败后**契约不可再编辑**，而下面的读数是在它失败
**之后**才测出来的。如果只写在对话里，下一个人接 t30 时会**重新猜一遍** —— 而
这一轮反复证明"重新猜"比"留下读数"贵得多。

## ① 已经排除的（都不是原因）

| 假设 | 实测结论 |
|---|---|
| CSS 没加载 | ❌ 列宽与声明**逐一吻合**（见下） |
| 头像是"巨大"的 | ❌ 我忘了除以 Retina 2×，实测 43.5 CSS px vs 声明 42px ✅ |
| 展开层在占位 | ❌ 折叠时**根本不渲染**（结构探针数出 0 个） |
| CSS 产物没生成 | ❌ `lib/client.js` 里 4 个 `data-plugin-css` 注入点与完整 CSS 文本都在 |
| 构建陈旧 | ❌ stamp 与 HEAD 一致，且 bundle 里有 R2 的 4 列规则 |

## ② 行本身是**对的**（像素测量，截图是 2× Retina）

以行左边缘为 0，实测（已折半为 CSS px）：

| 实测 x | 宽 | 对应 | 声明 | |
|---|---|---|---|---|
| 33.0–34.5 | 1.5 | 左侧竖线 | 1px | ✅ |
| **60.5–105.5** | **45.0** | 头像 | 列 1 = 46px | ✅ |
| **111.5–127** | **15.5** | 状态点 | 列 2 = 16px | ✅ |
| 135.5–145 | 9.5 | 箭头 | — | ✅ |
| 173–201.5 | 28.5 | 文字 | 列 3 | ✅ |

**行高 43.5 CSS px** vs `min-height: 48px` ✅

⇒ 所以 `grid-template-columns: 46px 16px minmax(0,1fr) 96px` **确实生效**。

## ③ 错的是**行与行之间**

```
行 1 顶部:  y = 621 (物理)
行 2 顶部:  y = 1261
⇒ 行距 640 物理 px = 320 CSS px

而样式声明只有:
  .memberBlock   padding: 3px 0 7px     = 10px
  .delegationTree gap:    2px           =  2px
                            合计        = 12px

⇒ 实测是声明值的 26 倍
```

而那 320px 空白里**只有两个孤立的小点**（x=107 与 x=272），**没有任何文字**。

## ④ DOM 结构是最小的（受控复现）

队长挂起**真的 `TeamSection`**（复用 `workspace-activity.test.mjs` 的最小 DOM 与
宿主 stub），打印出结构：

```
.delegationTree[data-member-rows=2]
  .memberSlot
    .memberBlock
      <span .memberBranch>        ← 绝对定位，不占布局
      <button .memberRow>         ← 恰好 4 个网格子元素，与 4 列吻合
        <span .memberAvatar>  <span .memberDot>
        <span .memberInfo>    <span .memberStatusTail>
```

**折叠时 `memberSubagents` 容器数量 = 0。**

⇒ 所以**行内没有多余元素占位** —— 空白**不在行内**。

## ⑤ ★ 缺的那一个读数

最小 DOM **没有布局引擎**（`getBoundingClientRect` 恒返回 0），
而截图只能给"渲染后的像素"。

**⇒ 两者之间缺的正是"计算后的样式"（computed style）。**

⇒ 而用户打不开 DevTools，所以队长**停在这里**，没有继续猜 ——
这一轮的教训之一就是"没量就下结论"会错（见 §① 的 Retina）。

**⇒ 接 t30 的人要做的就是补上这个读数，在一个真实浏览器里。**

## ⑥ 顺手测到的一条死规则

```css
.memberSlot[data-has-model='true'] { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
```

**`data-has-model` 在全部 `.tsx` 里从未被设置过**（grep 实测）。
⇒ 它是一条**读起来像在管事、实际不生效**的规则。**删掉它**，或让它真的被设置。

## ⑦ 给 t30 的验收（它失败后契约已冻结，见本文档开头）

1. 拆分的**集合比对**（既有要求）
2. **行距必须等于声明值**：相邻行**顶部**相距 12px + 行自身 48px
   —— 而**必须由真实浏览器测量确认**，不是读样式表
3. 测量**走侧边栏路径**（`WorkspaceActivity → TeamSection`），
   因为**那是用户看到缺陷的那条路**，而**它此前从没有样式测试**
4. 删掉 §⑥ 那条死规则
5. 每条新臂都要有**反向的一半**

## ⑪ ★★★ 队长撤回 §③ 的 320px：那是**我的测量错误**

**（2026-10-12，由 `ui-eng2` 的实测推翻，队长复核后采纳）**

### 用真实浏览器测出来的读数

`ui-eng2` 用无头 Chrome（154，DevTools Protocol，**没有新增依赖** —— Node 自带的
`fetch`+`WebSocket` 驱动本机已有的 Chrome）渲染**真实的编译后样式表**，在**真实的侧边栏嵌套**
下逐宽度测量：

| 侧边栏宽 | 列宽 | 行高 | **相邻行顶差值** |
|---|---|---|---|
| 1440 | 528.5 | 50 | **62.0** |
| 900 | 860 | 50 | **62.0** |
| 700 | 660 | 50 | **62.0** |
| 420 | 380 | 50 | **62.0** |
| 388 | 348 | 50 | **78.2** ← 只有它不同，而它**往另一个方向**偏（状态行换行） |
| 展开（3 个容器） | — | 50 | **100.0** |

**⇒ 而 62px 正是声明值**：`memberRow(48) + memberBlock padding(3+7) + delegationTree gap(2) = 60`，
行高实测 50（多出的 2 是边框）。

**⇒ 所以 §③ 说的"是声明值的 26 倍"是**错的** —— 声明**本来就是对的**。**

### ★ 我的 320 是怎么来的（这才是本节的价值）

**⇒ 它来自一张**截图**，而**不是布局引擎**。**

**§④ 自己就写着：最小 DOM **没有布局引擎**（`getBoundingClientRect` 恒返回 0），
所以那些 y 值只能来自"**渲染后的像素**"** —— **也就是那张图。**

**⇒ 而 §③ 从那两个 y 值（621 与 1261，物理）直接断言它们是**相邻的两行成员行** ——
这一步**我从未验证过**。**

**⇒ ★ 而那是**同一个错误的第二次**：§① 我已经犯过一次 Retina 倍率错误，
而这次犯的是它的近亲 —— **从一个像素读数反推它是什么元素，而不去核对那个对应关系。** **

**⇒ 所以 320 的**成因**是：**我把两个**不属于同一对相邻行**的 y 值配成了一对。**
（**具体是哪两个元素，我没有直接证据** —— **而它作为一个"未解释"比一个编出来的解释更有价值。**）

### 而它顺带**排除**了一个我曾以为是主因的假设

**⇒ 我先前猜"两屏共用一个网格"造成了行距异常 —— 而实测**否定**了它：**

```
≥1000px 时那条两列网格规则【确实生效】
  （1440 下 display:grid，grid-template-columns: 528.531px 839.469px；
    900 下回退成 flex）
★ 而行距在【两种情况下都是 62.0】
⇒ 网格与行距【无关】
```

**⇒ 所以拆分仍然是对的**（**1171 行的文件混着两屏，那是**可评审性**与**改动冲突**的问题**），
**但理由**不是**行距**。**⇒ 而**不能**声称拆分修好了 320px，因为**320px 不是真的**。**

### 可迁移的纪律

1. **从一个像素反推元素对应关系时，必须先验证那个对应** ——
   `y1=621, y2=1261` **不等于**"这是相邻两行"；那是一个**假设**，而假设要单独核。
2. **"测不了"就去借一个能测的工具** —— 最小 DOM 没有布局引擎，而本机有 Chrome；
   `ui-eng2` 用 Node 自带能力驱动它，**零新增依赖**。
3. **一个被推翻的读数要留档，并写清它是怎么错的** —— 只写"62 才对"，
   下一个人仍会踩同一个坑；写上"320 来自截图配对错误"，它就成了**可识别**的形态。
4. **我自己 §① 的教训没有被我用到 §③ 上** —— 同一个会话里犯了两次同族错误，
   而两次都是"读数正确、解释错误"。
