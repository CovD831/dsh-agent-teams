## 0. 用户的原话（这是本文件唯一的依据）

> 「原本大家都是做**侧边栏**形式，比如 Codex 这样，侧边栏里有一个个项目，
>  项目内有一个持久的 task 或 session。**但后来大家发现这种形式并不好**：
>
> **1. 历史的 session 其实你也不会回去看**
> **2. 在做多项目并发跑的时候，每个项目都有 session 在跑，而且每个项目里又有很多个 session，
>    导致项目之间被隔开了，不太好去观察每个 session 到底在干什么**
>
> 所以我觉得，最后呈现的形式应该是像现在主流的 **BOT** 一样（不管是 Grok BOT 还是 OpenAI 的 dot），
> 它们都偏向于把**对话入口只压缩在一个地方**，**人可以看到好几个项目在工作，但对话入口可能只有一个**。
>
> 所以我对 Agent Teams 的想法是：**目前它可能还只是一个侧边的单项目可视化**，
> 能让我看到这个 Agent Team 的各个成员在干什么，以及整个流程。
>
> 那我后续想的就是**直接改造整个 DSH**：
> 1. **只有一个入口进入，一个 Agent Team 对应一个项目**
> 2. **直接看到好几个 Agent Team 在干活，不需要再去查看每个项目的每个会话了**」

## 1. ★★★ 我错在哪（两处，都要留痕）

### 错误 ①：我用「队级」指了两个不同的东西

我说「L1 队级 / L2 成员级 / L3 任务级」,而用户问:
> 「你说的一个"**队级**"和"**成员级**"是什么意思？」

**用户澄清**:
> 「目前而言，我们的 Agent Team **只是在一个项目里面存在**，并且我**同时可能只能看到一个 Team** 在干活。
>  所以，**目前其实是没有"队级"信息的，只有"成员级"的信息**。
>  后续可能才会出现"队级"的信息，因为我可能要好几个项目同时开工，需要拉起好几个 Agent Team。」

⇒ ★★ **「队级」必须分成两个意思,而我混用了**:

| 词 | 意思 A | 意思 B |
|---|---|---|
| **队级** | ★ **同一个 Team 的整体聚合**（现在的需求）| ★ **跨 Team 的汇总**（**改造 DSH 之后**才需要）|

⇒ **现在只需要 A。** 用「队级」指 A 会让人以为要做跨 Team 汇总 —— **那是将来的事。**

### 错误 ②：★★★ 我以为「判据管线是主屏」,实际**正好相反**

**B1 的样张把六个插入点画成了主屏**（六个点 × 四符号）。
用户纠正:
> 「如果是 Agent teams 它的一整个管线的话，其实这个管线就是一个个模块嘛……
>  **除了想看到目前的呈现（比如他工作了多久、进行到第几轮），我可能希望看到更多**。
>  因为我们还做了**变异测试**等，这些其实也是**成员内部的一个流程**，
>  所以总体而言，**可能还是以成员为主**。
>  ★ **如果以管线为主的话，感觉成员是不是就不太好呈现更多的东西了？**」

★★★ **这个判断是决定性的,而我搞反了**:

```
判据插入点（contract → dispatch → completion → delivery）
  ⇒ 它描述的是【任务的阶段】，★ 不区分是谁在做
  ⇒ 它是跨成员的【同一条】轴线

变异测试等
  ⇒ 它发生在【某个成员内部】
  ⇒ 它描述的是"这个人在这一步里干了什么"

★ 若以插入点为主屏 ⇒ 主屏只有"阶段"，★ 没有位置放"成员内部在做什么"
★ 以【成员】为主屏   ⇒ 每个成员展开后，【里面】就是他的判据管线
```

⇒ ★★★ **结论:「判据管线」不是主屏,它是【成员展开后的内容】。**

### ★ 而用户自己把「管线」分成了两种（这是最关键的区分）

> 「关于"管线"的定义，需要区分一下：
>  **1. 判据插入点的管线**：这是**大的管线**，它其实**只需要在背后知道一个流程就行了**。
>  **2. 我所说的管线**：因为我们**造了很多判据，并且做了很多约束**，
>    所以我希望能**体现出这些约束**。」

| | 是什么 | 该不该占主屏 |
|---|---|---|
| **① 判据插入点管线** | **大管线** —— 任务的阶段轴 | ★ **「只需要在背后知道」** |
| **② 约束的体现** | ★ **"我们造了很多判据/做了很多约束"这件事** | ★ **要显示,但它是成员内部的** |

★★ **所以 B1 样张画的是 ①,而用户要的是 ②。** 两者**不是同一层的东西**。

## 2. ★★★ 修正后的信息架构

### 2.1 现在（阶段一：单项目、单 Team）

```
┌─ 侧边栏：Agent Team 的面板（现在的形态）────────────────┐
│                                                          │
│  ★ 以【成员】为主屏 —— 这已经是现状的方向（组件名就是证据）│
│                                                          │
│    captain  ●  第 2 轮  12m                             │
│    archaeologist ●  implementing t59 · 变异测试 8/14     │
│    test-triage   ○  idle                                │
│    ...                                                   │
│                                                          │
│  ── 点开某个成员 ──────────────────────────────────────  │
│                                                          │
│  ★【成员内部】= ② 约束的体现                            │
│    · 他当前任务走到哪个阶段（① 大管线在这里出现,作为背景）│
│    · ★ 变异测试等【成员内部的流程】                      │
│    · 判据在他这一步的裁决（✓/⊘/●/✗ + 观察模式）          │
└──────────────────────────────────────────────────────────┘
```

★ **关键**:① 大管线**不占主屏**,它在成员展开后**作为背景轴**出现。

### 2.2 将来（阶段二：改造 DSH 之后）

> 「**只有一个入口进入，一个 Agent Team 对应一个项目**
>  **直接看到好几个 Agent Team 在干活，不需要再去查看每个项目的每个会话**」

★★ **这是对 DSH 本身的信息架构改造** —— 三篇里 **Codex 和腾讯都是"侧边栏 + 项目树"**,
而用户的判断是**那种形式不好**,理由给了两条（历史 session 不回看 / 多项目并发时被隔开）。

★ **参考形态**:**Grok BOT / OpenAI dot** ——
「**对话入口只压缩在一个地方,人可以看到好几个项目在工作**」。

⇒ ★★ **这不是本插件能单独完成的** —— 它要**改 DSH 的入口模型**。
⇒ **所以它是"后续计划",不是"现在做"。**

## 6. ★★ 仍需用户拍板的（一条,不是四条）

**问题**:成员展开后,「② 约束的体现」**具体显示到哪一层**？

| 选项 | 显示 | 代价 |
|---|---|---|
| **(甲)** | 只显示**当前阶段的判据裁决**（✓/⊘/●/✗）| 最简,但**变异测试等内部流程看不见** |
| **(乙)** | 显示**成员内部的完整流程**（含变异测试/红绿测试等）| ★ 信息量大,但要**新的数据出口** |
| **(丙)** | 分层:默认甲,**点开**才是乙 | 兼顾,但要设计"点开"的交互 |

★ **用户的倾向已经写明**:「**我希望看到更多**……变异测试等其实也是成员内部的一个流程」
⇒ ★ **倾向 (乙) 或 (丙)**,但**具体到哪一层需要用户确认**。

★ **而这决定了一件事**:`MemberScreen`（现在只到"任务 + 模型 + 轮次"）**要不要接判据数据** ——
而**判据数据已经有出口了**（A1 的 `gate_view`,`src/tools/status.ts`）。
