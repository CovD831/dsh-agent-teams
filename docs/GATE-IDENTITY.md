# 「一条判据」按什么认（t74）

> **一句话**：按**导出形状**认，不按**目录**认。
>
> 判据实施：`scripts/verify-gate-tristate.test.mjs` 的 `classifyGateModule`。
> ★ 这份文档解释**为什么**，以及**三态各自意味着什么**。

---

## 1. 缺陷（MEASURED，t69 归因）

那条普查原本**按目录扫**：`lib/gates/<point>/*.js` 里每个 `.js` 都算一个判据模块。

而 t54 往 `src/gates/completion/` 里放了**两个不是判据的文件**：

```
kind-requirements.json    —— ★ 数据
kind-requirements.ts      —— ★ 纯函数模块（导出 parseKindRequirements /
                              gateRequirementFor / loadKindRequirementsOfHost）
```

⇒ 普查把两者都当成判据模块 ⇒ 对它们跑「必须有 `id` / `point` / `description` / `gate`」
那套检查 ⇒ **红**。

★ 而**判据本身一条都没错** —— 错的是普查**认判据的方式**。

---

## 2. ★★ 为什么修法不是「把这两个文件加进白名单」

白名单要回答的问题是「**哪些非判据文件是允许的**」—— 而那正是错的问句：

```
按目录认 ⇒ 那个目录里将来放【任何】非判据的文件都会红。
          而 gates/<point>/ 是一个【合理的家】：
          判据、它用的数据、它用的纯函数模块，都会长在这里。
★ 每一次新增都要改白名单 ⇒ 那是一条【靠人记得维护】的规则 ——
  而"凭经验 / 靠记得"正是本队从头到尾在消灭的东西。
```

⇒ 改成按**判据的定义**认：

```
一个判据模块 = 导出了那四个名字的模块
               （id / point / description / gate —— 见 src/gates/index.ts 的 GateModuleParts）
```

★ 于是：
- 目录里多一个数据文件 ⇒ 它**不是判据** ⇒ 普查不看它 ⇒ **不红** ✓
- 目录里少一个 `gate` 导出 ⇒ 它**本应是判据而残了** ⇒ 普查**该红** ✓

---

## 3. ★★★ 三态：它必须能说「不是判据」，而不是静默跳过

| 态 | 判据 | 含义 | 该做什么 |
|---|---|---|---|
| `gate` | 四个关键导出**都在**（且 `gate` 是函数） | 它是判据 | 对它跑那套三态检查 |
| `notAGate` | **一个都不在**，且**说得出它是什么** | 它在这个目录里，但不是判据 | **什么都不用做** |
| `ambiguous` | 只导出了**一部分** | ★ 判不了 | **看一眼** |

### ★ 为什么 `notAGate` 必须【有理由可说】

一个被**静默跳过**的文件，与一条**被漏掉的真判据**在读数上**同形** ——
两者都是"普查里没有它"。⇒ 所以那类必须带一句人话理由（按它**导出了什么**说，不按文件名猜）：

```
纯数据模块      ⇒ "it exports nothing at all (a data-only module)"
纯函数模块      ⇒ "it is a plain-function module: it exports parseKindRequirements,
                    gateRequirementFor, loadKindRequirementsOfHost — none of them is a
                    gate definition"
普通工具模块    ⇒ "it exports CONSTANT, helper — none of the four gate-defining names"
```

### ★★ 为什么 `ambiguous` 不能并进 `notAGate`

「少了 `gate` 而其它三个都在」的模块，与「一个恰好导出了 `id` 的普通模块」在**形状上无法区分**。
⇒ 那一类**不许猜**：它落 `ambiguous`（判不了）。

★ 而这一条区分**很重要**：若把它并进 `notAGate`，一条**残了的真判据**会静默消失；
  若把它并进 `gate`，一个缺导出会在**装配时炸**（`register()` 校验），而普查却说它好。

---

## 4. ★★ 分水岭：同一份文件，两种口径给出**不同的动作**

```
旧口径（按目录）：kind-requirements.ts 缺 "id" ⇒ 红
  ⇒ 读的人会去【补一个 id 导出】—— 而它对一个纯函数模块完全没有意义

新口径（按形状）：kind-requirements.ts 是纯函数模块 ⇒ notAGate
  ⇒ 什么都不用做 —— 因为它本来就对
```

★ ⇒ **一条给出错误动作的红，是最贵的红。**
  它不只浪费一次排查：它会让人学会"这条普查爱误报" —— 而那之后它说什么都没人看了。

---

## 5. 反向半边：真的判据一条都不许漏

普查**按形状**认，风险是"认少了"。⇒ 那条反向断言必须存在：

```
注册表 11 条（已接线的），磁盘按形状认出 15 条，漏 0 条
★ 15 = 11 条已接线 + admission 3 条（尚未接线）+ contract.task-atomicity 1 条（诊断，不接生产）
```

★ 而"磁盘上多出来 4 条"本身是一条**读数**（"装了但调不到"），
  本文件照旧**报告**它、**不断言**它为 0 —— 因为把"此刻还没接"写成不变量，
  会在接线的那一刻按设计变红（t5 文件头明确禁止过那种棘轮）。

---

## 6. 这条口径与其它判据的关系

```
src/gates/index.ts 的 asRegistration     —— ★ 装配层用它【校验】判据（缺导出当场抛错）
scripts/verify-gate-tristate.test.mjs    —— ★ 普查用它【识别】判据（缺导出归一类，不抛错）
```

★ 两者读的是**同一组名字**（`id` / `point` / `description` / `gate`），而**行为不同**：

| | 缺一个导出时 |
|---|---|
| 装配层 | **当场抛错**（启动即炸，不静默少一条判据） |
| 普查 | **归 `ambiguous` 并报出来**（它还要能描述"磁盘上有一份残的"） |

⇒ ★ 两条路径**不互为替代**：装配层管"跑起来的那一批"，普查管"盘上那一批"。
  而"装了但调不到"正是两者**之间的差集** —— 那是本文件臂 0 一直在报的那条读数。
