## 9. ★ 交付机制的一处真实缺陷（队长 2026-10-15 实测）

**现象**：t18 报告「F1 已修，两条文档已提交（commit `e7c617b`），worktree 干净」，
而**队长工作区的两份文档仍是修复前的旧版**（`186 / 开火 8`）。

**定位**：

```sh
$ git branch -a --contains e7c617b          # ⇒ 空（不在任何分支上）
$ git worktree list | while read p _; do
    git -C "$p" merge-base --is-ancestor e7c617b HEAD && echo "$p"; done
  /Users/abab/Desktop/agent-teams-dev/.agent-teams/worktrees/task-agent-teams-refactor-t18
```

⇒ 提交落在**该任务自己的 worktree**（`.agent-teams/worktrees/<task>/`），
**没有回流到队长工作区**。

**内容差异（实测 md5 不同）**：

| 文件 | worktree 提交 | 队长工作区（当时） |
|---|---|---|
| `docs/GATE-EFFICACY.md` | 546 行 | 461 行 |
| `docs/GATE-EFFICACY-CONTEXT.md` | 243 行 | （旧版） |

**危害（差点造成误判）**：`t19` 复审员读的是**队长工作区**。
若不先取回，它会看到**已被判定为错的那一版**（186 / 开火 8），
从而可能判「F1 未修复」—— 而那与事实相反。

**处置**：队长把 `e7c617b` 的两份文件取回队长工作区后，t19 才读到正确版本。

```
git -C .agent-teams/worktrees/<task> show e7c617b:docs/GATE-EFFICACY.md > docs/GATE-EFFICACY.md
git -C .agent-teams/worktrees/<task> show e7c617b:docs/GATE-EFFICACY-CONTEXT.md > docs/GATE-EFFICACY-CONTEXT.md
```

★★ **这是一条系统性的记账缺口**，值得与 t14 报的 scope 误报一并看：

1. **任务说"同步回队长工作区"，但没有机械判据检查这件事** ——
   成员可以诚实地以为自己同步了（它确实写了文件、也确实提交了），
   而两处内容并不相同。
2. **复核员读的是队长工作区，实现者写的是自己的 worktree** ——
   两者的桥**没有人负责**。本仓有 `dispatch.worktree` 判据管"建得出隔离目录"，
   却**没有判据管"交付物回流"**。
3. ⇒ 正确的形态应是一条**「交付回流」判据**：任务完成时断言
   *队长工作区的那份文件内容 == 该任务提交里的那份*（md5 或 git hash 比对）。
   它可机械判定、可证伪，且正好堵住这一类沉默的失败。

★ 记在这里的理由：**这是"机制建好了，没有接线"的又一个实例**，
只不过这次缺的那根线是「交付物的回流」，而不是判据的注册。

| 9 | 复核员 | F4 是"规则与结果不符" | t18 | 机制层根因：正则末段 `[a-z-]+` **不含数字**，`completion.r5` 的 `5` 读不到 |
| 10 | 复核员 | 「76 vs 77」是窗口口径差异（与队长同错） | t20 | 同上，实测证伪 |

★ 注意第 9、10 条：**复核员的两次判断也被下游修正了。**
★ 而它自己**逐条记录、不作淡化**，并写下：
> 「对抗性复核的价值不在『我比作者强』，而在**独立复跑**这一动作本身。」

### 10.2 ★★ 这一族错的统一形状

**10 条里有 8 条是同一个病**：

> **把一个「读不到 / 没测过」读成了「就是没有 / 就是这样」。**

它的变体（全部本队实测）：
- `catch{}` 把**损坏**读成**不存在**（语料 372/384）
- `t.skip` 把**跳过**读成**通过**（t1 探针）
- 正则**数字盲区**把**含数字的 id 读成没有该 id**（`completion.r5`）
- 单归因面把**另一面没读**读成**没有归因**（29%/48.7%）
- 未实测的解释填补空白（76/77 的"窗口"假说）

⇒ ★★ **结论：对语料的不信任，必须同样施加于自己的聚合口径。**
   t18 自己写下的那句话是最准确的：
> 「这与报告自己的头号发现是**同一族的错**：不是『文件坏了被跳过』，
>   而是『**id 含数字的判据被静默漏算**』—— 一层之差，我的聚合器犯了同一件事。」

### 10.3 这条线上真正起作用的东西（可复用的机制）

| 机制 | 效果（本队实测） |
|---|---|
| **对抗性复核**（独立复跑，不复用作者脚本） | 抓出 blocker 1 条、high 3 条；且复核员自写独立读取器 |
| **反向半边**（把修复弄回去 ⇒ 判据必须红） | t20 用它证明 76/77 的成因（回到 `[a-z-]+` ⇒ 变 76） |
| **三态而非二值**（ok / blocked / unmeasured） | 「读不出」与「不一致」处置相反，不许同形 |
| **错误留痕**（§十 修订史、勘误表、显式否定） | 数字被更正三轮，而每一轮都能回溯 |
| **拒绝队长的建议**（t20 拒绝我的窗口解释） | 阻止了一条"看似合理但实测为假"的归因进入文档 |

★ 最后一条尤其值得注意：**t20 拒绝的是队长的建议，理由是队长自己立的判据标准。**
  ⇒ 这正是用户第 7 点所说的形态：**卡点被沉淀成机械判据，而不是沉淀成 prompt。**
