## 1. 现象（★ 比任务书报的更重）

任务书写「13 行 · 3 组 id 重复」。★ **实测是 15 行 · 5 组**：

```
.agent-teams/evolution/signals.jsonl   15 行
★ id 出现两次的: e-0001 · e-0002 · e-0003 · e-0004 · e-0005   （各 2 次）
形状两种:
   第 1–10 行 ← t88 手工补录  {"id": "e-0001", "at": "2026-…", "kind"…}   ★ 冒号后有空格
   第 11–15 行 ← t87 采集      {"id":"e-0001","at":1792145697290,"kind"…}   ★ 无空格
```

⇒ ★★ **`e-0001` 指向两条不同的记录** ⇒ **任何按 id 回溯的读取端会读到错的那条**。

---

## 2. ★★★ 根因：正则假设了单一序列化格式，而两种写法在同一文件里共存

旧实现（`nextSignalId`）：

```js
const matched = /"id":"e-(\d+)"/.exec(line)     // ★ 要求 "id" 与 "e-…" 之间【没有空格】
```

```
带空格的那 10 行  ⇒ 正则【匹配不到】 ⇒ 对 max 完全不可见
⇒ max 从 0 起算   ⇒ 分配 e-0001     ⇒ 覆盖已存在的 e-0001
```

★ **实测**：`maxSignalNumberIn(真实文件)` 旧实现给 **0**，正确值应是 **10**。

---

## 3. ★★★ 而真正的教训不是"正则少写了 `\s*`"

★ 补一个 `\s*` 只修**这一次**。**根因是"靠解析文本推断状态"这件事本身** ——
它假设了**写者与读者对序列化的约定一致**，而那个假设**没有任何地方强加**：
任何人用 `JSON.stringify(x, null, 2)`（带缩进）都能让同一个正则**再次失明**。

### 3.1 修法 ①：读 id 与**序列化格式解耦**

`maxSignalNumberIn(text)` 现在**逐行 `JSON.parse`**，从**解析出来的对象**上读 `id`：

```
正路：JSON.parse(line).id          ⇒ 文本形状再怎么变（空格 / 缩进 / 键序 / 多了别的键）都给同一个对象
兜底：/"id"\s*:\s*"e-(\d+)"/       ⇒ 只对【解析不了的行】生效，容忍空白
```

★ **兜底为什么必须留着**：历史数据里若有半行，它的编号**已经被占用过** ——
漏掉它会让同一个 id 被分配第二次，而"撞车"正是本函数要消灭的东西。

★ **而"解析失败的行只跳过它自己"**（不整文件放弃）：
坏一行不该让**所有**既有 id 都变得不可见 —— 那正是旧实现会**静默放大**的错。

### 3.2 修法 ②：**并发两次 append，id 凭什么不撞**（必答题）

★ **先用实测把问题范围缩到一处**：

```
20 次并发 appendFile 到同一路径 ⇒ 20/20 行都在，20/20 都能 JSON.parse
⇒ ★★ 这条流的 append **本身已经是原子的**（O_APPEND）
⇒ ★★ 竞态【只在分配那一段】，不在写入那一段
```

（★ 这与 `frictions/` 那边**不同**：那边一次写一个**文件**，写入不原子 ⇒ t89 要修两处。
本任务只需修一处，而"只需修一处"是**测出来的**，不是推断的。）

⇒ **修法**：把「读 max → 算 id → 追加」整段**串行化**，新增 `appendSignalClaimingId`：

```ts
export async function appendSignalClaimingId(stateRoot, build) {
  return withEvolutionLock(stateRoot, async () => {
    const id = await nextSignalId(stateRoot)   // ★ 在临界区内重读 —— 全部要点
    return await appendSignal(stateRoot, build(id))
  })
}
```

★ 与 t89 的 `claimFrictionId` **同一条纪律**（"分配与占用是一步"），但**落点不同**：

| | 占用是什么 | 排他怎么做 |
|---|---|---|
| `frictions/` | 创建一个**文件** | `open(path, 'wx')`（`O_EXCL` 天然排他） |
| `evolution/` | 追加一**行** | ★ `O_APPEND` 原子但**不排他** ⇒ 排他落在**那个文件的临界区**上 |

### 3.3 ★★ 边界：`withEvolutionLock` 是**进程内**的（不许读成"任何地方"）

- 它是模块级 `Map` 上的 promise 链（与 `state.ts` 的 `withTeamLock` **同形状**，注释注明同源）
  ⇒ ★ **不跨进程**。两个**进程**同时追加仍可能撞 id。
- ★ 而那个边界**现在有一个显式的读数**：`duplicateSignalIds()`（§4）——
  它让"撞了"**读得出来**，而不是表现为"某条记录不见了"。
- ★ **为什么不干脆做跨进程的锁文件**：持锁进程崩溃留下的锁文件会让**整条采集流永远卡住**，
  而采集是**旁路**（`void … .then(warn)`）⇒ **卡住比偶尔撞一次更坏**
  （t89 那条注释为 `ATTEMPTS = 64` 记过**同一取舍**）。
  ⇒ 本任务选「**进程内串行 + 撞击可读**」，而不是「跨进程排他 + 可能永久卡死」。

## 4. ★★ 那五组既有的撞车怎么处置：**不重写，给可区分读数**

审计数据**不许改** ⇒ `duplicateSignalIds(text)` 报出「**哪个 id 撞了、撞在第几行**」：

```
$ node -e "…duplicateSignalIds(真实文件)…"
[{"id":"e-0001","lines":[1,11]},
 {"id":"e-0002","lines":[2,12]},
 {"id":"e-0003","lines":[3,13]},
 {"id":"e-0004","lines":[4,14]},
 {"id":"e-0005","lines":[5,15]}]
```

⇒ ★★ **读取端现在能先问一句再决定信谁**，而不是"读到错的那条还不知道"。
★ 而**静默重编号**会让「**它曾经撞过**」与「**它从来没撞过**」**同形** ——
那正是本仓记账最久的形态，所以**不重编号**。

## 5. ★★ 三条反向半边（均实测）

### A：混有两种写法 ⇒ 分配出的 id 不许撞任何一个

| 读数 | 值 |
|---|---|
| `maxSignalNumberIn(真实文件)` | **10**（旧实现 **0**） |
| 因此 `nextSignalId` 给出 | **`e-0011`**（旧实现给 `e-0001` = 撞车） |
| 合成样本（4 种空白写法混排） | **12**（正确认出 `"id" : "e-0012"`） |
| ★ 真建文件的臂 2（带空格那行**编号更大**） | 分配出 **`e-0008`**，不撞 `e-0007` |

### B：并发两次 ⇒ 两个不同的 id

```
2 次并发  ⇒ e-0001 e-0002          distinct ✅
12 次并发 ⇒ e-0003 … e-0014        unique 12/12 ✅
盘上 14 行（14 次调用）· 14/14 都能 parse · 编号连续 1..14
```

★★ **而"不撞"必须不是恒真 —— 我做了对照组**：把三段**拆开**跑（= 旧路径）：

```
OLD way ids: e-0001 ×12        unique 1/12     ★ COLLISION REPRODUCED
```

⇒ ★ **同一条测试在拆开跑时红、在串行化后绿** —— 这就是反向半边 B 该有的分辨力。

### C：既有 15 行不受损
