# 路径解析只在某一种深度下成立（t85）

> **一句话**：一个写死层数的路径常量，**只在一种深度下**解析到它该去的地方。
> 而 worktree 与主树的差别，就是那个深度。
>
> 判据实施：`scripts/gate-path-depth.test.mjs`。
> ★ 而它【报告而不拦】—— 理由见 §5。

---

## 1. 为什么它值得单独一条判据：昨夜它出现了【六次】

| # | 实例 | 形状 |
|---|---|---|
| ① | t39：搬运时 t41 的接线被覆盖 | 底本取自**另一个 worktree** 的 HEAD |
| ② | t54：并入时把 t59 的接线覆盖回去 | ★ 与 ① 同一条 |
| ③ | t76：把队友的两个 lib 文件一起提交 | ★ 它自己纠正了 |
| ④ | t83：同上 | ★ 它主动说"我 t76 那次搞错了" |
| ⑤ | t84：夹具的 `repoRoot` 算成 `..×4` | ★ 见下 |
| ⑥ | t80：46 个 worktree 里 current 1 · behind 45 | 最深 61 个提交 |

⇒ ★ 六条的共同形状：**「这棵树」与「那棵树」之间的差异，反复地骗到了人。**

★ 而它是**所有其他判定的前提**：一个不知道自己**在哪棵树里**的检查，
  它读到的任何东西都可能是**另一棵树**的。

## 2. ★★★ 那个真实实例（t84）

```js
const here = dirname(fileURLToPath(import.meta.url))
const root = join(here, '..', '..', '..', '..')     // ← 写死 4 层
const wtRoot = join(root, '.agent-teams', 'worktrees')
```

| 住在哪棵树 | `here` | `..×4` 解析到 |
|---|---|---|
| worktree | `<root>/.agent-teams/worktrees/task-x/scripts` | `<root>` ✓ **恰好对** |
| 主树 | `<root>/scripts` | `<root>/../../..` ✗ 指到仓库**外面** |

★ 而它旁边就写着那次学费（原文：**「层数必须按"它该回到哪里"算，
  不是按"看起来像几层"」**）—— 而它**仍然是一个写死的层数**。

★ 而那正是这条判据要说的那句话：**「这个常量只在某一种深度下成立。」**

### 判据实测（臂 3 在临时沙箱里造两棵树）

```
向上查找（浅树 depth=1）⇒ <sandbox>          ← 找到根 ✓
向上查找（深树 depth=4）⇒ <sandbox>          ← 找到同一个根 ✓
写死 ..×4（浅树）      ⇒ /var/folders/1y    ← ✗ 指到别处
写死 ..×4（深树）      ⇒ <sandbox>          ← ✓ 恰好对
★ 而这就是那个根因：同一个常量，浅树指向别处、深树恰好对
```

## 3. 三态

| 态 | 形状 | 判据 |
|---|---|---|
| `depth-independent` | **向上查找**（`for` + `existsSync(j(dir,'package.json'))`） | ★ 层数是**被发现的**量 ⇒ 任何深度都对 |
| `depth-bound` | 写死的 `..×N` 链 | ★ 层数是**决定的**量 ⇒ 只在 N === depth 时对 |
| `unmeasurable` | 基点不是"这个文件自己所在处" | 静态看不出深度依赖 |

★ 第三态不许并进前两者：把看不出来的判成坏的，就是"把不可判并进可判"。

---

## 4. ★★ 判别问句（这一条动作才是本判据的价值）

> **「这个层数是一个【决定的】量，还是一个【发现的】量？」**

决定的（`..×4`）⇒ 它编码了一个**关于布局的事实**，而那个事实**只对一种布局为真**。
发现的（向上找 `package.json`）⇒ 它**不假设**布局，它**问**布局。

★ 而这与 t39/t54 那两次是**同一条**判别动作 —— 那两次的原文也是
  「层数要按『它该返回什么』算，不是按『在作者那棵树里深几层』算」。

---

## 5. ★ 为什么它【报告而不拦】

★ 因为**有些写死层数是合理的**：一个脚本住在 `<root>/scripts/` 下，
  它的 `..` 就是**那个脚本自己的约定**，而它不打算在 worktree 里跑。

⇒ 所以本判据的产出是【读数 + 它在哪个深度成立】，**不是 blocked**。
   ★ 臂 4 把它写成**可执行性质**：全仓扫完后**无论存量多少，本判据不 fail**；
     它只断言"装置在工作"（扫到 >50 个脚本、三态之和 >0）。

★ 把存量断言成 0 会在下一次有人合法地加一个 `../` 时按设计变红 ——
  而那时读的人会去改断言（棘轮），而不是去判断那一处该不该改成向上查找。

### 全仓存量（如实报出，119 个脚本）

```
depth-independent  3
★ depth-bound      3
unmeasurable       0
三态之和            6

★ 那 3 条 depth-bound（逐条）：
  · scripts/sync-skill.mjs:6            （写死 1 层）
  · scripts/update-skills.mjs:9         （写死 1 层）
  · scripts/worktree-baseline-freshness.test.mjs:364  （写死 4 层）★ t84 那一条
```

★ 前两条住在 `<root>/scripts/` 下、写死 1 层 —— **在主树里是对的**，
  而它们**不打算在 worktree 里跑**（`sync-skill` / `update-skills` 是维护脚本）。
  ⇒ 它们是"待判断清单"的成员，而不是"错误清单"。
★ 第三条是 t84 那次的原形 —— 而它已经落在**跳过分支**上（看不到 worktrees 就跳过），
  所以它的失效表现为"静默跳过"而不是"指错地方"。★ 而那**更隐蔽**。

## 6. ★★ 这条判据自己踩过三次同一个坑（值得记在文档里，不只是注释）

我写这个装置时**错了三次**，而三次都是同一个主题：

| 错法 | 现象 | 形态 |
|---|---|---|
| ① 把"深度 N"实现成**向上走** N-1 步 | 6 个深度都落在真实树里 ⇒ 报"6 个都成立" | 量算错了 |
| ② 从根往下搭时**每步加两级** | `..×4` 回不到根 ⇒ 报"一个都不成立" | 树造错了 |
| ③ 改用 worktree 形状之后，深度 2/3 与 3/4 **同形** | `..×4` 报出两个深度 | 模仿形状引入了额外因素 |

⇒ ★ 三次的共同点：**我搭的那棵树与真实的树在【深度】上对不上** ——
  而那**正是本判据的整个主题**。

⇒ ★ 最终的修法：**不要模仿任何真实形状**，就老实造一棵"恰好 N 级"的树。
  判据要问的是"深度"这个**量**，而不是"worktree 长什么样" ——
  **模仿形状会给这个量引入别的影响因素。**

★ 一条测"深度依赖"的判据，自己先三次栽在深度上。这件事本身值得留在这里。
