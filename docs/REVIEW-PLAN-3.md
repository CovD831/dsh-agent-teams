## 3. F2（high）★ P0a 的验收「测试集合相等」不能捕获它要防的那件事

### 3.1 计划的原话与它自己的纪律

### 3.2 实测：一个被放宽的断言照样给出"集合相等"

```js
// 严格的：断言 x > 0        被放宽的：断言 true
const run = (f) => ({ passed: f() ? 1 : 0, failed: f() ? 0 : 1 })
run(() => 5 > 0)   // => { passed: 1, failed: 0 }
run(() => true)    // => { passed: 1, failed: 0 }     ← ★ 两个读数逐字相同
```
⇒ **"同一批断言、同样通过"在"断言被放宽"这件事上恒真。**
★ 用本仓自己的话：这是**一条看不见差异的验收** —— 与 `docs/HANDOVER.md:72` 记的
「t94 的『恰好落一栏』看不见哪一栏」**同形**（那条的可判性缺陷，`docs/PURE-MOVE.md` §4 已记）。

### 3.3 可判的替代验收（★ 最小改动）

把"集合相等"换成**三条可判读数**（都已在盘上，不需要新机制）：

1. **断言条数不减少**：`grep -c "assert\." <file>` 改前 ≥ 改后。
   ★ 但这条**自己也近乎恒真**（`assert.` 计数不区分强弱）⇒ 只当**下限**用，不够。
2. **每条断言仍可被证伪**（真正的判据）：对**每一处被改的断言**，做一次**定向突变** ——
   把被断言的那个语义事实弄坏（例如把 `role="img"` 删掉），断言**必须变红**。
   ⇒ 这是本仓现成的形状（每条判据配一条"弄坏它必须红"的臂，见 `PROPOSAL-DELIVERABLE-RETURN.md:86`）。
3. **计数型断言仍计数**（`:1660` 已经踩过这个坑，可直接引用）：

### 7.1 为什么 D4 可以删（可核的推理）

D1 落地后，**"哪条判据从不生效"变成一个可读事实**。而一旦可读，**"优化"这个动作就只剩两种**：
1. **人看一眼读数，删掉/接上某条判据** —— 这是一次**人的决定**（且 D3 已经在做这件事的入口）；
2. **让插件在运行时自动删/自动接判据** —— 这是一个**机制**。

★ 而 (2) **与本仓已定的纪律直接冲突**：
- `docs/GATE-EFFICACY.md` §8 A4 的定论是「**证据既不足以支持删除，也不足以支持保留**」（有开火证据 9 条、无证据 8 条，其中 3 条是**未接线**而非无效）；
- 本仓明文纪律「**判据不替人做决定**」（`PROPOSAL-DELIVERABLE-RETURN.md:108` 逐字：*「不自动归并……归并动作是人的决定（本仓纪律：判据不替人做决定）」*）。
⇒ 一个"按运行时数据自动优化判据"的机制，**正是替人做决定** —— 而它要优化的对象（判据的存废）**恰恰是本仓刚刚裁定"证据不足以支持"的那一格**。

★ **所以 D4 的合法最小形式是**：把 D1 的读数**显示给人**（一个只读列表：哪些判据 N 天没开火、各多少次）。
⇒ ★★ **而这一格已经存在**：`docs/GATE-EFFICACY.md` §6 就是那张表（我已复跑，逐条命中）。
⇒ **D4 的增量 = 0**（至少在本轮 MVP 的定义下）。

★ **判据（计划要求的"用户能看见什么变化"）**：
- D1 + D2 做完，用户能看见：**"哪条判据从不生效"第一次有读数**（且它回答了 `GATE-EFFICACY` 里唯一那条"测不了"）。
- D4 做完，用户能看见：**与 D1+D2 相同的读数**，外加一个**会自动改判据的机制** —— 而那个机制**当前没有可安全作用的对象**。
