# B0 · 面板视图分层模型

> **本文件回答用户原话**：
> 「你这些是**任务粒度**的 UI，但是我们的**任务 DAG 是很多很庞大的**，所以任务粒度的确实要显示，
> **但是不能堆积**。当前的**成员粒度也是有优势的，可能更宏观一些**。
> 所以**整个 UI 面板到底需要些什么，看来我们还没讨论清楚**。」
>
> ⇒ 这是**架构问题**（视图层次未定义），不是视觉问题。本文件**只定义层次**，不画视觉。
> **纪律**：只写 `docs/UI-VIEW-MODEL.md`；不改 `src/`；需用户拍板的**不自答**（§7）。

---

## 0. 一句话

**三层各有各的"上界"，而 L3 的上界不是"少画几条"，是"一次只存在一张"** ——
它由**选择**（selection）驱动，不由**渲染**（enumeration）驱动。

---

## 1. ★ 先修正一个数：任务总数是**活的**，不是 51

队长给的依据是「本队任务总数：51（completed 34 / cancelled 8 / failed 9）」。
我实测**现在是 52**：

```sh
python3 -c "import json;d=json.load(open('.agent-teams/agent-teams-refactor/team.json'));
ts=d['tasks'];import collections;print(len(ts), collections.Counter(t['status'] for t in ts))"
# ⇒ 52 Counter({'completed': 34, 'failed': 9, 'cancelled': 8, 'claimed': 1})
```

**差的 1 条就是 t58 本身**（我 claim 它之后才被计入）。

★ **这个观察本身就是本文件的第一条论据**：
**"任务总数"是一个每接一个任务就会变大的数** ⇒ 任何"按任务数铺开"的视图
**上界都不存在**。⇒ 这就是为什么 §3 的 L3 必须**由选择驱动**，而不是**按数量裁剪**。
（只写"51"会让下一个人以为那是个可以拿来算布局的常数。)

## 2. 三层定义（问题 → 粒度 → 上界)

| 层 | 回答的问题 | 粒度 | ★ 规模上界 | 上界**由什么保证** |
|---|---|---|---|---|
| **L1 队级** | 「**现在顺利吗**」 | 整个队 | **1 张** | 一个队只有一个 |
| **L2 成员级** | 「**谁卡住了**」 | 每个成员一行 | **成员数**（4–8） | 由**成员数**封顶（队伍规模有上限） |
| **L3 任务级** | 「**这一件走到哪一步**」 | 单条任务的判据管线 | ★ **1 张** | ★ **由"选中"保证，不由"数量"保证** |

★ **三层的上界来源不同** —— 这是本模型的关键：
- L1：**结构**（一个队）；
- L2：**规模**（成员数有上限）；
- L3：★★ **交互**（用户选了哪一条）。

⇒ 前两层的上界是**自然常数**，第三层的上界是**一个设计决定**。
**用户担心的"堆积"只可能发生在 L3**，因为只有它"输入规模无上界、输出规模有上界"。

---

## 3. ★★ L3 的触发方式：「N 个任务时不堆积」的机制

**用户的原话是"不能堆积"。** 而"堆积"的成因不是"画得太多"，是**驱动方向错了**：

| | ❌ 渲染驱动（会堆积） | ✅ 选择驱动（不堆积） |
|---|---|---|
| 输入 | 全部任务（N 个，且 N 在增长） | 当前**选中**的那**一个** `taskId` |
| 输出规模 | O(N) 张管线图 | **恒为 1 张**（或 0 张） |
| N 变大时 | 越画越多 | **输出规模不变** |
| 修法 | 裁掉一些（"少画几条"）⇒ **上界仍随 N 漂移** | 换选择 ⇒ **上界是常数** |

### 3.1 机制（四条，每条都要能机械核对）

**① 唯一性：任一时刻至多一张 L3。**
由 `selectedTaskId: string | null` 驱动（该状态**已存在**：`ActivityPanel.tsx:165`）。
⇒ 断言可以是"DOM 里 `.pipelineRoot` 的数量 ≤ 1"，**与任务总数无关**。

**② 入口唯一：L3 只能从 L2/L1 的一个可点元素进入。**
现成先例：`DependencyGraph.tsx:65` 已经收 `onSelectTask?: (id: string | null) => void`，
而 `ActivityPanel.tsx:165` 的 `selectedTaskId` 就是它的落点。
⇒ **这一条不需要新造交互，只是把已有的选择接给一张新图。**

**③ 默认不画：`selectedTaskId === null` ⇒  L3 不存在（0 张，不是"空图"）。**
★ 与 `DependencyGraph` 的既有纪律同形 —— `DependencyGraph.tsx:74-77` 逐字记着用户原话
"the dependency graph can stay collapsed by default"，且 `ProgressSummary` 那边有
"不画空图"的先例（`arm 29`：空队/单任务/全孤立 ⇒ **不画**一张空图）。
⇒ **"没选"与"选了但没判据"必须不同形**（本仓三态纪律）。

**④ 选中失效时的处置必须显式：**
选中的任务**消失了**（被删/被改派/换队）⇒ `selectedTaskId` 指向的 id 不再存在。
现成处置在 `TeamSection`：`team.tasks.find(task => task.id === selectedTaskId)?.assignee`
（`ActivityPanel.tsx:166`）—— 找不到就是 `undefined`。
★ **必须写在设计里**：L3 此时应**回到 0 张**（不是画一张空管线）。

### 3.2 为什么"不靠少画几条"

「少画几条」有**两种**都会退化的形态，必须点名，否则会被当成等价方案：

| 形态 | 为什么仍会堆积 |
|---|---|
| 只画"最近 N 条" | N 是常数，但**用户要看的可能是第 N+1 条** ⇒ 要么看不到，要么 N 被调大 ⇒ **上界跟着漂** |
| 只画"异常的那些" | 异常数**随任务数增长**（实测本队 failed 9 + cancelled 8 = 17，已超过一个屏幕）⇒ **仍然是 O(N)** |

⇒ ★ **判据**：一个方案是否合格，就看 **"任务总数翻倍时，L3 的输出规模会不会变"**。
选择驱动的答案是**不会**；上面两种都是**会**。

## 6. ★ 项目特定 vs 通用底座（用户裁定 U 线为「乙：只分层」）

| 内容 | 归属 | 理由 |
|---|---|---|
| 三层的**结构**（L1 队 / L2 成员 / L3 任务） | ★ **通用底座** | 任何多智能体编排都有这三层 |
| "选中才画 L3"的**选择驱动机制** | ★ **通用底座** | 它是"不堆积"的**通用解**，与判据内容无关 |
| 六个插入点本身 | **项目特定** | `INSERTION_POINTS` 是本插件的判据模型 |
| 四符号 + 未检查 + 观察 | **项目特定** | 映射自本仓 `registry.ts` 的三态 |
| 成员的中文名/职责 | **项目特定** | 数据内容，不是结构 |
| `memberClock` 四态 | **通用底座**（语义） | "在跑/停滞/空闲/读不出"是通用读数 |

★ 按 U 线裁定「**只分层不抽取**」⇒ **本次不建包、不抽公共库**，
只在文档上把上表标清楚，让后续分层（U2）有依据。
