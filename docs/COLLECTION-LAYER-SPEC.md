> **用户的问题（逐字）**
> 「采集层其实一方面做的是**采集**,另一方面是**存储**,对吧?
>  也就是它**在哪里采集**,**以什么形式存储**,以及**存储在哪里**。」

★ 而我先量了一个数,它改变了这三问的**优先级**（见 §0）。

```
.agent-teams/frictions/  ⇒  384 条,12.9 MB（磁盘 14 M）
  平均每条 35 KB
```

## 1. ★ 在哪采（三个汇合点,不是 13 个模块）

### 原则（用户硬约束:模块不许互相侵入）

```
❌ 侵入:  在 src/gates/contract/task-atomicity.ts 里 import evolution
✅ 不侵入: 宿主在【已有的】汇合点调用一次 observe()
```

### 三个汇合点

| 汇合点 | 位置 | 覆盖什么 | 状态 |
|---|---|---|---|
| **A** `recordFriction()` | `entities.ts:3805` | ★ **所有判据拒绝** | ✅ **已在** |
| **B** 工具拒绝抛出点 | `tools.ts`（`transitionError` 一带）| ★ **闸门拒绝** | ★ 新增一行 |
| **C** 契约校验 | `quality-gates.ts:843` `validateCreateTask` | ★ **契约类** | ★ 新增一行 |

★ **而 `src/gates/**` 一个字不改。**

### ★★ 外加两个**没有汇合点**的采集需求（用户原话的三类）

```
① rejection  ⇒ ✅ 上面三个汇合点覆盖
② success    ⇒ ❌ 【没有汇合点】—— 现在无处可采
③ insight    ⇒ ❌ 【没有汇合点】—— 现在无处可采
```

**用户原话:**
> 「不管是**报错**,还是主会话发任务时**子代理觉得不合理**;
>  或者子代理做出了一些**比较好的处理办法**,主会话觉得在什么方面**处理得很好、很有价值**」

⇒ ★★ **② 与 ③ 是【人/AI 主动标记】的,不是自动触发的。**

**所以它们各自需要一个显式入口:**
```
② success  ⇒ ★ 一个工具调用（人有意的）+ 一个自动信号（任务 completed 且无 rejection）
③ insight  ⇒ ★ 一个工具调用（人有意的）
```

★ **而"自动信号"那条要小心** —— 见 §5 的失败模式:
**" успех 不报"会让循环只看到失败,于是它优化出来的东西会趋向"什么都不做"。**

## 2. ★★★ 什么形式（这是本规格的核心）

### 依据:GEPA 那句 + Raven 那条

**GEPA（hermes-self-evolution ★5512）逐字:**
> 「GEPA reads execution traces to understand **WHY** things fail
>  (**not just that** they failed)」

**Raven（★5470）§4 逐字:**
> 「Analyst 会把"**装上的机制本轮实际做了什么**"一并交给 Curator:
>  哪条审核放行了几次、打回了几次、理由是什么,哪个工具调用失败了。
>  Curator 据此**核对自己上一轮的修订是否起效**,而不是只看它的计划。」

⇒ ★★★ **所以记录必须带"机制活动"（which mechanism did what）** ——
**而本仓恰好有那个数据:判据的 `ran[]`（逐条裁决）+ `commandsRun`。**

### 建议的形状

```ts
export interface EvolutionSignal {
  readonly id: string                    // e-0001（单调,与 f- 同族）
  readonly at: number

  /** ★ 三类（用户原话） */
  readonly kind: 'rejection' | 'success' | 'insight'

  /** ★ 确定性来源 —— 谁拒的 / 哪条判据 / 哪个工具 */
  readonly source: {
    readonly where: string               // 'create_task' | 'update_task' | 'validateCreateTask'
    readonly gateId?: string             // 'contract.task-atomicity'（可空）
    readonly tool?: string               // 工具名（可空）
  }

  /** ★ 原文，不改写 */
  readonly message: string

  /** ★★★ 机制活动：装上的机制本轮实际做了什么（Raven §4）
   *   —— 数据来自判据的 ran[]，不是重算 */
  readonly mechanisms?: readonly {
    readonly gateId: string
    readonly verdict: string             // ok | blocked | skipped | unmeasured
    readonly count?: number
  }[]

  /** ★ 场景：只存【标识】，不存快照（那是 38% 噪声的来源） */
  readonly scene?: {
    readonly team?: string
    readonly task?: string
    readonly attempt?: number
  }

  /** ★★ 引用而非内嵌：状态快照按【内容哈希】单独存（见 §3） */
  readonly stateRef?: string             // 'sha1:abc123...'

  /** ★ 分类（复用既有 9 类，不发明第二套） */
  readonly index?: { readonly component?: string; readonly kind?: readonly string[] }

  /** ★★ 分流（用户要的那一格） */
  readonly routing?: {
    readonly decision: 'soft' | 'hard' | 'unmeasured'
    readonly why: string
    readonly target?: string
    readonly effect?: string
  }
}
```

### ★★★ 三条硬约束（都来自实测的教训）

| # | 约束 | 为什么 |
|---|---|---|
| **1** | ★ **`scene` 只存标识,不存快照** | 现在 `scene.ctx` 占 38%（4.96 MB / 384 条）|
| **2** | ★★ **状态快照按内容哈希【单独】存,记录只引用** | 331/337 份不同 ⇒ **引用能省 4.96 MB 里的绝大部分** |
| **3** | ★ **`mechanisms` 不重算,直接抄判据的 `ran[]`** | 重算会引入第二个口径 ⇒ 两处漂移（本仓记账过）|

★ **而 (3) 特别重要** —— 因为在观察点重算判据**会与当时的裁决不同**,
于是"记录说 X,当时实际是 Y" ⇒ **两个口径,一个事实。**

## 3. ★ 存哪里

### 现状与问题

```
.agent-teams/frictions/*.json   ⇒ 一条一文件，12.9 MB
```

★ **一条一文件的问题**（不是错,但有代价）:
```
· 384 个 inode
· 每次都是整文件读写（35 KB）
· 而 38% 是同一个 team 的不同快照
```

### 建议:三层,按"变化频率"分

```
① 信号流（append-only）
   .agent-teams/evolution/signals.jsonl
   ★ 一行一条,只含 §2 的形状（无快照）
   ★★ 平均 3 KB ⇒ 384 条只需 ~1.1 MB（而现在 12.9 MB）

② 状态快照（content-addressed，去重）
   .agent-teams/evolution/states/<sha1>.json
   ★ 记录里只放 stateRef
   ★★ 同一 team 的多次记录 ⇒ 同一份快照只存一次

③ 索引（派生，可重建）
   .agent-teams/evolution/index.json
   ★ kind 分布 / routing 分布 / 各 component 的计数
   ★★ ★ 它是【派生】的 ⇒ 删了能重建 ⇒ 坏不了
```

### ★★ 为什么 signals 用 **jsonl** 而不是一条一文件

| | 一条一文件（现状）| ★ jsonl |
|---|---|---|
| append | 建新文件 | ★ **一行** |
| 全量读 | 384 次 open | ★ **一次** |
| 并发写 | 需要锁 | ★ **append 是原子的**（本仓 mailbox 已这么做）|
| 部分损坏 | 坏一条 | ⚠️ 坏一行 —— ★ **但有 id,可跳过** |

★ **而本仓【已有先例】**:`inbox/*.jsonl`（mailbox）就是这么做的。

⇒ ★★ **所以不是新发明 —— 是复用本仓既有的存储约定。**

### ★★★ 而"存哪里"有一个必须回答的:**与既有 frictions 的关系**

```
选项 ① 迁移:把 384 条转换成新格式（含拆出快照）
选项 ② 并存:新的走 evolution/，旧的 frictions/ 冻结不动
选项 ③ 复用:直接扩展现有的 frictions/ 形状
```

★ **我建议 ②（并存,旧的冻结）**,理由:
```
· 那 384 条是【历史】，它们的形状有它自己的读者（frictions.html / verify:frictions）
· ★ 迁移会让"历史"与"新格式"混在一起，而两者口径不同
· ★★ 而"旧的冻结"是可验证的:它的 count 不再增长
```

★ **而这也符合本仓的纪律:先并存,确认新的能用,再决定迁移。**

## 5. ★★ 采集层必须自带的三个防护（来自失败模式研究）

| # | 防护 | 依据 |
|---|---|---|
| **1** | ★★ **不只在失败时采,也要在成功时采** | 否则循环只看得到失败 ⇒ **优化出"什么都不做"**（classic specification gaming）|
| **2** | ★ **采"机制活动",不只采"结果"** | Raven §4:让 Curator 能"核对自己上一轮的修订是否起效" |
| **3** | ★★ **采集有【冷却】+ 去重** | MemOS 的 `cooldownMs`;同一 (kind, component, message) 在冷却期内只记一次 |

★ **而 (1) 我认为最容易被忽略,也最危险** ——
**因为"成功"现在【完全没有汇合点】,它需要显式设计。**

## 8. ★★★ 修正:用户是对的,而我的去重口径错了

> **用户原话**
> 「关于你说的**去重只省 2%**,是因为里面的内容都各不相同。我觉得我们在做这种采集时,
>  可以做一个类似于**模型底层训练中 KV cache 缓存广播**的优化:
>  尽量**把相同的上下文,或者其他相同的部分统一保存起来,然后进行广播和复用**。」

### ★ 我错在哪

```
我测的是【整块 scene.ctx】的哈希
  ⇒ 331/337 份不同 ⇒ 省 2%
★ 而共享发生在【子结构】层，不在整块
```

### ★★★ 三层口径的实测对比（同一批 372 条）

| 粒度 | 引用总计 | 去重后 | **省** | 唯一块 |
|---|---|---|---|---|
| **整块**（我原来的测法）| 4.92 MB | 4.88 MB | ★ **1%** | 332 |
| ★★ **子结构**（成员 / 任务）| 2.32 MB | **0.69 MB** | ★★★ **70%** | 199 |
| 字段级（每个字段各寻址）| 2.17 MB | 0.61 MB | 72% | **1956** |

⇒ ★★★ **结论:用户的类比是对的,而"子结构"就是那个正确的粒度。**
```
· 整块 ⇒ 几乎没有共享（1%）
· ★ 子结构 ⇒ 70%
· 字段级 ⇒ 只多 2 个百分点，而唯一块从 199 涨到 1956（复杂度高得多）
⇒ ★★ 所以【成员】与【任务】是天然的共享单元
```

### ★ 而共享确实存在（实测）

```
复用最多的子块（按出现次数）:
   7 次 ·   183 字节 · 一个 member
   7 次 ·  5865 字节 · ★ 任务 t5
   7 次 ·  7317 字节 · ★ 任务 t6
   7 次 ·  6514 字节 · ★ 任务 t7

★ 出现在【多条记录】里的子块引用: 522 / 607  ⇒ ★ 86% 的引用是可复用的
```

⇒ ★★ **即:同一个任务（t5）在 7 条不同的卡点里各存了一份。**
**而那正是 KV cache 广播要消除的东西。**

### ★ 而这对"足够复现的上下文"没有损害

> **用户原话**
> 「可能是因为我当时说,记录时**需要带上足够的上下文**,也就是**足够复现的上下文**。
>  我觉得带上足够复现的上下文,会更利于后续做测试 ——
>  无论是**验证改动是否能有效解决当时的问题**,还是做其他测试。」

★★ **所以"减少 10 倍"不能靠【删上下文】** ——
**它靠【一次存、多处引用】。**
```
✅ 内容一字不少（可复现性不变）
★ 只是同样的内容不存第二遍
```

⇒ ★★★ **那与本仓的"软归档不硬删"是同一个纪律:
减少体积靠【引用】,不靠【丢弃】。**

## 9. ★★★ ④ 成功 / 洞察信号的采集（待讨论的那一条）

> **用户原话**
> 「关于你说的 **success 和 insight**,确实需要做**某种判断**,
>  也就是**怎么样才能采集到一些比较好、有价值的模式**。
>  我们不光要采集错误,**也希望能采集到一些比较好的处理方式**,
>  这些都是要做**沉淀和复用**的。」

### 难点在哪（三条,而它们性质不同）

| # | 难点 |
|---|---|
| **1** | ★ **"好"没有确定性判据** —— 而错误有（闸门拒绝就是拒绝）|
| **2** | ★★ **"有价值"是【事后才知道】的** —— 本会话里"t75 这条判据有价值"是几轮后才显出来的 |
| **3** | ★★★ **一旦"成功"进入循环,它就会成为被优化的目标** ⇒ ★ **可以刷** |

### ★★ 所以我建议:**三类信号用三种【不同强度】的采集**

```
rejection（错误）  ⇒ ★ 自动采（确定性，已有的三个汇合点）
success（好做法）  ⇒ ★★ 自动采【候选】+ 人/AI 显式【确认】才升级为"模式"
insight（洞察）    ⇒ ★★★ 只由人/AI 显式提交（不自动）
```

★ **理由:**
```
· rejection 是【事实】—— 闸门拒绝了就是拒绝了，无可争议
· success   是【判断】—— 需要一个确认步骤，否则"它没报错"就会变成"它做对了"
★ insight   是【提炼】—— 那是人的工作，自动提炼会造出看似深刻的噪声
```

### ★★★ 而"自动采候选"要采什么（这才是有依据的部分）

**依据:那份清单里的 specification gaming 与 METR 那条。**

★★ **"成功的候选"不该是"没报错"** —— 那会优化出"什么都不做"。
**而该是【可核的读数】:**

```ts
/** ★ 一个"好做法"的候选：必须带【可复跑的读数】，不是"我觉得不错" */
export interface SuccessCandidate {
  readonly what: string            // 做了什么（一句话）
  readonly readings: readonly {    // ★★★ 可复跑的证据
    readonly command: string
    readonly exitCode?: number
    readonly evidence: string
  }[]
  /** ★ 它【避免了】什么 —— 与 rejection 关联 */
  readonly avoided?: string        // 关联的 rejection id
  /** ★ 复用次数：它被后来的会话用了多少次（这是它"有价值"的读数）*/
  readonly reusedBy?: readonly string[]
}
```

⇒ ★★★ **而 `reusedBy` 是关键 —— 它是"有价值"的**唯一可测代理**:
```
一条"好做法"如果【从没被复用】⇒ 它的价值未证实
而它被复用了 N 次 ⇒ ★ 那是可数的
```
★ **而那正好接上 `confidence.ts` 的 `tallyRecall` / `tallyAdopt` 双计数** ——
**"被找到"与"被采纳"是两个不同的数,而它已经实现好了。**

### ★ 三个防护（照 §5,但针对 success）

| # | 防护 |
|---|---|
| **1** | ★ **"没报错"不等于"做对了"** —— 候选必须带可复跑读数 |
| **2** | ★★ **"有价值"用【复用次数】度量，不用自我评价** |
| **3** | ★★★ **"成功模式"不许直接进循环** —— 先作为【可选建议】,被复用 N 次后才晋升 |

★ **而 (3) 是 §4 那条"评估器待在循环外"在 success 上的形态:
如果"成功"能立刻改 prompt,那循环就会**生产成功**而不是**发现成功**。**

## 11. ★★★ 树形结构:用户补的那一层,而它成立

> **用户原话**
> 「其实它的 KV cache 复用有一点像**树的结构**。比如我们目前是一个团队,
>  下面有几个**成员**,每个成员又有好几个**任务**。这其实就像一个树的结构一样:
>  比如某一个报错,它属于哪个任务;而这个任务,可能又属于哪一个成员。
>  所以,它应该类似于**树一样的结构**,这样可以**层层复用**一些东西,
>  很多东西都只需要存一份。或许可以通过某种**拼装**的方式,就可以得到一个完整的上下文。」

### ★ 实测:确实是树（层越往上,唯一块越少）

| 层 | 唯一块数 | 体积 |
|---|---|---|
| **team 级字段** | ★ **12** | 9.0 KB |
| **member** | ★ **36** | 25.1 KB |
| **task** | **163** | 681.9 KB |

⇒ ★★★ **层次分明:team 级只有 12 个唯一值（高度共享）,而 task 级 163 个。**

### ★★★ 而"拼装"实测可行

```
唯一块存储: 211 块 ·   716.0 KB
引用表    : 372 条 ·    30.7 KB     ← ★ 引用极便宜
总计      :            746.7 KB
原始 ctx  :           4920 KB
⇒ ★★ 压缩比 7×
```

⇒ ★★ **所以形状是:**
```
signals.jsonl          一行一条，只含【引用】+ 缺陷本身
states/team/<hash>.json     team 级（12 个）
states/member/<hash>.json   member 级（36 个）
states/task/<hash>.json     task 级（163 个）
★ 拼装 = 按 id 取引用 → 组装出一份完整 ctx
```

### ★★★ 而用户对"要不要存这么多"的态度我记下

> 「当然,我们或许**不需要那么多的环境上下文**,**具体看后面用起来怎么样**吧。
>  如果后面用完之后,我们发现**只需要用到哪些部分**,那就可以做一个优化,
>  在缓存的时候,就**不需要把公共缓存做那么多**。」

⇒ ★★ **即:先按树存全,等用一阵子,再按【实际读到的部分】裁剪。**
★ **而那正好是"用读数决定"而不是"现在猜"** —— 与本仓纪律一致。

★ 而我会把它落成一条:**每次拼装时记一行"读了哪几层"** ⇒
**那是裁剪的依据（一个可复跑的读数,而不是印象）。**

## 12. ★★★ 用户新提的第三点:**还需要一套"该不该采"的评估**

> **用户原话**
> 「其实关于这种自进化,**除了需要一个评估器去对修改后的版本做跑分以外**,
>  或许**还需要一个评估,去帮采集层评估是否需要采集**。
>  也就是说,需要维护一套**评估体系**。」

### ★★★ 这是本设计里我**之前漏掉的一层**

**我原来的设计只有两条链:**
```
采集 → 处理 → 生效        （★ 缺了"要不要采"这一关）
```

**而用户指的是三条,而第二条是关键:**
```
① ★ **该不该采**（采集层的评估）    ← ★★★ 用户新提的
② 改完跑分（生效后的评估）           ← 我原设计的 verify
③ ? 还有没有第三条
```

### ★ 为什么"该不该采"是独立的一关

**三条理由,都有本仓的证据:**

| # | 理由 |
|---|---|
| **1** | ★ **不是所有报错都值得采** —— 本会话里"我 inScope 写错"重复了 3 次,**那是一个模式;而某个一次性 typo 是噪声** |
| **2** | ★★ **采了就有成本** —— 12.9 MB / 384 条已经证明:采错的代价是**后面所有的读都要绕过它** |
| **3** | ★★★ **不设这一关,"采"就会成为循环的优化目标** —— 与 §5 的"成功可以刷"同族 |

### ★★ 而我建议它与【判据体系同形】,而不是新造一套

```
采集层的评估  ⇒ ★ 其实就是【判据】,只是插在"采集"这个位置上
★ 而本仓的判据体系已经有:
   · 17 条判据 · 6 个插入点 · 三态（ok/blocked/unmeasured）· 观察模式
   · 注册式（改一行即加一条，写错启动即炸）
```

⇒ ★★★ **所以"该不该采"应该是【一组判据】,插在"采集"位置上:**
```
· 去重：同一个 (kind, component, message) 在窗口内出现过 ⇒ ★ 不采（或只加计数）
· 冷却：同一来源在 N 分钟内 ⇒ ★ 不采（MemOS 的 cooldownMs）
· 可分性：这条信号能否【落到一个 component】？落不到 ⇒ ★ unmeasured，不硬塞
· 免疫：这条来自【已知的噪声源】（例如 worktree 路径差异）⇒ ★ 不采
```

★★ **而那需要给判据体系加【第七个插入点】`collection`** ——
**而本仓恰好刚把 admission 接完（六位置全有判据）。**

★ 而**那个新位置现在是空的** —— 而 `index.ts` 的注释逐字说明过:
> 「本任务只加位置,一条判据都不加,所以这个位置现在是空的……
>  而"它现在为空"这句话**不是不变量**」

⇒ ★★★ **所以加 `collection` 位置 + 第一批判据,是本设计该做的事 —— 而它已经有先例和纪律。**

### ★★ 而第二个评估（跑分）我原来叫 `verify`,而它其实也是判据

```
verify  ⇒ "改完之后，那件事好了没有？"
★ 而它测的是【该 kind 的卡点是否下降】—— 那也是一个读数
★ 而 confidence.ts 的 readFlywheel 已经在算这个（promote/observe/archive/unmeasured）
```

---

## 13. ★★★ 于是评估体系有三处,而它们该【分开】

| # | 评估 | 问什么 | 落在哪 |
|---|---|---|---|
| **①** | ★ **该不该采** | 这条信号值得进库吗? | ★ **新插入点 `collection`** |
| **②** | **该怎么分流** | 走软还是硬? | `route`（软硬判据）|
| **③** | **改完好了没有** | 该 kind 的卡点降了吗? | ★ **`verify` + `confidence.ts`** |

⇒ ★★★ **三者是【三个问题】,合一个会让"没采"与"采了但没用"同形** ——
**那正是本仓记账最久的形态。**
