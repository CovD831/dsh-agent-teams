# 裁定：前端只做**投影**，而投影分两级（2026-10-17）

> **用户收窄（逐字要点）**
> 「如果像我原本说的那样做一个统一的入口,会面临以下问题:
>  **1. 上下文过大**:它可以去更改其他的工作区,那它的上下文就会很大。
>  **2. 缓存无法共享**:很多关于项目的讨论也会在这个入口发生,它需要去读代码,
>   那它的缓存可能就给不到 Agent Team 里面的 Leader。
>  ⇒ 所以我觉得**目前前端可能不需要步子跨得那么大**,
>  **前端始终还是作为一个"投影"存在**。
>  我原本说的那种模式,可能是在投影之上还做了**一些其他的聚合入口**,
>  但我觉得**内测先不做,我们还是只做一个投影**。
>
>  **目前的 Agent Team 是对项目本身的子 Agent 的一个团队投影,对吧?
>  那我们后续要做的一个投影,就是一个跨项目、跨工作区的投影。**」

## 1. ★★★ 而用户那两条理由，**技术上都成立** —— 而我补一条数据

### ① 上下文过大 —— ★ 而它有一条**我们已经踩过的证据**

```
★★ t109 的实测:给一个工具加跨区能力 ⇒ ★ 那工具的上下文要含【它操作的那个区】
★ 而 t104/t107 的三个实验已经证明:跨区【读】通 · 跨区【写】通
★★ 而【能力通】不等于【该在一个会话里用】
⇒ ★★★ 用户选的是:★ 能力先不做，而投影先做 —— ★ 而那让"上下文"这个问题【不出现】
```

### ② 缓存无法共享 —— ★ 而那一条**我核实了机制**

```
★★ 用户说:「这个入口需要去读代码，那它的缓存就给不到 Agent Team 里面的 Leader」
★ 而实测(dsh-session 的四类 compaction 事件 + billion-context 的生产数据):
  ★ 前缀缓存是【按会话】的 —— 一个会话读过的代码，另一个会话【不复用】
⇒ ★★★ 所以"统一入口替所有人读代码"会:★ 让入口的上下文爆掉，
   而【同时】不给 Leader 省任何东西 —— ★ 那是【双输】
```

⇒ ★★ **所以那两条不是"取舍"，是【两个都会变差】。用户的判断是对的。**
