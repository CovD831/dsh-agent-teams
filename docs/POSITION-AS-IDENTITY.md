# 位置不是身份：夹具把行号当成了身份（f-0029 / t88）

> 本文记录 f-0029 的**兑现**与修法。
> 判据本体在 `scripts/gate-index-assembly.test.mjs` 的 `deliversConclusion()`。

---

## 1. f-0029 的原文与它的处置

```
★★ 5 处夹具硬编码了 src/tools.ts 的【行号】
★ 而当时（t30）captain 的处置是：
  「要求 t30 在报告里点明它们会失效，并把『该怎么改』留成建议」
⇒ ★ 即：那 5 处【没有被修】，只被记下来了。
```

---

## 2. ★★★ 它兑现了：600 行的窗口已经不够

`gate-index-assembly` 臂 4c 里此前是：

```js
const index = lines.findIndex((line) => line.includes(site.line))
const window = lines.slice(index, index + 600).join('\n')
```

★ 它的历史是**两次换常数**：80 → 600。而两次都是**位置式**读数。

### 2.1 ★★ 实测：逐点量出来的距离（t88）

```
delivery    anchor@2988  exit@3031  距离   43  ✅ 在窗口内
runtime     anchor@5721  exit@5815  距离   94  ✅
contract    anchor@5835  exit@5893  距离   58  ✅
delivery    anchor@6992  exit@7052  距离   60  ✅
completion  anchor@7618  exit@8585  ★ 距离 967  ❌ ★ 在 600 行窗口【之外】
dispatch    anchor@7738  exit@8584  距离  846  ✅（差一点就出界）
```

⇒ ★ `completion` 那一处**被判成"没有出口"，而出口就在源码里**
（`src/tools/update-task/dispatch.ts` 一类模块里的
`completion_input_surface: completionInputSurface`）。
⇒ 实测：臂 4c 因此**红着**，而它红的原因是"两次出现的**距离**变了"。

### 2.2 它与 t69 是同一个形态（j-0003）

> **代理读数在它所代理的东西没变时也会变。**

```
代理是"距离 ≤ 600 行"，被代理的是"那个变量【有没有】被交出去"。
★ 而"有没有"是一个【全文】问题，不是"附近 600 行"问题。
```

### 2.3 ★ 为什么"把 600 改大"不是修法

任何常数都会被下一次重排超过（今晚已有两次拆分：t39 拆 tools.ts、t70 拆 update-task）。
⇒ 那是一个**位置常数**，而**位置不是身份**。

---

## 3. 修法：按【归属】判断，而归属由出口自己说出来

要看的是：**有没有一处出口，它交出去的正是【这个变量】**。
而出口的形状本身就带着那个变量的名字：

```
input_surface: <变量>            ·   <前缀>_input_surface: <变量>   ·   return <变量>
```

⇒ 所以判法是**全文**找那个形状（`deliversConclusion()`），而不是在某个窗口里找。

### 3.1 ★ 它不是"放宽成全文匹配"——它比窗口【更严】

```
窗口里出现【别的变量】的出口  ⇒ 原写法**通过**（那才是误判）
全文要求出口【点名那个变量】  ⇒ 原写法在这里会红，而新写法对
```

### 3.2 ★ 实测：这个口径既精确又唯一（不是"我觉得"）

在 8599 行的源码面上，每个变量的出口出现次数：

```
deliveryInputSurface      2 次      runtimeInputSurface     1 次
inputSurface              1+1 次    completionInputSurface  1 次
dispatchInputSurface      1 次
```

⇒ ★ 没有"满地都是"的歧义，而它对**重排完全免疫**。

### 3.3 反向半边：它没有放宽

```
把一个出口从源码里删掉（或改成 `return undefined`）
  ⇒ 全文也找不到 ⇒ `deliversConclusion` 为 false ⇒ 臂【仍然红】
```

## 4. ★★★ 修的过程中我引入的第二个缺陷（与要修的那个同形）

★ 我为了"剥掉注释与字符串"写了一个状态机，而它**两次**都以"源码在某个位置之后被截断"收场：

| 版本 | 错在哪 | 后果 |
|---|---|---|
| 一 | 退出字符串时比的是 `ch === 'str'`（一个**词**），而 `ch` 是单字符 | 状态再也回不到 `code` ⇒ 第一个字符串之后**全部丢掉** |
| 二 | 引号修好之后，**模板字面量里的 `${…}`** 又让它失衡 | 源里有 **2954 个反引号**，算错一次就让**后面全部**丢掉 |

⇒ ★ 后果：本判据的**读数范围**悄悄变短，而它的结论仍然看起来很确定
（"没有出口"）。

> **我为了修"位置不对"，而引入了一个"范围不对"。**

⇒ 而两者是**同一种**缺陷：**读数不是它声称的那个东西。**

### 4.1 正确的做法：只剥注释

```
要看的是「有没有一处出口交出的是这个变量」，而出口的形状长在【代码】里。
字符串里的那些出现（'completion_input_surface' 这种【字段名常量】）不是出口 ——
而它们也不会被误判：正则要求冒号右边**就是这个变量名**，
而字符串常量里写的是**字段名**，右边没有变量。
```

★ 而**已知代价**（写出来，不假装没有）：行内 `//` 之前若在字符串里会被误剥 ——
那只会让那一行的**尾部**少几个字符，而出口的形状是**一行之内**的完整表达式，
不会跨过被误剥的边界。

## 6. 剩下什么没做（如实）

```
1. ★ 我只改了 inScope 里的两个夹具。实测：那 5 处里**没有一处在 out-of-scope 的
   三个夹具**（gate-input-wiring / verify-input-requires / verify-readout-uniform）——
   它们在那些文件里的 `slice(` 命中全是【错误消息截断】（`.slice(0, 160)` 那类），
   不是位置式读数。⇒ 无需转给 t86。
   （本队记账：「一个 grep 命中与一个真缺陷在计数上同形。」）

2. ★ `gate-proxy-readings.test.mjs` 里保留着 t69 那份**旧写法**作为
   【测试数据】（`t69old` / `distance`）—— 那是对的：它记录的是**被证伪的那个写法**，
   而它的存在正是"这条形态被抓住过"的证据。⇒ 本任务**不动它**。

3. ★ 本文记的"只剥注释"是一个**够用**的口径，不是最精确的。
   若将来出口的形状需要跨行判断，那就要一个能正确处理模板串的词法分析
   —— 而那件事**不该**由这条判据自己做（它会变成不可测的解释器）。
```
