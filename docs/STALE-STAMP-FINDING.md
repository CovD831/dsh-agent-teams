# stamp 的自指性：一个无法描述自己所在提交的产物（MEASURED 2026-10-12）

## 由来

`runtime-eng` 在 `t34` 的第 6 次尝试里报告：契约命令全绿（41/41），而**全量套件
多出 3 条红**，全在 `gate-stale-module`。它给的成因是**结构性**的，不是编码错误。

**这份文档的存在理由**：这个成因**看起来像**"某个人的改动弄坏了三条不相干的臂"，
而它实际是**产物与提交之间的一条循环依赖**。队长独立复现并逐条核过下面每个数字；
若不留下，下一个人会把那 3 条红读成"t34 引入的回归"。

---

## 1. 机制：产物无法描述自己所在的提交

```
commit N    : 跑 pnpm build ⇒ 写 stamp{commit: N}
commit N    : ……而【包含这个 stamp 的那个提交】是 N+1
```

⇒ **`stamp.commit` 永远落后 HEAD 恰好一个提交，这是构造性的，不是失误。**

`scripts/git-artifacts.mjs` 的判据把这件事**明确定义**成第三态（不是"通过"）：

| 三态 | 含义 |
|---|---|
| `current` | 三个摘要都对上，**且** `stamp.commit` 就是当前 HEAD |
| `stale-commit` | 摘要都对上，**而** `stamp.commit ≠ HEAD` |
| `content-differs` | 摘要对不上（并说出是哪一半变了） |
| `unknown-commit` | commit 读不出来（不在仓库里 / 没有 git）⇒ 不许报 current，但**不阻断** |

⇒ 而 `stale-commit` 的**读者指引**说得很重：进程可能在跑更早的构建，
那"能重新打开一个已经修好的缺陷，并**同时阻断两种终态**"。

---

## 2. 队长独立复现（逐条实测，不是转述）

| 步骤 | 读数 |
|---|---|
| 起始：`stamp.commit = 02976b4`，`HEAD = 887d98a` | 相差 ⇒ 落后态 |
| `node --test scripts/gate-stale-module.test.mjs` | **20 pass / 4 fail** |
| 手工把 `stamp.commit` 直接改成 HEAD（**只改标签**） | **18 pass / 6 fail** ← ★ **更差** |
| 恢复，改走**真实路径** `pnpm build`（末步 `git-artifacts --write`） | stamp=887d98a=HEAD |
| 再跑同一条 | **23 pass / 1 fail** |

★ 第三行是个**反直觉的对照**，值得记住：**手工把标签改成 HEAD 反而更红。**
`--write` 不只写 commit，它同时重算 source/output 摘要并原子地写三者；
只动 commit 会造出"标签说 current、而摘要与提交不一致"的组合 —— 也就是
**用一次伪造把三态压成两态**。⇒ **修法是跑那条真实的写入路径，不是编辑产物。**

---

## 3. 4 条红里有多少是它造成的

```
4 fail（落后态） − 1 fail（`臂 10（三态在拒绝里也分形）`）
```

而 `臂 10` **在改动前的基线里也红**（`/tmp/gates-baseline.txt` 与改动后各出现 2 次）
⇒ 它是**存量 19 条**之一，与本成因无关。

⇒ 所以这个成因恰好贡献 **3 条**新增 —— 与报告者的数字**逐条吻合**。

---

## 4. 为什么它值得单独记：它伪装成三件互不相干的事

同一个成因让 `gate-stale-module` 的**臂 1 / 臂 4 / 臂 6** 一起变红，
而这三条断言的**标题里都没有 "stamp" 这个词**。⇒ 读到的是
"三条不相干的臂坏了"，而不是"一个产物落后了一个提交"。

**★ 而它还会和别的东西叠加成路障**：报告者称它很可能就是**前几次尝试**卡住的原因 ——
一条看起来像自己改坏了的红，会把人引向"回滚自己的改动"，而**回滚不会让它变绿**。

---

## 5. 未做的修法（两条，都要人定）

| 修法 | 代价 |
|---|---|
| **stamp 的 commit 不与"移动的 HEAD"比较** —— 例如只比摘要，或把 commit 记为"构建时所在提交"而不作判据 | 会**削弱**一条真实能力："本进程加载的是哪个提交的代码"就答不出来了（见 `git-artifacts.mjs` 的注释：这正是它存在的理由） |
| **提交 stamp 的那一步立即重新打戳**（同一提交内自洽） | 需要一条"提交后重打并 amend/追加"的流程；而每次 build 都会改变 git 状态，容易与"干净工作树"的要求打架 |

⇒ **两条都有真实代价，所以没有擅自改。** 当前的处置是：**构建按真实路径重打戳**
（这就是 `pnpm build` 已经在做的），并在**提交后**接受它落后一个提交。

---

## 6. 可迁移的纪律

1. **产物无法忠实描述包含它自己的那个提交** —— 任何"产物里记录它被提交于何处"的设计，
   都要先回答"那这个记录本身在哪个提交里"。
2. **修一个产物要走产出它的那条路径，不要编辑它** —— 手工改标签把 4 红变成 6 红，
   因为写入器的语义不止"写一个字段"。
3. **一个成因伪装成多条臂时，先看它们是否共享一个输入** —— 三条标题里没有 "stamp"
   的臂，共享的输入正是那个 stamp。
4. **回滚自己的改动之前，先问"它能不能让这条红变绿"** —— 如果不会，那这条红就不是你的。
