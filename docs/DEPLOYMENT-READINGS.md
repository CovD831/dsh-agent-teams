# 部署读数：两个并列的问句

> **出口**：`status` 的 `deployment` 格
> **本文回答**：一个部署读数该接到哪，而理由是什么。

---

## 一、★★★ 它先要回答的那个设计问题

> **部署读数属不属于【成员能看见的面】？而它与 `status.deployment` 是什么关系？**

### 答案：属于；而它是**第二个并列的问句**，不是同一个

MEASURED（同一时刻、同一进程里同时读两个）：

```
PROCESS  (moduleFreshness)            ⇒ stale   | behind = "58bd7e93fd84…"   ← 一个 **hash**
WORKTREE (worktreeBaselineFreshness)  ⇒ current | behind = 0                  ← 一个 **计数**
```

★ 两个答案**同时成立** —— 而它们说的是两件独立的事：

| 读数 | 问的是什么 | 主体 |
|---|---|---|
| `deployment`（t34 / f-0026） | **这个进程**手里的是旧代码吗 | 进程 |
| `deployment.worktree`（t80 / t84） | **这个检出**比主干旧吗 | 目录 |

⇒ ★ 它们可以**任意组合**：
进程可以是当前版而检出落后 67 个提交（本仓实测 `task-t13`）；
检出可以在尖端而进程持有旧构建。

**⇒ 所以不能合并。** 合并会让「我该重启」与「我该重切分支」**同形** ——
而那两个补救动作完全不同。

---

## 二、★★ 而它们**同名**：两处都有 `behind`，而类型不同

```
deployment.behind           ⇒  **string**（那个 hash：我在哪个提交上构建的）
deployment.worktree.behind  ⇒  **number**（落后几个提交）
```

★ 这正是本队记账的「**守卫检查了另一个同名的东西**」的近亲 ——

> 两个读数同名而不同义 ⇒ 读的人会拿错。

⇒ 所以 `worktree` 那一支**嵌一层**，而不是把字段摊平进 `deployment`。
（判据臂 T2 钉住这一条：两个 `behind` 的类型必须不同形。）

---

## 三、★★ 接法：扩那一格，不新开通路

### 为什么扩 `deployment`

t34 的先例在这里同样成立：**`status` 是每次收口后必然被读的那个出口。**
而"我这个检出旧不旧"恰恰是**每个 worktree worker 收口时**最需要知道的事 ——
t72 读到 28 条红而主树只有 4 条 · t70 报了一条已经修好的缺口，两次都栽在它上面。

### 为什么不新开一格

本队那条纪律是决定性的：

> **一个没有人读的读数，与没有那个读数在观测上完全相同。**

⇒ 新开一格**可能永远没人读**；扩一个**已经在被读**的格子不会。

### 为什么不走 t76/t83 那条路

那两个走的是「**由调用方注入**」—— 而那是**给判据读**的（判据不读盘）。
这一格是**给人和成员读**的。

⇒ **两个方向，两个出口**，而它们的判据不同：

| 出口 | 谁读 | 接法 |
|---|---|---|
| `ctx.*`（注入） | **判据** | 调用方在求值前传进去 |
| `status.deployment` | **人和成员** | 判据层之外的读数，挂在唯一必被读的那个出口上 |

## 四、三态，且从**出口**读得出来

```
current      ⇒ 检出在主干尖端（差 0 个提交）
behind       ⇒ 落后 N 个（★ 附 N、主干尖端、以及本检出的 HEAD）
undecidable  ⇒ 读不到（不是仓库 / 没有 HEAD / 没有主干引用）
```

★ 而三态**必须从出口读得出来**，不是只能从函数返回值读 ——
否则它就是"一个存在但没人看得见的读数"。

---

## 五、臂

| 臂 | 它钉什么 |
|---|---|
| **T1** | **出口臂**：构造一个真的落后的检出 ⇒ `status` 必须报 `behind`，且 `behind` 是一个**计数** |
| **T2** | **同名不同义臂**：两个 `behind` 的类型必须不同形（string vs number） |
| **T3** | **反向半边**：在尖端时出口必须报 `current`（不许恒报 behind） |
| **T4** | **不变**：进程那一支的读数一字不改（顶层 `status` 仍说进程那件事） |
| **T5** | **schema 对齐**：出口 schema 必须声明新字段（否则 `additionalProperties: false` 会让 status 拒绝自己） |

### 定向突变（实测打红）

```
把出口改成恒报 current  ⇒ 臂 T1 红
```

## 六、★★★ 本任务实测踩的坑（三个，都留在这里）

### 坑 ①：夹具里那个局部的 `git()` 助手没 `.trim()`

`git rev-parse HEAD` 的输出带一个**尾换行** ⇒ 那个"SHA"不是 SHA ⇒
`git switch --detach <它>` 报 `fatal: invalid reference`。

★ 而那个报错的形状【**与"这段代码没生效"同形**】——
我第一反应是去查 git 的 ref 语义，而真因只是少了一个 `.trim()`。
★ 文件顶部那个 `git()` 助手是 trim 的，而这个局部的不是：
**同一个名字，两处不同实现** —— 而那正是本队记账的形态之一。

### 坑 ②：`git switch` 会把 `.agent-teams/team/team.json` 弄没

它是未跟踪的，而 checkout 会清掉挡路的未跟踪内容 ⇒
`status()` 报 `you do not lead or belong to any active team yet`。

⇒ ★ 所以构造顺序是**决定性的**：**先动检出，最后建团队** ——
因为"检出移动"与"团队存在"是两件独立的事，
而这一臂要测的是**前者对读数的影响**。

### 坑 ③：那个定向突变**第一次没编译过**

写成 `const baseline = { status: 'current', … }` ⇒ TS2345 ⇒ `pnpm build` 退 2 ⇒
`lib/` 里还是旧代码 ⇒ **臂 T1 全绿**。

★ 形态：**「突变没生效」与「臂是恒真的」在症状上完全相同**
（本队已在 t39 与 t76 各记过一次）。
⇒ 修法：让突变是**类型正确**的（`const baseline: typeof baselineReal = …`），
确认 `pnpm build` 退 0 之后再读臂的读数。

## 七、★ 一条与 t80 同源的话

t80 发现：两点式（`main..HEAD`）方向是反的 ⇒
塞进**观察面**会把**别人的**改动算成本次任务的改动。

★ 而这里的风险**同形**，所以本任务问的是：

> **这个读数该与哪个读数并列，而不该与哪个混？**

答案：它与 `deployment`（进程那一支）**并列**，而与 `changedPaths`（本次改了什么）
**不相干** —— 后者问的是"我改了什么"，前者问的是"我站在哪里"。
