## 1. ★★ 调研：变点检测（changepoint detection）给了什么

**`deepcharles/ruptures`（★2098,Signal Processing 2020 综述）逐字:**
> 「`ruptures` is a Python library for **off-line change point detection**.
>  This package provides methods for the analysis and segmentation of
>  **non-stationary signals**.」

**`zhaokg/Rbeast`（★373,BEAST,Bayesian）逐字:**
> 「**Bayesian Estimator of Abrupt change, Seasonality, and Trend**……
>  a fast **Bayesian model-averaging** algorithm for decomposing time series
>  into **abrupt-change, trend, and seasonal components**.」

★★ **它们都指向同一个东西:一个序列里"什么时候变了"是**可以算的**,但有前提:**
```
· ruptures ⇒ ★ 需要【足够多的点】才能分割（它的算法都是"分段代价最小化"）
· BEAST    ⇒ ★ 用【模型平均】给出"某个点是变点的概率"
⇒ ★★ 两者的共同前提:序列要有【多点】—— 而本仓 91% 的桶只有 1 点
```

★ **所以本仓的处境是:**变点检测**方法上可用,而数据上暂不可用**。
⇒ ★★★ **而那【必须如实报出】,不能假装能算。**

### 1.1 ★★ 一个可用的中间形态（在数据不够之前）

```
★ 不假装能算"变点",而只报【三个可数的量】:
   ① 改动前的计数（before.count）
   ② 改动后的计数（after.count）
   ③ ★★ 而 verdict 用【结构性判据】而不是统计判据:
      · before.count === 0        ⇒ ★ unmeasured（无基线，无从比较）
      · after.count <  before.count ⇒ ★ improved（它降了）
      · after.count >= before.count ⇒ ★ unchanged（它没降）
★ 而"降了多少才算 improved"这个问题 ⇒ ★★ 先不设阈值，先报数
  （理由见 §4：MemOS 的"阈值永不触发"教训）
```

## 2. ★★ 靶的选取规则（第 ② 项）

### 2.1 ★★★ 而它有一个**天然的答案** —— 因为信号【自己带着靶**

**实测 `EvolutionSignal` 已有这些字段:**
```ts
source: { where, gateId?, tool? }     ← ★ 谁拒的
index?:  { component?, kind? }        ← ★ 分类
```

⇒ ★★ **所以靶不是"选"出来的,而是【从信号本身读出来的】:**
```
target = { component: signal.index.component,
           kind:      signal.index.kind }
★ 而改动前那个桶的计数 = 【改动那一刻】从台账算
```

### 2.2 ★ 而"一条改动可能影响多个桶"怎么办

```
选项 ① 一个靶（主靶）
选项 ② 多个靶（全部）
选项 ③ ★★ 一个主靶 + 其余作【副作用观测】
```

★ **建议 ③** —— 理由:
```
· 一个改动通常针对【一个】桶（否则它该被拆成两条改动 —— 闸门 contract.task-atomicity 就这么要求）
· ★ 而"副作用"是真实存在的（改了 A 桶可能动 B 桶）
⇒ ★★ 主靶进 verdict，副作用只进 readings（不进 verdict）
```

## 3. ★★ "effective" 的阈值（第 ③ 项）

### 3.1 ★★★ 而它撞上 §0 那个测量:**91% 的桶只有 1 条**

⇒ ★★ **所以不能用"显著性"**（没有任何统计检验能用 n=1）。

### 3.2 ★ 而 MemOS 的教训正好适用

**`memos-local-plugin/core/feedback/ALGORITHMS.md` 逐字:**
> 「**`minEpisodesForInduction` 在源码里【已被下调到 1】**,
>  注释**反复记录「真实使用中阈值永不触发」**。」

⇒ ★★★ **所以本仓的阈值也该是同一形态:**
```
★ 阈值【不精确】也可以，只要它【只做提示】而不做【执行开关】
★★ 而 memex 把这条写成了通则:
   「阈值不该是执行开关，该是提示开关。判据满足 → 提议；不满足 → 等用户直接说」
```

### 3.3 ★★ 所以建议：**三级判据,而第一级不含阈值**

```
① before.count === 0                      ⇒ ★ unmeasured（无基线）
② after.count <  before.count             ⇒ ★ improved（★ 无阈值：降了就是降了）
③ after.count >= before.count             ⇒ ★ unchanged
★ 而"幅度"作为一个【读数】报出（降了 30% / 降了 2%），不进 verdict
⇒ ★★ 理由:一个【精确阈值】在 n 很小的时候会把"降了 2%"判成无效，
   而那与"根本没动"同形 —— 正是本仓记账最久的形态
```

★ **而真正的"要不要晋升"该由【人】或【第二个读数】决定** —— 见 §5。

## 4. ★★ 窗口的长度（第 ④ 项）

### 4.1 ★★★ 而固定窗口在这个数据上站不住

```
实测:dispatch·unwired 的跨度是 2026-10-07 → 10-14（7 天）
     而 49 个桶只有 1 条 ⇒ ★ 任何"固定窗口"都会让它们落进 unmeasured
```

### 4.2 ★★ 所以建议：**窗口按桶自适应,而默认是"全历史"**

```
before 窗口 = ★ 从该桶的【第一条记录】到【改动那一刻】
after  窗口 = ★ 从【改动那一刻】到【评估那一刻】
★ 而两边都用【计数】，不用速率（速率需要时间归一，而 49 个桶没有第二个点）
```

★★ **而这个选择的代价要如实说:**
```
· ★ 它不控制"时间长短"⇒ 一个 7 天的 before 与一个 1 天的 after 可比性弱
· ★★ 所以 after 窗口【太短】时必须报 unmeasured
  ⇒ 判据:after 窗口 < 【某个最小观察期】⇒ ★ unmeasured
  ★ 而那个"最小观察期"是多少 —— ★ 我没有依据，需要实测积累
```

### 4.3 ★ 而"最小观察期"的一个可用代理

```
★ 用【该桶的历史中位间隔】:
   dispatch·unwired 的 167 条跨 7 天 ⇒ 中位间隔约 1 小时
⇒ 而最小观察期 = max(1 天, 中位间隔 × N)
★ 而 N 取多少 —— ★ 也没有依据
⇒ ★★ 所以第一版建议:最小观察期 = 【1 天】,并把它作为一个常量记录在注释里
   ★ 而它【必须可改】—— 因为它是一个猜测，不是一个测量
```

## 5. ★★★ 结论：四项的答案,以及**哪几项是猜的**

| # | 项 | 答案 | 性质 |
|---|---|---|---|
| **①** | 分流的映射表 | ★ 用**已有 21 条判据**量"能否机械判定" | ⚠️ **需实测**（见下）|
| **②** | 靶的选取 | ★ **从信号读出**（`index.component` + `index.kind`）| ✅ **可确定** |
| **③** | 阈值 | ★★ **不设精确阈值** —— 只看"降了没有",幅度作读数 | ✅ **有依据**（MemOS）|
| **④** | 窗口 | ★ 自适应（该桶全历史），且 after 太短 ⇒ unmeasured | ⚠️ **"最小观察期"是猜的** |

### ★★★ 而"哪几项是猜的"必须写进代码注释

```
★ 有依据的:②③（② 可从数据读出，③ 有 MemOS 的实测教训）
★★ 是猜的:④ 的"最小观察期 = 1 天"（我没有依据）
⇒ ★★★ 而"猜的"与"有依据的"在代码里必须【不同形】——
   否则下一个人会把一个猜测当成一个测量
```

### ★★ 而 ① 的实测方法（我建议的）

```
★ 拿本会话那 10 条记录（t88 补录的）去问:
   "它像不像某条已注册判据能抓的形态？"
   · e-0007（五条未声明产物）⇒ ★ 像 contract.build-artifact-scope ⇒ hard
   · e-0003（两表重叠）      ⇒ ★ 像 scope 校验 ⇒ hard
   · e-0002（四态逻辑在别处）⇒ 不像 ⇒ soft
   · e-0005（S1 被删）       ⇒ ★ 像 t75/t76 的新判据 ⇒ hard
★ 而那个映射【是人工做的第一版】—— 因为只有 10 条
⇒ ★★ 而它【正是用户说的"数据回填"】:先人工标，再让模型做
```

## 6. ★ 一个我必须如实说的边界

```
★★ 本仓现在的数据【不足以】做统计意义上的收益衡量:
   54 个桶里 49 个只有 1 条 ⇒ 91% 无趋势可言
⇒ ★ 所以第一版的收益衡量【只能】是"降了没有"这种粗判据
⇒ ★★ 而它【够用】—— 因为它的目的不是"证明有效"，
   而是把"改了但没生效"与"没改过"【分开】
   ★ 而那正是本仓记账最久的形态
```

★ **而它什么时候能升级到统计判据:** 当有桶积累出**多个时间点**时。
**⇒ 那是一个可观测的条件,不是一句"等数据够了"。**
