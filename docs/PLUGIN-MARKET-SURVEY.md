## 1. ★★★ `dsh-taskboard`（★66）—— **它的挂载方式是我们该抄的**

### 它的原话（逐字）

> 「**双轨挂载（0.8.0）**：dsh ≥ 0.1.7（带官方 slot 系统）时,
>  看板作为**一等侧边栏面板**注册（`sidebar.panellist` + `main`,
>  **宿主拥有侧栏行与面板切换**,从根本上消除「**看板打开后其他面板点不动**」这类问题）;
>  旧版 shell 自动回落到原有的 DOM 注入方式……
>  ★ 两条路径**运行时自动互斥选择**,无需配置。」

★★★ **而那句「看板打开后其他面板点不动」正是我们需要核实的:** 我们现在是哪种?

**队长实测:**
```
★ 我们的 ActivityPanel 用 @deepseek-ai/dsh-client-ui-slots（官方 slot）
★ 而 AgentTeamsCard / SessionIdAction 也用
⇒ ★★ 所以我们【已经在】官方 slot 上 —— 那一条我们不缺
```

★★ **而它有一句值得我们记的边界:** 「宿主拥有侧栏行与面板切换」
⇒ **那解释了为什么"侧栏行"不该由插件画。**

### ★ 它的形态（实测自 README + 截图）

```
★ 五列流转看板（待办 → 执行中 → 待验收 → 完成 → 归档）
★ 每张卡:标题 · 优先级 · 模型/preset · 状态
★★ 卡内嵌 diff 查看器 · DoD 验收清单（agent 勾选 + 附证据）
★ SSE 实时刷新 · 筛选排序持久化 · JSON 导入导出 · 任务模板
```

★★ **而它的分工与我们的**关键差别:**
```
它:人建卡 → agent 认领 → 结构化报告 → 【人验收】
我们:队长建任务 → 成员认领 → 判据裁决 → 【判据验收】
⇒ ★★ 它是"人当验收者"，我们是"判据当验收者" —— ★ 而两者不冲突:
   我们的判据层可以【投影进】那种卡片上
```

## 2. ★★★ `dsh-agent-board`（★6）—— **它的 PRD 与本会话的裁定高度重合**

### 它的描述（逐字）

> 「DeepSeek Harness 智能看板:**任务卡片 + 一次性 Worker/Verifier 派发 + 依赖调度
>  + 管线分档 + Team 模式（歧义上报主窗口裁决）**」

### ★★★ 而它的 PRD 里有**四条值得我们直接吸收**的（逐字）

**① 「计时器从刽子手变为报警器」**（v5.8）
> 「**不再自动杀 Agent**：pump 移除 300s 死刑,改为看门狗（30s 间隔检查事件增量）;
>  运行 >300s 且事件流停滞 >60s → 标记 `suspect` + `task.stuckSince`,
>  **不 dispose、不重排队**」

★★★ **而那正是本仓 `runtime.stall` 判据的同族** —— 而**它的处置更保守**（只标记,不杀）。
★ **可吸收:** 我们的 stall 判据是否也该有 `suspect` 而不只是告警?

**② 「裁决对话线程」**（v5.6）
> 「`task.messages[]` **持久化完整问答流**（escalation 疑问全文 / arbitration 裁决全文 /
>  intervention 介入全文,带时间与身份）,**不再"裁决后即删疑问"**。
>  详情页呈现为**对话线程**（Worker 红泡 / 主窗口品牌泡 / 介入黄泡）」

★★ **而我们有 `inbox/*.jsonl` 与 `reviewed` 记录** —— 而**没有"一条线程"的呈现**。
★★★ **而那正是"歧义上报"这件事的形态**:一个问题 + 一次裁决,是一条对话,不是两个字段。

**③ 「verifier 异构化」**（v5.12）
> 「`spawnAgent` 支持 `agentOptions.model` 覆盖……默认 `qwen/deepseek-v4-pro`……
>  ★ **spawn 失败回退父级模型**」

★ **而我们已经做了**（`reviewer-glm` 用 glm-5.3-flash ⇒ 跨模型复核）—— **两边独立想到同一件事。**

**④ ★★★「v5.4 的四条真实缺陷」—— 与我们踩过的完全同族**

```
它 (1): init 竞态 ⇒ seed 误判（spawn 后 init turn 未完成就派发,
        readOutput 回扫到【主会话 seed 的旧消息】⇒ verifier 凭陈旧内容误判驳回，曾连续 3 次）
   ★★ 而我们是:t84 的 role 两个消费者 · t90 的 12 个坏台账文件
   ⇒ ★★★ 同一条:"读到了一个【不是此刻】的状态"**

它 (3): verdict 误判 —— `/approved/ && !/rejected/` 全文匹配把
        "提及历史 REJECTED 的正面审查"误判为驳回
   ★★ 而我们是:t73 的"判据自毁参照"· t96 的"引的锚点属于另两个测试"
   ⇒ ★★★ 同一条:"模式匹配到了【不该匹配的那一处】"
```

## 3. ★★ `dsh-graph`（★18）—— 一个**形态上新颖**的

> 「把工作组织成目标看板的插件:**目标 / 判据 / 上下文卡片 / 执行 attempt
>  的【二维泳道】看板**,数据以文件+事件流落在 `.dsh-graph`」

★★ **"二维泳道"值得看一眼**:两轴分别是**目标**与**执行 attempt**。
⇒ ★★ **而那与我们"判据插入点(一维) × 成员(另一维)"是【同一种二维】:**
```
我们的纵轴:成员（谁）
我们的横轴:判据插入点（走到哪一步）
⇒ ★★★ 而 dsh-graph 把第二维叫 attempt —— ★ 那正是"一次尝试"
```

★ **可借鉴:** 它把**判据**作为卡片的一类（与目标、上下文并列）⇒
**那与我们"判据是可投影的读数"是同一条。**

## 4. ★★★ 三条我对"我们该抄什么"的判断

### ① ★★ 挂载方式:**我们已经对了**（官方 slot）

```
★ 它花了 0.8.0 一整版去解决"看板打开后其他面板点不动"
★★ 而我们一开始就在官方 slot 上（@deepseek-ai/dsh-client-ui-slots）
⇒ ★ 这一条不缺，也不必改
```

### ② ★★★ 而**形态**上最值得吸收的是它那条「**裁决对话线程**」

```
★ 我们有:inbox/*.jsonl + reviewed 记录 + gateEvaluation —— ★ 全是【字段】
★★ 而它把一次"提问→裁决"呈现成【一条对话线程】
⇒ ★★★ 而那正是你反复要的:"把约束体现出来" ——
   约束不是一组数字，它是【一次一次的问与答】
```

★ **而它还能直接回答我们 §"歧义上报"那个待裁定的问题**（如果我们要做的话）。

### ③ ★★ 而**最该警惕**的是它那种"五列看板"

```
★★ 它的看板是【以任务为主屏】的（卡片是主体）
★★★ 而你已裁定「以成员为主屏」（UI-INFORMATION-ARCHITECTURE §2.1）
⇒ ★★★ 所以【不能照抄它的形态】—— 但可以吸收它的【卡片内部】的做法:
   diff 查看 · DoD 清单 · 结构化报告 · 对话线程
```
