# 接线要被钉住（S3）

> **判据**：`scripts/gate-wiring-pinned.test.mjs`
> **一句话**：断言**调用点**存在，而不是断言**函数**存在。

---

## 一、它来自一次真实事故（静默了几个小时）

```
① t41 造出 worktree-aware 扫描 workspaceAndWorktreeChangedPaths
   （src/harness-compat.ts:302）
② captain 用一行把它接上 —— 这是那次修复真正落地的版本：

     a0f6504   gitChangedPaths: workspaceAndWorktreeChangedPaths(workspace)   ← 接上

③ 而 t39 拆 tools.ts 时，那一行被【搬回了旧版】：

     9779c58   gitChangedPaths: gitChangedPaths(workspace)                    ← 回退

④ ⇒ 那个函数【又变成零调用方】，而【没有任何东西报】。
     ★ 直到 t56 的成员被那条拒绝挡住 —— 那是几小时之后。
```

**写这份判据时的实测**（HEAD `46624be`）：

```
$ grep -rn "workspaceAndWorktreeChangedPaths" src/ | grep -v harness-compat.ts:302
$ （无输出）

⇒ ★ 事故不是"曾经发生过"，它在写下这些字的时候【仍然是活的】。
  臂 1b 每次都把这条现状打印出来。
```

---

## 二、★★ 为什么判据的形状是关键的

一个"**函数存在吗**"的断言，在那次事故里**全程是绿的** —— 因为函数一直在
`src/harness-compat.ts` 里，从来没被删。

```
   「函数还在」与「有人调用它」
   ⇒ ★ 在【函数还在而没人调用】时，这两件事【同形】。
```

而那正是本队记账最久的形态：

> **一个没有调用方的修法，与没有修法在观测上完全相同。**

⇒ 所以本判据数的是**调用点**：

```js
// 回退之后，这一行里 gitChangedPaths 仍然【在被调用】
gitChangedPaths: gitChangedPaths(workspace),
//                 ^^^^^^^^^^^^^^^^ ← "函数存在"式看到的是它
//   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ← 本判据问的是另一个符号有没有被调用
```

★ 本队已经在**四个不同地方**写下过同一句话（t42 两次、t47、t57），
而这里是它第一次被做成一条**判据**。

---

## 三、★★ 它为什么是【一张被声明的清单】，而不是"所有导出都要有调用点"

captain 的设计提醒：**"接线"这个概念太宽。**

断言「每个导出函数都必须有调用点」会：

- 与 **S1**（供给必须有消费）重叠；
- **误伤合法的 API 表面** —— 对外导出、被下游 `import` 的那些，本来就不该被调用。

⇒ 所以本判据**窄**：它读一张**人写下来的清单**，每条说「这一行必须调用那个函数」。

```
★ 而那张清单是它【全部的价值】：
  一条接线的存在是被【声明】的，而不是被推导出来的。
    · 推导只能得到"某处有人调用过它"
    · 声明才能得到"这一处必须一直调用它"
```

### 清单现在只有一条 —— 而那是刻意的

```js
export const DECLARED_WIRING = [
  { id: 't41-worktree-aware-scan', file: 'src/tools/update-task.ts',
    symbol: 'workspaceAndWorktreeChangedPaths', account: '…' },
]
```

★ 一份预先填满的清单，会把"我们决定要钉住什么"变成一个没人再看的长表 ——
**而那份长表与"没有清单"在维护效果上相同。**

### 加一条的判据（写给下一个人）

> 那条接线**必须曾经真的断过**，或者它的断裂**曾经真的静默过**。
> 不是"它看起来重要"。

---

## 四、三态，且第三态不得与第一态同形

| 读数 | 何时 | 含义 |
|---|---|---|
| `pinned` | 剥掉注释/字符串之后，数得到调用点 | 接上了 |
| `unwired` | 符号**在代码里完全不再出现** | 断开了（或从没接过） |
| `undecidable` | 读不到文件，**或**符号在、但没有直接调用点 | **判不了** |

★★ `undecidable` **绝不许**读成 `pinned` —— 那是本任务要防的那个合流。
★★ 而它也**不得**与 `unwired` 同形：

```
unwired      = 我看清了，它不在        ⇒ 动作：去接线
undecidable  = 我看不见                ⇒ 动作：换一种断言方式
```

★ 而 `unwired` 需要**更强的前提**：符号在剥掉注释之后**完全不再出现**。
那时没有动态构造能凭空变出一个文件里没提过的名字。
只要符号还被 `import` 着，本判据就**不能说**它一定没被调用 —— 那时它报 `undecidable`。

## 五、★ 附条件（用户 2026-10-08 的标准）

用户原话要点：

> 「特定条件下起效的也能加，只是需要把那些特定条件顺便加上去。」

⇒ 本判据的适用条件：

> **它只对【有明确调用点】的接线适用。**

★ 而那个条件写在**判据里**，不是写在文档里靠使用的人记得：
对一条动态构造的调用点（`handlers[name](...)`），它给出 `undecidable`
—— 也就是**明确说出"这不在我的适用范围内"**，而不是硬下一个结论。

## 六、★★ 一处实测出来的坑：探针找到了它自己的说明书

本文件的第一版**不剥注释**，于是它在那次事故里会报 `pinned`。

原因：`src/tools/update-task.ts` 的注释里**逐字写着**那次修复的说明 ——

```
★★ 2026-10-07（t41 的接线）：从 `gitChangedPaths(workspace)` 换成
   `gitChangedPaths: workspaceAndWorktreeChangedPaths(workspace)`
```

⇒ 一个不剥注释的 grep **在注释里找到了那个符号**，于是报 `pinned`，
而真实代码那一行仍然调用着旧函数。**探针找到了它自己的说明书。**

★ 形态：本队记账的「**守卫检查了另一个同名的东西**」的又一实例 ——
而这一次同名的是**注释里的那个名字**。
⇒ 所以剥离是**正确性的前提**，不是洁癖。臂 4 把它钉成断言。

## 七、臂与它们的定向突变

| 臂 | 它钉什么 | 打红它的突变 |
|---|---|---|
| 1 | 接线正确的样本 ⇒ `pinned` | 判据改成恒 `unwired` |
| **1b** | **如实报出现状的读数** | ★ 不允许消失（见下） |
| 2 | 回退那一行 ⇒ `unwired` | 判据不再数调用点 |
| 3 | 「函数存在」与「调用点在」同形 | 把两件事混成一个布尔 |
| 4 | 注释里的符号不算接线 | 去掉剥离 |
| 5 | 三态两两不同形 | 把 `undecidable` 并进 `pinned` |
| 6 | 真接好的报 `pinned` | 判据恒红 |
| 7 | 附条件写在判据里 | 把 `reason` 删掉 |
| 8 | 清单本身可核对 | 清单指向不存在的文件 |
| 9 | 端到端（真副本上的回退） | 同臂 2 |
| 10 | **历史臂**：`a0f6504` 上必须 `pinned` | 判据在真实源码上不工作 |

### ★ 臂 1b 为什么是【读数】而不是断言

它记录的是写下这份判据时仓库的真实状态。**故意没有写成 `must be pinned`**：

- 写成那样 ⇒ 它此刻恒红，而恒红的臂会教人忽略它；
- 而让它消失 ⇒ "清单里那一条其实没接上"这件事就无人知晓了。

⇒ 所以它断言"给出的是一条确定读数（不是 `undecidable`）"，
并把 `pinned` / `unwired` 都打印出来。**接回来之后，它应当被收紧成 must-be-pinned。**

### ★ 臂 10 为什么值得单独存在

它从 git 里取出 `a0f6504`（那次修复真正落地的版本），喂给**同一个**判据函数，
断言它报 `pinned` 并指名那个调用点。

- 它证明判据**能**在真实源码上工作（不只是合成字符串）；
- 它把"事故之前的正确形态"变成了一条**可复核的回归基线**；
- ★ 而它与臂 1b 合起来，就是那次事故的完整可执行陈述：

```
   同一个函数：a0f6504 上 pinned、今天 unwired
```

## 八、★★ 三关：为什么"数调用点"还不够（实测出来的两次）

写下这条判据的过程中，「断言调用点」这个说法被**两次**证明不够精确 ——
而两次都是**实测**发现的，不是想出来的。

### 第一关：那一行在哪（`at` 锚点）

**MEASURED**：只声明"文件 + 符号"时，把那一行改回旧版 **判据不报** ——

```
   const observed = observeWorkspaces(workspace)   ← 这个函数【仍然被调用着】
   …
   gitChangedPaths: gitChangedPaths(workspace),    ← 而那一行接线已经断了
```

⇒ ★ 「这个函数被调用了吗」与「**就是那一行**在用它吗」**不同形**。
   前者在"接线被搬走、函数另作它用"时是**绿的** —— 而那正是 t39 回退的精确形状。

⇒ 所以声明里有一个 `at` 锚点：**在那个键上，用的是不是那个值**。

### 第二关：那个值从哪来（`upstream`）

**MEASURED**：把上游换成单树扫描，而接线那一行**一个字不改** ——

```
   const observed = { paths: gitChangedPaths(workspace) ?? [] }   ← 不再是 worktree-aware
   …
   gitChangedPaths: observed?.paths,                              ← 锚点仍然匹配
```

⇒ ★ 值还在、接线还在，而**性质丢了**。
   那正是本队记账的「**守卫检查了另一个同名的东西**」的精确形状。

⇒ 所以还有 `upstream`：**那条接线要求的东西，真的还在做那件事吗**。

★ 两关合起来才是完整的"接线被钉住"：

```
   at         ⇒ 那一行还在用那个值
   upstream   ⇒ 那个值还来自 worktree-aware 的遍历
```

### 而它下面是【符号级】那条路

没有 `at` 锚点的声明，问的是更弱的「这个文件里有人调用它吗」。
**它单独使用时是不够的**（上面第一关就是它的反例），本文件保留它
是因为"动态构造 ⇒ 判不了"这件事只在那条路上才可能发生 ——
有锚点时不匹配就是**确定**的 `unwired`（锚点是明写的文本，没有动态余地）。

### ★ 第三关（意外发现的）：清单自己过期

**MEASURED**：把清单里的 `symbol` 改成一个拼错的名字，所有臂**曾经全绿** ——
因为臂的样本是从清单派生的，跟着错名字一起错，**自洽**；
而"清单失效"与"接线断了"在读数上同形。

⇒ ★ 形态：**清单自己错了，而症状看起来像代码错了。**
   那是「检查了另一个同名的东西」的近亲：检查的是**一个名字**，
   而那个名字与代码里的那个不是同一个。

⇒ 所以加了一臂：**清单里的符号必须在源码里（剥掉注释后）真的出现过**。
它问的不是"接好了吗"，而是「**这张清单还在说现在的事吗**」。

## 九、修复已落地（本条判据的现场验证）

```
t41 的接线在 9779c58 被搬回旧版。
★ 写这份判据时（HEAD 46624be）它是**断的** —— 臂 1b 当时打印出的就是那条缺陷。
★ 而 t59 把它接回来了，用的是 observeWorkspaces：
     const observed = observeWorkspaces(workspace)
     gitChangedPaths: observed?.paths,
```

⇒ ★ 臂 1b 的历史正好演示了它被设计时的用法：

```
  写下时      ⇒ 它是【读数】（打印现状，不断言）—— 因为当时写成断言会恒红
  它的注释里写下了收紧条件：「接回来之后，它应当被收紧成 must-be-pinned」
  接回来之后  ⇒ 按那条预先写下的条件收紧成【断言】
```

★ 一个曾经是读数的臂，在它等待的事实到来之后变成了断言。
**而那个转换不是事后决定的 —— 它是当初就写在注释里的。**

★ 而收紧之后立刻暴露了上面"第三关"那个洞（臂 1c 因此存在）：
若它一直是"读数"，清单过期会被一直打印成"一条待修的缺陷"。

## 十、★ 一条与全文同源的话

本判据的**全部内容**是这三个字：

> **断言调用点。**

而它一路展开成三关（`at` / `upstream` / 清单完整性），
每一关都是**实测撞出来的**，而不是设计时想到的。

★ 形态：**一个正确的方向（"断言调用点而不是函数"）在落到可执行形式时，
会分裂出好几个"何谓调用点"的层次** —— 而每一层都只有跑起来才会显形。
