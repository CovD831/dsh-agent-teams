## 二、今天建成的三套机制（你要的三件事）

### ① 卡点/经验 → 自动变成可执行的任务

```
卡点发生  ⇒ 自动记录（t22）
判决产生  ⇒ 有格式有读者（t57）

```

**★ 而它有三处【不硬凑】**（而那是最值钱的部分）：

| 情形 | 它说什么 |
|---|---|
| 匹配不上 | 「这只是谁现在空闲，不是谁擅长它」—— ★ 一个"总能挑出一个人"的实现会**撒谎** |
| 团队读不到 | 「我没能看」—— ★ 不许说成"没人空闲"（补救动作相反） |
| 契约缺项 | `cannot-emit` 并**逐项指名**缺什么 |

### ② 审查前移到生成那一刻（带 `reviewed` 字段）

```
★ 两条来源走不同的路，而字段是判据：
  · 带 reviewed  ⇒ 放行（生成时已审）
  · 不带         ⇒ 必须先审一遍（问过用户、用户裁决过的走这条路）
  ★ 而"不带"不是错误 —— 它是"这条路没走自动生成"的正常状态
```

**而审查问五问**，每问都有今天的事故作为出处：

| 问 | 出处 |
|---|---|
| 写域：inScope 覆盖了它要改的全部吗 | t54 漏了三个文件 |
| 前置：它依赖的东西在不在 | t58 拆成两半而第二半前提不在 |
| 搬运：要搬东西 ⇒ 有核对手段吗 | t70 丢了 4 组接线 |
| 验收：能判真假吗？会恒真吗 | t94 的"恰好落一栏"看不见哪一栏 |
| 越界：outOfScope 挡住了它会碰的吗 | — |

**★ 而每问三态**：`pass` / `fail`（附为什么）/ `unmeasured`（附缺什么）
**★ 而 `unmeasured` 绝不并进 `pass`** —— 那会把"没测到"变成"通过"。

### ③ 大活不进派发池（先拆解）

```
★ dispatchable 的准入是【三条都要】：
  ① to-dispatch（值得做）② 审查通过（带 reviewed）③ 分档是【小档】
⇒ ready · awaitingRuling（大档，★ 是队列不是错误）· rejected · cannotEmit
```

**★ 而分档判定放在生成契约【之前】** —— 因为一条大活的正确处置**不是"再审一遍"，
而是"先拆解"**。

**三条分档信号**（各由一个真实事故教出来）：

```
A 跨多个现有 src 文件          ← t54
B 含【还不存在的】目录条目      ← t70
C 有重组词【且】要搬的东西已存在 ← t39/t30
```

**★ 而实测读数（全台账 94 条）**：`small 78（83%）· large 16 · unmeasurable 0`

**★ 而它如实报了一个抓不到的**：t58 判 `small` 而它确实是三次事故之一 ——
因为它的风险是"某个拆解的第一半而第二半的前提不在"，而那个风险的载体
**不在契约字段里** ⇒ 它写成断言 + 理由，而不是"它应该被抓到"
（后者会让判据去**猜一个它读不到的东西**）。
