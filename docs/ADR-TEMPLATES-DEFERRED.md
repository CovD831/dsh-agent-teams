# ADR · 模板库（线 D）今天不做

```
状态       DEFERRED（不是 Rejected —— 它没有被否掉，是没有开工条件）
日期       2026-10-24
决策       主理人（韩承宇）
相关        四线计划里的 D：flow.yml + EXPERIENCE.md + INDEX
```

## 背景

四线计划里，D 线要建「流程模板库」：用 `flow.yml` 描述一条交付流程有几道关卡、每道关卡挂哪些检查项，配 `EXPERIENCE.md` 与 `INDEX`。目标是"用户能加/删/换检查项而不改代码"。

A（证据链）/ B（软硬配对）/ C（后端能力位）已落地；D 一直没开工。

## 决策

**今天不做实现。** 只把"为什么不做"和"什么条件下才开工"写下来。

## 判据（可机械复核）

```
grep -rn "flow\.yml|flow\.yaml" --include=*.ts --include=*.mjs --include=*.tsx  ⇒  0 命中
```

**今天没有任何代码读 `flow.yml`。** 没有读者，就没有消费者，也就没有验收标准。

⇒ 现在做 D，产出的会是一份**只有写端、没有读端**的目录（`src/templates/`）——
按本项目自己的口径，那是第 11 个「零读者字段」。

这个形态在本仓已经有 10 个现成样本（24 个顶层字段里 10 个在 `src/client/` 零引用）。
**再添一个不是进步，是把同一个病记第 11 次。**

## 为什么不否决它

三条理由，说明它只是「还没到时候」：

1. **需求可能存在，只是还没被表达成代码。** "加/删检查项不改代码"是产品愿景里明写的一条；它没实现，不代表不该实现。
2. **前置件已经到了。** B 线的 `PAIRING` 侧表已经把"每条判据的 soft 说明"外置成数据；`flow.yml` 里"挂哪些检查项"那一格，本质上就是同一个问题的下一步。
3. **成本不对称。** 现在做的成本是"一份无人读的目录 + 后续要迁移"；晚做的成本是"等人想起来"。前者更贵。

## 与既有 `src/profiles.ts` 的关系（这条曾被误判为重复）

| | `src/profiles.ts` | 线 D 的模板库 |
|---|---|---|
| 管什么 | **团队编成**：几个成员、什么角色、`MAX_TEAM_PROFILES = 16` | **流程形状**：几道关卡、每道挂哪些检查项 |
| 数据形态 | 配置键值（`listConfiguredProfiles`） | 声明式流程（`flow.yml`） |
| 变更频率 | 每个团队一份 | 跨团队复用，属于组织资产 |

⇒ **两者不重叠，不该合并。** 但如果将来要合并，合并的方向是"模板里引用 profile"，不是"profile 里塞流程"。

## 开工条件（任一满足即可，且必须可机械判）

1. **出现第一个消费者**
   ```
   grep -rln "flow\.yml" src/ | wc -l   ≥ 1     # 且该处是【读】不是【写】
   ```
   典型形态：`snapshot.ts` 或某个 gate 装配点按 `flow.yml` 决定"这次跑哪几条判据"。

2. **用户明确提出产品需求**，且能写成一条可验收的话（例如"我能在这份文件里加一条检查项，不改代码、重启后生效"）。

3. **B 线的 `PAIRING` 需要第二张表时** —— 如果 soft 说明已经无法只靠"id → 一句话"表达，而需要"关卡 → 多条检查项 → 各自 soft/hard"，那就是 D 的真实起点。

## 反向断言（做什么会破坏它）

> **不许为了"先把模板攒下来"而建 `src/templates/` 目录、或写一份没有读者的 `flow.yml`。**

理由：一旦存在一份 `flow.yml`，"有模板"与"模板生效"在读数上会同形 —— 下一个人会以为它已经在用了，然后去改一个没人读的文件。

**这是本条 ADR 唯一需要执行的部分**，其余都是记录。

## 如果将来开工，第一件事

不是写 `flow.yml`，是**先写它的读者**：
挑一条真实存在的判据（建议 `delivery.review-coverage`），让它的"挂在哪道关卡"由数据决定而不是写死在 `ALL_GATES` 里。

**读者先行，格式后定。** 反过来做，格式一定会被读者的实际需要推翻一次。
