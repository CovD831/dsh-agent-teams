# 聚合入口（真正的主会话）：三级架构与缺口（2026-10-17）

> **用户裁定（逐字要点）**
> 「我需要一个**权限非常大的主会话**,它可以**操纵不同的工作区**。
>  也就是说,我从这个入口进去,它可以帮我在**侧边栏的任何工作区**里面去做事情。
>
>  不过,我们需要**尽可能减少它的上下文**。目前每个 session 都有一个主会话,
>  但我想要的效果是:
>  **1. 聚合入口（真正的主会话）**:我们做一个聚合的入口作为真正的主会话。
>     为了减少它的上下文,它一般来说**不能干太多事情**,
>     需要**把任务交给下一级的 session 主会话**去干。
>  **2. Session 主会话（次级主会话）**:这是下一级的主会话。
>     每个 session 可能都有一个 agent team,session 主会话会把需要干的事情
>     **进一步交给 team 成员**去干。」

---

## 0. ★★★ 最重要的发现:**"读"已经跨工作区了,"写"还没有**

### 读那一侧:已经实现了

```ts
// src/index.ts:405 —— /state 路由
const roots = workspaceRegistry.list().map((workspace) => ({
  workspace: workspace.title,
  stateRoot: join(workspace.path, resolved.stateDir),
}))
const snapshots = await collectTeamsActivity(ctx, roots)
```

★★★ **即:`/state` 【已经遍历所有已注册的工作区】,而 `collectTeamsActivity` 本身就接 `roots` 数组。**

### ★★★ 写那一侧:只认调用者自己的工作区

```ts
// src/tools/shared/entities.ts:275
export function workspaceOf(agent: Agent): string
// ★ 它给出 session.header.cwd —— ★ 即【调用者自己所在的那个工作区】
```
```
★ 而所有工具的落点都由它决定:
   stateRootOf(workspaceOf(caller), config)
⇒ ★★★ 所以:【工具只能操作调用者所在的工作区】
```

⇒ ★★★ **缺口的精确形状:**
```
读:workspaceRegistry.list() ⇒ ★ 全部工作区
写:workspaceOf(caller)      ⇒ ★ 只有自己那个
⇒ ★★★ 所以"从入口操作另一个工作区"现在【做不到】—— 而那正是你要的
```

## 1. ★★★ 而 DSH 的模型解释了为什么

**`dsh-workspace` 逐字:**
> 「A session **joins the project of the directory it runs in**……
>  ★ **A session can only belong to one project.**」

⇒ ★★ **即:会话与项目是 1:N（一个项目多个会话）,而一个会话【只能属于一个项目】。**

★ **而"聚合入口"那个会话本身呢?**
```
★ 它也必须【跑在某个目录里】⇒ ★ 它属于某一个项目
★★ 而它要操作【别的项目】—— ★ 而那在 DSH 的模型里不是默认的
```

⇒ ★★★ **所以"权限非常大的主会话"要做的,是【跨工作区写】—— 那需要我们自己实现。**

---

## 2. ★★ 而"减少上下文"这一条,恰好与架构吻合

```
★ 你的要求:聚合入口【不能干太多事情】,要把任务交给下一级
★★ 而 DSH 的模型:一个会话属于一个项目,它自己的上下文含【那个项目的东西】
⇒ ★★★ 所以"聚合入口不干活"不只是设计偏好 ——
   ★ 它也是【上下文最小化】的必然:干得越多,上下文越大
```

★ **而两级委派映射到【已有的机制】:**
```
聚合入口        ⇒ ★ 派任务给某个工作区（★ 缺:跨工作区写）
Session 主会话  ⇒ ★ 已有的 captain + agent team（★ 完全现成）
```

---

## 3. ★★★ 所以缺的是**一个能力**,而不是一套架构

### 缺的那个能力:工具能【指名工作区】

```
现在:stateRootOf(workspaceOf(caller), config)        ← ★ 隐式,只有自己
要有:stateRootOf(targetWorkspace ?? workspaceOf(caller), config)
      ★ 而 targetWorkspace 来自【显式参数】
```

★★★ **而它带来一个必须一起设计的东西:【权限】。**
```
★ 你说"权限非常大"—— ★ 而"大"要落在【可审计的规则】上，不是没有规则
⇒ ★★ 所以建议:
   · 默认:工具【只认自己的工作区】（现状不变）
   · 显式:一个 `workspace` 参数可以指名【已注册的】工作区
   · ★★★ 而它【必须记在】台账/事件里（谁在什么时候操作了哪个工作区）
```

★ **理由（本仓的纪律）:**
```
★★ "能操作任何工作区"与"不知道它操作了哪个"是【两件事】——
   前者是能力，后者是缺陷
⇒ ★★★ 所以能力与审计要一起上
```

---

## 4. ★ 而"聚合入口"落在哪个槽位（与上一份规格衔接）

```
★ 上一份查清:'main' 是 keyed 且 scope: root ⇒ ★ 可以注册一个【不绑会话】的面
★★ 而聚合入口【需要一个会话】（它要派任务）⇒ ★ 所以它【不是】那个面
⇒ ★★★ 所以两件事要分开:
   · 角色视图（文件夹 ⇒ 工作区 ⇒ 团队）⇒ ★ 一个 main key（不绑会话）
   · 聚合入口（真正的主会话）        ⇒ ★ 一个真的会话（跑在某个目录里）
```

★ **而两者的关系:**
```
★ 角色视图是【看】的（遍历所有工作区,只读）
★★ 聚合入口是【做】的（派任务到指定工作区,要写）
⇒ ★★★ 而"点了某个工作区的某件事"⇒ ★ 角色视图把那个动作交给聚合入口
```

---

## 5. ★★ 所以我的建议：四步,而第一步是**能力**

| 步 | 做什么 | 依赖 |
|---|---|---|
| **①** | ★★ **工具收 `workspace` 参数**（指名已注册的工作区）+ **记审计** | ★ 无 |
| **②** | ★ **`main` key 的最小实验**（不绑会话的面能不能立起来）| ★ 无（与 ① 并行）|
| **③** | 文件夹视图（工作区列表）| ② |
| **④** | 聚合入口那个会话（★ 它是【一个真的会话】,不是槽位）| ①③ |

★★ **而 ① 与 ② 独立,可以并行。**

# ★★★ 追加：最小实验②的读数（2026-10-17，t104）

> **做法**：**只读探针** —— 直接调两个既有导出（`readTeam` / `collectTeamsActivity`），
> 用 `mkdtempSync` 在 `/tmp` 造临时区，跑完删掉。★ **未改任何真实区的任何文件**（连 stamp 都没碰）。
> **判据**：**没有跑真实浏览器 / 真实会话**，读数全部来自库层直调。

## ① 跨区**读**：✅ **通**

```
readTeam(<另一个工作区的 stateRoot>, '<teamId>')  ⇒ ★ 读到了那个队
```
★ 原因（比"能读"更重要）：**`readTeam(stateRoot, teamId)` 读的是
`<stateRoot>/<teamId>/team.json`** —— ★ **它本来就接受任意 stateRoot**，
**与 `workspaceOf(caller)` 无关**。
⇒ ★★ 所以"读别区"在**库这一层**不需要任何新能力；**§0 那条不对称在读取层不存在**。

## ② ★★★ 反向半边 A：**做不到** —— 而根因是**错误码在同一层合流**

```
readTeam(<不存在的区>,      'tX')          ⇒ undefined
readTeam(<存在的区>,        '<没有的队>')  ⇒ undefined
★★★ 两者【同形】
```

**根因（逐字回源，两处都在 `ENOENT` 上合流）：**
```ts
// src/state.ts:640  —— readTeam
catch (error) {
  if (code === 'ENOENT') return undefined      // ★「目录不存在」与「team.json 不存在」都是 ENOENT
  throw error
}
```
```ts
// src/snapshot.ts:831  —— collectTeamsActivity
catch (error) { if (code === 'ENOENT') continue }   // ★ 不存在的区【静默消失】
```

⇒ ★★★ **即：「那个区不存在」与「那个区里没有那个队」在【错误码这一层】就已经合流了** ——
不是返回值写得不好，而是**信息在更上游就丢了**。

## ③ `/state` 那条路**同样**静默跳过不存在的区

```
collectTeamsActivity(ctx, [有效 root, 不存在的 root])  ⇒ 快照数 = 1
★ 不存在的那个【静默消失】 ⇒ 与"那个区里没有队"同形（两者都不产出快照）
```
★ 而 §0 说"读那侧已经遍历所有已注册的工作区"**是对的** ——
★★ 但"遍历到"不等于"**读不到时说得出来**"。

## ④ 三态的现实（★ 而"做不到"是**设计决策**，不是缺陷）

| 情形 | 库这一层给出 | 与谁同形 |
|---|---|---|
| 读到了 | `TeamState` | —— |
| 那个区**没有队** | `undefined` | ★ **与下一行同形** |
| 那个区**读不到** | `undefined` | ★ **与上一行同形** |

★★ **它有两条补救路，而选哪条要人定**（所以这是**决策**，不是 bug）：
```
(甲) 调用方先探目录    —— statSync(stateRoot) 分"区在不在"，不改库
(乙) 给读取函数加返回  —— 让它回"为什么是空的"（区不存在 / 区里没队 / 读不了）
```
★ **本实验到此为止**：选哪条会改变夹具的验收标准，
⇒ **所以夹具（`gate-cross-workspace-read.test.mjs`）等这条决策定了再派。**

## ⑤ ★ 锁：两个锁键都按 `stateRoot` 分 ⇒ 跨区**写**要拿**别的区**的锁

```ts
// src/tools/shared/entities.ts:1135
export function teamLockKey(stateRoot, teamId) { return `team:${stateRoot}:${teamId}` }
export function captainLockKey(stateRoot, captainId) { /* ★ 同形 */ }
```
★ **本实验只读、未取任何锁** ⇒ ★★ **"跨区取锁能不能成"未验证**（那要写，越界）。
★ 如实标注：这一条是**观察**，不是实测。

## ⑥ ★ 一条预警（由 ② 直接推出来）

```
★★ 跨区写时把区名【拼错】⇒ 表现成「那个区没有队」
   —— ★ 而不是「你指错了区」
```
★ 理由：② 已经证明「区不存在」在读取层就是 `undefined`。
⇒ ★★ 所以**跨区写的第一步不是写，而是让"指错了区"这件事说得出来** ——
否则权限越大的入口，**越难发现它操作错了对象**（与 §3「能力与审计要一起上」同一条纪律）。
