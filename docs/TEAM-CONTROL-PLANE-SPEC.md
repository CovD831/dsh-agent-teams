## 2. 三个设计约束（这三条决定成败，不是建议）

### ① 真相只能有一份，且在控制面

harness 持有**会话**；控制面持有**任务**。

绝不能让某个 harness 的 session 状态成为任务真相 —— 否则 N 个后端 = N 份真相，回滚、归因、复跑全部失效。
落地：台账是**文件**（人可读），一次任务一个目录，与你现在 `.agent-teams/` 的形状一致。

### ② 后端只许「报告」，不许「裁决」

后端说：「我改了这 3 个文件」「这条命令 exit 0」「我调了 5 次工具」。
**是否通过，由控制面的判据算。**

理由：你整个体系的信任来源是「裁决可复算」。一旦允许后端自报「完成」，就等于允许它自授权 —— 这正是 `docs/HARNESS-COMPARISON.md:234` 记的「机器不能自授权」那条。

### ③ 每个后端必须过 conformance 套件才能进白名单

同一组 fixture（**一条已知该绿 + 一条已知该红**）在两个后端上必须给出**同一个三态裁决**。

**不过就只是「能启动」，不是「支持」。** 这条不写进代码，这个项目三个月内就会变成一堆「看起来支持」的后端。

## 3. 判据的可移植前提：后端能力位

判据不是「一段话」，是「一组读数」。不同 harness 提供的读数不同：

| 能力位 | 谁需要它 | claude | pi | dsh | 缺失时 |
|---|---|---|---|---|---|
| `reportsChangedPaths` | `dispatch.changed-paths` | 需实测 | 需实测 | ✅（worktree diff） | `unmeasured` |
| `canExec`（回传 exitCode） | `completion.verify-rerun` | ✅ `--allowedTools Bash` | ✅ | ✅ | 判据不得报 ok |
| `exposesToolCalls` | 反事实 / 调用点普查 | ✅ stream-json | ✅ rpc events | ✅ | 该项 `unmeasured` |
| `resumable`（外部 session id） | 长迭代 / 重试 | ✅ `--session-id` | ✅ `--session-id` | ✅ | 只能一次性任务 |
| `isolatesFs` | worktree 隔离 | ✅ 可选 | 需实测 | ✅ | 退化为共享检出 |

★ **这套「声明 + 核对」的机制你已经写好了**：`src/gates/requires.ts`。
它现在描述的是「判据需要哪些 **ctx 路径**」，改成「判据需要哪些**后端能力位**」，是**同一套形状的扩展，不是新机制**。

⇒ 一条判据永远有四种结果，且必须不同形：
```
ok · blocked · unmeasured(缺哪个能力位) · 不适用(本轮没有这条)
```

## 4. ★ 异构 harness 的价值排序（本节是本文最该被记住的部分）

用户问的是「每个成员配不同 harness」。诚实排序：

| # | 用途 | 价值 | 判据 |
|---|---|---|---|
| **1** | **审查独立性**：代码由 A 产出、由 B 审 | ★★★ **真价值** | 破同源盲区。这正是你「对抗性审查 / 反事实」体系的自然延伸 |
| 2 | 能力互补（工具生态 / 速度 / 成本） | ★★ 中等 | 大部分可用「同一后端 + 不同 `--model` / profile」替代 |
| 3 | 并行吞吐 | ★ 低 | 并行靠**任务 DAG + worktree 隔离**，与 harness 无关（你已有） |
| 4 | 「各家能力不同所以都想要」 | ⚠️ **伪需求** | 差异主要来自**提示词与工具集**，不是模型上限；而且一旦 harness 成为可调变量，「这次为什么通过」就不可归因 |

**⇒ 建议：v1 只做 2 个后端，且第二个后端的用途写死为「审查者」，不是「并行 worker」。**

这个结论反直觉，但它是这套体系的内在要求：**异构 harness 的第一用途是审计隔离，不是能力拼盘。**

## 7. 不做什么（明确的非目标）

- ❌ **不做「基于 pi 重写一个 Agent 产品」**。pi 的正确用法是「当库/当后端」，不是「当底座再把你的两万行团队层重写一遍」。
- ❌ **不做 N>2 的后端矩阵**。单人维护，2 个是上限；第 3 个后端进来之前必须先有 conformance 套件。
- ❌ **不做「任意 harness 均可接入」**。见 §3：能力位不全的后端只能是顾问。
- ❌ **不重写判据**。13,004 行一行逻辑都不用改，改的只是它的 `requires` 从 ctx 路径扩到能力位。

## 8. 最大的失败模式（提前承认）

**双后端是这整个方向的唯一价值来源。如果第二个后端一直没接上，这个项目就是纯负债。**

因为单后端时，「控制面」带来的只有可移植性 —— 而可移植性在你只有一台机器、一个工作时，价值接近于零。额外背上的是：进程管理、崩溃恢复、并发、日志、凭据分发。

⇒ **所以实验 A 必须在任何架构重构之前做完。** 它便宜、可逆，且能一次判死这个方向。

## 10. 产品形式建议

**形态：CLI 入口 + 库内核 + 只读看板。不是桌面 App，不是 IDE，不是又一个 runner。**

| 面 | 形态 | 为什么 |
|---|---|---|
| **入口** | `tg check --task <id>` → `PASS / BLOCKED / UNMEASURED` + 证据包 | 能被 CI 调、能被任意 harness 调、能在终端里看 |
| **内核** | npm 包，导出判据与三态裁决 | 别人要嵌的时候有东西可嵌 |
| **看板** | **只读**，看谁在干什么、哪条判据红了 | 你已有 11,310 行 client，先砍到只读 |

**类比（用来对外一句话说清）**：

> 不是「agent 时代的 Vibe Kanban」，是「**agent 时代的 SonarQube / required check**」。
> SonarQube 不管你怎么写代码，只管这段代码能不能进主干；你这套不管 agent 怎么干活，只管它干的活能不能算交付。

这条类比决定了很多默认值：**CI-first、无 UI 也能用、结论可机器读、证据可归档**。

**明确不做**：不做 IDE、不做 agent runner、不做规格生成、不做模型路由。

## 12. 复用策略：不要 fork，要三层薄复用

> 用户问：「是否可以对市面上已有的开源项目做二次开发？」—— 下面逐个判。

### 12.1 三种复用的成本差一个数量级

| 方式 | 你要背什么 | 你的既有教训 |
|---|---|---|
| **fork 源码** | 别人的架构债务 **+ 永久的上游同步** | 你已经 fork 过 DSH：258 个 commit、1,078 行 compat、10 个 host 版本、5 个 harness audit 目录 |
| **依赖库** | 版本约束，但不背架构债 | 可接受 |
| **协议对接** | 几乎为零 | 最优 |

★ **fork 会把你现在的痛苦原样重演一遍**：你现在改 DSH 的痛苦，一半来自「上游会变」；再 fork 一个**停更 6 个月**的项目，等于把「上游会变」换成「上游已经死了」——而后者更坏，因为没人再修它的 bug。

### 12.4 ★ 你真正的问题：「加了，但没接线」

**这不是选型问题，换底座不会消失。**

你自己的 `src/gates/requires.ts` 开头逐字记过那个形态：

```
inScope 缺席 → verify 缺席 → 执行器缺席 → event 名不匹配 → 窗口表没接线
「五次都不是判据本身写错，而是判据要的那一格 ctx 没接上」
```

**换到 Vibe Kanban 的 fork 里，同样的断层只是换了一批名字**（crate 注册点 vs 消费点）。

**⇒ 唯一根治办法：把「接线」变成可机械核对的数据，而不是人记的约定。**

```ts
// 每个模块导出，不是靠文档记
export const manifest = {
  id: 'gate.dispatch.changed-paths',
  provides: ['verdict.changedPaths'],
  requires: ['backend.changedPaths', 'contract.inScope'],
}
```

启动时构图，三条判据全部是**机械的**：

```
provides 无 consumer   → ORPHAN   （红：装了没人用）
requires 无 provider   → UNWIRED  （红：要了没人给）
图里一条边都没有        → EMPTY    （★ 不是绿！沿用你 skippedAll 那条不变量）
```

★ **这套东西你已经发明过一次**，只是它现在寄生在 DSH 插件里：

| 已有物 | 作用 |
|---|---|
| `src/gates/requires.ts` | 声明 + 实测，缺一格就报 `unmeasured` |
| `src/gates/registry.ts:897` `allSkipped` | 「全跳过 ≠ 都通过」 |
| `scripts/gate-producer-consumer.test.mjs` | producer/consumer 对齐 |
| `scripts/gate-input-wiring.test.mjs` | 输入接线检查 |
| `docs/ORPHAN-AUDIT.md` · `docs/OUTPUTS-CONSUMER-AUDIT.md` | 孤儿与无消费者的普查 |

⇒ **把它抬成控制面的「启动自检」，这类痛苦就永久消失。** 这是本项目最该复用的东西——而它是你自己的。

### 13.3 ★ 一个更根本的顺序问题：你要的「低代码」其实是「流程是数据」

你自己说过：

> 「比如我现在喜欢在某个地方加一个什么审核或者测试，以后可能就变了，
>  可能变成另外一个审核或者干脆不要了。」

**这句话说明流程还在演化。** 而低代码画布的价值是「让不改代码的人改流程」——你是写代码的人，改一行 YAML 比拖三个节点快。

更关键的是顺序：

```
先做画布  ⇒ UI 的数据格式被画布的交互绑架；换一种流程就要迁一次数据结构
先做数据  ⇒ 画布只是这份数据的一个视图，随时能接、随时能换
```

**⇒ 正确顺序：流程先落成数据（DSL），画布后置。**

一旦流程是数据，三件事同时成立：
- 加一个审核 = 加一行配置
- 换掉审核 = 改一行
- 将来要画布 = 画布是这份 DSL 的编辑器，不是它的定义者

**这也是你已经做过的事**：`gates` 的「固定插入点 + 可插拔判据」，本质就是「骨架是代码，节点是数据」。
你缺的不是低代码平台，**是把这套模型从「判据」扩到「流程节点」**。

### 13.4 ★ 队长 BOT 与低代码画布是两个范式，必须分层

| | 低代码画布 | 队长派活 |
|---|---|---|
| 谁决定下一步 | **人**（预先画好） | **agent**（运行时判断） |
| 图 | 静态 | 动态生成 |
| 适合 | 交付流程的**骨架**（需求→计划→实现→审核→交付） | 骨架内部的**组队与分工** |

把它们塞进同一层一定会打架。正确的结构是**两层**：

```
外层（人画的骨架，可插拔节点）  ← 低代码画布管这一层
   └── 每个节点内部（队长动态组队）  ← agent team runtime 管这一层
```

### 13.5 推荐路径（三步，每步都能独立验证）

| 阶段 | 做什么 | 验收 | 时间 |
|---|---|---|---|
| **① 流程 DSL** | 把「需求→计划→实现→审核→交付」写成 YAML，节点声明 `requires/provides`（复用 §12.4 的 manifest） | 改一行 YAML 就能插入/移除一个审核节点，且 ORPHAN/UNWIRED 自检通过 | 2–3 天 |
| **② CLI 跑通** | `tg run --flow flow.yml --task <id>`，节点内部调 harness（ACP/pi） | 一条真实任务从需求走到交付，证据包完整 | 1 周 |
| **③ 画布后置** | 二选一：<br>(a) **Langflow**（MIT）当外壳，节点是 20 行薄壳、POST 到本地 `tg` 服务<br>(b) **React Flow**（MIT，Langflow 底层同款）自建画布 | 在画布上拖一个节点就能改变 ① 的 YAML | 看 (a)/(b) 选择 |

**为什么 (a) 不是「拿来就能用」**：Langflow 的节点是同步 Python 函数，而你的任务是**几十分钟到几小时**的长时执行，还要 worktree 隔离与人工审批卡点。你只会用到它 30% 的能力，却要背它 100% 的运维。
⇒ **只有当「前端打磨」真的成为瓶颈时，才值得走 (a)。**

## 14. ★ 预设 vs 自决：流程配置的边界判据

> 用户原话（2026-10-23 00:03）：
>
> 「低代码平台是我最终的想法，但目前我们肯定要先把产品本身做好。
>  我想要的流程替换，其实是让每个人都能按照自己的开发流程，去设置一个团队的运行流程。
>  1. **预先定义的低代码模块**：根据需求去拆解、拆解成什么样，这些流程需要预先定义好。
>     比如在什么地方加测试、什么地方需要审核，这些是我希望通过低代码模块去拖拽设定的**预设内容**。
>  2. **执行期间的动态流程**：真正执行时，派发什么任务、中间可能不止一个回合的交互，
>     这些都是执行期间根据不同的任务**自我决定**的。
>  也就是说，**低代码的开发习惯和过程沉淀，其实只是一些可以预设的东西**。」

### 14.1 ★ 两种切法：谁决定 vs 什么时候决定

§13.4 讲的是**谁决定**（空间分层：人画的画布 / 节点内部的队长）。
用户这次补的是**什么时候决定**（时间分层：预设期 / 执行期）。

**两者正交**，而且必须同时成立：**人预先定下检查点，agent 运行时自己决定怎么过。**

| | 预设期 | 执行期 |
|---|---|---|
| 谁定 | **人**（写下来、可拖拽、可分享） | **agent**（按任务内容决定） |
| 内容 | 拆解成什么样、哪里加测试、哪里加审核 | 派什么任务、派给谁、几轮交互、先改哪个文件 |
| 形态 | **数据**（可版本化、可导入导出） | **运行时决策**（不可预先写死） |
| 价值 | 把「开发习惯」沉淀成资产 | 把「任务差异」留给 agent |

**⇒ 低代码拖的从来不是「步骤」，是「检查点与产出模板」。** 这个区别决定产品天花板：拖步骤会变成一张永远对不上现实的图；拖检查点则永远成立。

### 14.2 ★ 一条可操作的判据

> **「能不能在不知道任务内容的情况下，把它写下来？」**

| 说法 | 能在不知道任务时写吗 | 归类 |
|---|---|---|
| 「交付前必须有独立审查」 | ✅ 任何任务都成立 | **可预设** |
| 「实现完成后必须跑 verify 命令，且退出码为 0」 | ✅ | **可预设** |
| 「拆解必须产出 ≥2 个可独立验收的子任务」 | ✅ | **可预设** |
| 「先改 `config.ts` 再改 `index.ts`」 | ❌ 依赖具体任务 | **不可预设** |
| 「这个任务要派 3 个人」 | ❌ 依赖任务规模 | **不可预设** |
| 「第 2 轮交互时应该质疑上一轮的结论」 | ⚠️ 只能预设**规则**（「每次审查必须给反例」），不能预设**轮次** | **预设规则，不预设序列** |

⇒ 这条判据同时防住了两种错：
- **过度预设**（把动作序列写死）→ 流程一遇到不同任务就废
- **预设不足**（什么都不写）→ 退化成「看 agent 心情」，无法沉淀

### 14.3 ★ 你的流程配置模型已经存在：`插入点 × 判据`

不需要发明流程引擎。你现在这张表就是它：

```
INSERTION_POINTS = admission · contract · dispatch · completion · delivery · runtime
判据             = 17 条，各自声明 appliesTo / requires
```

**「让别人配置自己的开发流程」= 让人编辑这张表：**
- 换一条判据（换审核方式）= 换注册清单里的一行
- 加一条判据（加一步测试）= 新增一个文件 + 一行装配
- 低代码画布 = 这张表的可视化编辑器

⇒ **产品化的工作量不在「造引擎」，在「把这张表变成数据 + 给它一个编辑器」。**

### 14.4 ★ 一个真实张力：固定插入点 vs 用户自定义阶段

用户要「每个人按自己的流程」，那么必然有人想要**自己的阶段名**（设计评审、灰度、回归…）。

但你的机制优势恰恰来自**插入点固定**——固定 7 个点，注册表才能机械核对「这个点有哪些判据、有几个被跳过」。

**解法：两层插入点。**

```
内核固定点（不可删，保证底线）
  admission · delivery          ← 进场与交付，删了就没有门禁
  runtime                       ← 全程告警
用户阶段点（可增删）
  每个阶段必须声明 parent: <某个内核点>
  ⇒ 阶段可以自由命名，但它挂在哪个内核点上必须显式
```

这样：
- 用户能加自己的阶段（满足「按自己的流程」）
- 「全跳过 ≠ 都通过」的不变量仍然成立（因为每个阶段都有父点）
- 删阶段不会把底线一起删掉

★ **判据：任何用户自定义的东西，必须能回答「它的父点是谁」。答不出来就是装饰，不是流程。**

### 14.5 这句话把 D1 改判了

原 D1 是「先只给自己用」。用户这句「**让每个人都能按照自己的开发流程**」把它改成了：**产品要面向他人配置**。

随之而来的四件事（不是小功能，是产品复杂度的大头）：

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **流程模板可移植** | 别人的流程要能拿走、能装进来 ⇒ 纯数据、无绝对路径、无本机依赖 |
| 2 | **版本与迁移** | 模板会演进；旧模板在新内核上必须能判断「还成立吗」 |
| 3 | **导入导出与冲突** | 两个人改了同一份模板要能合 |
| 4 | **配置错误的可诊断性** | 别人配错时不能静默通过 ⇒ 复用 §12.4 的 ORPHAN/UNWIRED |

⇒ **D1 从「自用/发布」的二选一，变成「先自用验证，但数据结构必须按可分享设计」。**

## 15. ★ 真正的价值主张：不是「管 agent」，是「让流程可固化」

> 用户原话（2026-10-23 00:09）：
>
> 「虽然现在写代码很方便，但由于各种各样的漂移，或者跳过一些不严谨的交付，
>  想实现一个自己想象中的产品其实还是不容易的。**因此，很多人无法固化自己的开发流程。**
>  如果一个人无法固化自己的开发流程，他可能更多的是在接受别人的输入。
>  别人说这边用某个提示词做审核效果很好；明天又刷到这边加某个流程效果会更好。
>  他可能想不断地做尝试，但**如果没有一个工具能让他快速地去替换和固化，这种尝试就很难延续下来**。
>  而且就算延续下来，也还是每次手动操作，无法固化。
>  所以我想提供这样一个平台，**让每个人都能很简单地去定制和固化自己的开发流程**，
>  去应用实践自己接收到的信息。」

### 15.1 ★ 这句话把产品从「效率工具」挪到了「能力沉淀工具」

```
卖效率（60 个 runner 都在做）  →  跑得更快、并行更多   →  红海
卖能力沉淀（没人做）          →  你的流程能被固化成资产 →  空白
```

**⇒ 一句话定位（对外）**：

> **流程的 git + A/B 测试。**
> git 让代码可版本化；这个东西让**开发流程**可版本化、可替换、可评估。

### 15.2 ★ 为什么「固化不了」——拆成三层，缺一层就断

| 层 | 缺它会怎样 | 市面现状 |
|---|---|---|
| **① 可存** | 技巧散在推文/聊天/repo 里，看完就忘 | 笔记工具能存，但存的是文字，不是可执行的关卡 |
| **② 可换** | 换一个审核方式要改代码 ⇒ 试错成本高 ⇒ **不试** | 低代码平台能换，但换的是「LLM 调用图」，不是「交付关卡」 |
| **③ 可判** | 换了之后不知道有没有变好 ⇒ 无法决定留还是扔 | **★ 没有任何工具做这件事** |

**⇒ 老板独有的资产正好是第 ③ 层。** 你仓库里已经有它的形状：

```
FlywheelReading { verdict: promote | observe | archive | unmeasured
                  confidence: number | undefined
                  reasons: string[] }
```
（`src/confidence.ts:153` `FlywheelReading`；`src/evaluator/` 三文件 `effect.ts` / `score.ts` / `types.ts`；`docs/EFFECT-MEASUREMENT-RESEARCH.md`）

**⇒ 产品不是「流程配置器」，是「流程的实验室」。** 这是它和所有低代码平台的根本区别：**别人让你配，你还能告诉你配得对不对。**

### 15.3 ★ 插入点该不该开放？—— 判据是「上下文可得性」

用户问：「甚至连插入点都可以允许用户自定义吗？」

**我的判断：v1 固定，不要开放。** 理由不是「怕复杂」，是**技术上会失效**：

```
一个插入点 = （生命周期的某个时刻，该时刻可获得的上下文）
判据        = 需要某几格上下文才能判
```

若允许用户凭空造一个时刻，他就能在一个**没有上下文的时刻**挂一条**需要上下文的判据**
⇒ 那条判据永远只能报 `unmeasured` ⇒ 用户配了，但没用，**而这正是他要解决的那个病**。

**⇒ 插入点的自由度，上限就是上下文的颗粒度。**

所以：

| 版本 | 插入点 | 理由 |
|---|---|---|
| **v1** | **固定**（沿用现有 6–7 个） | 保证每条判据都能拿到它要的格 |
| v2 | 允许在固定点之间插「子检查点」，**必须声明读取哪个固定点的上下文快照** | 有扩展空间，但不破坏可判定性 |
| 永不 | 凭空造时刻 | 会造出永远 `unmeasured` 的装饰 |

### 15.4 ★ 给用户的心智模型：不是「插入点」，是「关卡」

「插入点」是实现细节，用户不需要知道。用户看到的是：

```
立项 ✓  →  计划 ✓  →  实现 ✓  →  审查 ✓  →  交付 ✓
        每道关卡上可以挂检查项；关卡位置不变，挂什么可以换。
```

这个心智模型和开发者已有的经验同构（pre-commit → CI → PR review → release gate），
**不需要教学**。而且它天然传达了一件重要的事：**关卡位置稳定，检查项可迭代。**

### 15.5 用户循环（这就是产品的核心交互）

```
刷到一个技巧
   ↓ ① 存                    ← 变成一条「检查项」（含判据 + 验收条件）
   ↓ ② 挂                    ← 拖到某道关卡上
   ↓ ③ 跑 N 次               ← agent 照常干活，关卡自动执行
   ↓ ④ 看读数                ← effective / ineffective / unmeasured
   ↓ ⑤ 留或扔                ← 有效则 promote，无效则 archive
```

**这个循环 = 你 `confidence.ts` 里那套 flywheel 的形状，只是从「你自己的仓库」变成「任何人的流程」。**

⇒ 所以这件事**不是从零造产品**，是**把你自己已经跑通的飞轮，从私有变成通用**。

### 15.6 诚实的依赖链（这个产品的地基在哪）

```
流程可固化
  ← 取决于「换了之后能判」
    ← 取决于「判据能拿到读数」
      ← 取决于「后端能提供 changedPaths / exitCode / toolCalls」
        ← 取决于 §3 的能力位 + conformance
```

**⇒ 能力位那件事没做成，「流程实验室」就退化成「流程配置器」，和几十个低代码平台没区别。**
这是整条链上唯一不能省的一环。

### 16.4 ★ 一个必须承认的结构性限制

**「流程实验室」只对高频用户成立。**

**必须明确先服务哪一个**，否则默认值会两边都不讨好。

## 18. ★ 软硬配对：把「用户只写软的」变成可机械检查的不变量

用户 J5 说的是一个很具体的产品机制。它在你仓库里**已经有半成品**。

### 18.1 已有的那一格

```ts
// src/evolution/types.ts:189-193
export interface RoutingDecision {
  readonly needChange: boolean
  readonly modality: 'hard' | 'soft' | 'contract' | 'none' | 'unmeasured'
  readonly why: string
}
```

注释逐字：**「能否机械判定？能 ⇒ hard（加/改一条判据）；不能 ⇒ soft（改 prompt / profile）」**

⇒ **「软约束 / 硬约束」不是新概念，是 `modality` 的两支。** 产品化只是把它从「采集模块的内部类型」提到「用户可见的检查项」。

### 18.2 产品化的形状：成对表 + 三态

**每一条检查项必须成对存在：**

```
soft  提示词片段   ← agent 看得到，知道「为什么要这么做」
hard  判据         ← 机器能判，决定「算不算做到了」
```

三态（不许合并）：

| 态 | 含义 | 怎么办 |
|---|---|---|
| `paired` | 软硬都有 | 可以挂到关卡上，计入「已固化」 |
| `soft-only` | 只有提示词，没有检查 | **不算固化**，只是建议；读数永远 `unmeasured` |
| `hard-only` | 只有检查，没有说明 | 有**误伤风险**：agent 不知道为什么，会反复撞同一堵墙 ⇒ 要求补 `why` |

### 18.3 为什么两边都不能少（这是判据，不是偏好）

- **只有软** ⇒ 没有强制点 ⇒ 它就是 skill，不是门禁。**这正是你说的「skill 扛不住硬约束」。**
- **只有硬** ⇒ `requires.ts` 开头那条原则成立：**「判据误伤的代价比漏报更贵」**。
  agent 不知道规则存在，就会在同一个地方被拦十次，然后人把判据关掉 —— 判据死于此。

### 18.4 AI 生成硬检查时的硬约束（承接 §3）

`REQUIREMENTS.md §3` 的裁定是：**`src/evolution/` 里没有任何函数能改判据 —— 刻意不提供。**
（理由引 STOP 的两文件设计：**"一条只禁止调用的注释会腐烂，没有那个函数则不会"**）

⇒ **AI 可以生成硬检查，但只能进「待审」队列**，必须：
1. 人确认（不是 AI 自确认）
2. **过一条已知该红的反事实 fixture**（`discriminating-power-test` 的判据）

两条都过才进白名单。**否则 AI 生成判据这件事，就等于给机器开了自授权口子。**

### 18.5 这一节对 J4（默认流程）的直接含义

默认流程要「结构简单」，而软硬配对给它一个客观的「简单」定义：

```
默认流程的每条检查项都必须 paired，且总数不超过 N
（N 建议 3–5：超过这个数，用户第一次用就会关掉一半）
```

**⇒ 「简单」不是感觉，是「可数的检查项 + 每条都成对」。**

你记忆里的「评估这部分是有的」，精确说是：**判据写对了、测过、但零消费者**。
飞轮那四个状态（`promote/observe/archive/unmeasured`）判得对，**却从来没有真实数据喂进去过**。

★ 这恰好是你说的那个痛点的又一次复现：**「加上去了，但没接线」—— 连自迭代这条线本身也是这个形态。**
所以这不是「你某个模块没做好」，而是**这个形态会反复出现，除非接线被机械化核对**（§12.4）。

**② 真正值钱、可搬走的是三样「语义」，不是三份代码：**

```
三段式缺席语义：没问过 / 答不了 / 答了（这是全仓最值钱的一条，别丢）
五态分流：hard / soft / contract / none / unmeasured
三态收益：improved / unchanged / unmeasured
```

这三样是**设计资产**，换语言、换宿主都不变。函数本身（`effectReadingOf` 等）反而要重写。

**③ 断点 A 与断点 B 不是缺零件，是缺调用点。**

```
断点 A：提案 → 任务    （createTaskParamsOf 定义了，没人调）
断点 B：评估 → 晋升    （读数算了，没接到任务完成上）
```

⇒ **产品的 MVP 不是画布，是这两条调用点。** 接通了，闭环就活了；不接，做多少 UI 都是死的。

### 21.4 这对后端契约的含义（本轮最重要的产物）

`gate-tally.ts` 现在记的是 `{ at, point, gate, verdict, by }` ——
**它能算「哪条判据被求值/拦下几次」，但答不出「点开看这一次的证据」**。

⇒ 需要一个 **`evaluationId`**。形状**待定**，两个候选：

| 候选 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| 一维 | `ev-00NN`（同 signal id 的分配法） | 简单、可 grep | 不携带语义 |
| 三元组 | `(taskId, attemptId, gateId)` 复合 | 可从任一维度反查 | 需要拼接时处处一致 |

★ **先不急着定**：UI 的追溯链怎么设计会反过来决定字段形状。这正是「原型先于契约」的价值 ——
一个 399 行的静态页面，把一个后端字段的缺口逼出来了。

### 21.4b ★ 修正：不是一个 id，是**两条反向引用**

§21.4 我列了「一维 `ev-00NN` vs 三元组」两个候选。**原型的第二次迭代推翻了它**：

```
一个事件可能触发多条检查（一次 gate.evaluated 跑 17 条判据）
一条检查可能被多个事件佐证（verify 重跑、CI 结果、人工审查）
⇒ 这是【多对多】，不是一个标识符能表达的
```

⇒ 需要**两条反向引用**：

| 方向 | 字段 | 谁写 | 回答什么 |
|---|---|---|---|
| 检查项 → 证据 | `evidence_ref` / `triggering_event_id` | 判据求值时 | 「这条为什么红了」 |
| 事件 → 它产出的检查 | `produced_check_ids[]` | 事件落盘时 | 「这一次求值影响了什么」 |

**页面只是渲染器，真正的绑定在数据层。** 没有这两条，"链"在真实运行里会断 ——
尤其是**「谁主谁次」页面决定不了**（一个检查被三个事件佐证时，哪个是主证据是数据问题）。

★ 这条与全仓的老纪律同源：**关系必须显式，不能靠命名约定。**

### 21.4c ★ 产品形态推论：默认视图应该是「待你决策」，不是「运行态」

产品形态已定为「**一个队长跟人对接，其余成员不归人管**」（用户原话）。
按这个形态推论：

```
人打开看板的第一诉求不是"系统在跑什么"，而是"要我做什么"。
⇒ 默认视图 = 待你决策的队列；运行态是第二层。
```

因为**一切正常时人不需要打开看板**。人只在需要做决定时打开。

⇒ 原型已加两个 tab（`待你决策 3` / `运行态`），默认停在第一个。
**这是产品定位级决定，留给你拍，不替你定。**

### 23.1 「投影 vs 第二份真相」判据（终裁）

一句判据：

```
一条读数改完之后，如果不去重算它，会不会自己变？
  会变 ⇒ 它是投影（可以现算、可以放在容器里）
  不变 ⇒ 它是第二份真相（必须删掉一个）
```

| 东西 | 性质 | 处置 |
|---|---|---|
| `evolution/gate-tallies.jsonl`（每次求值追加） | **流 = 真源** | 唯一真相 |
| `readouts.evidence` | **投影**（按任务过滤 + 聚合） | 可以建，**只读不存**，每次现算 |
| `task.gateEvaluations` | 另一个投影（按任务切片） | **不再扩展**：不写新字段，只保留只读兼容 |

**两条硬约束（写进线 A 的任务卡）：**

★ 这条判据的价值不在"证据存哪"，在它把两难题消掉了：**"两份真相 vs 多一次读盘"的取舍，在"只读不存"下不成立。**

### 23.3 「已驳回」必须可查（机制建议）

**问题（实测）**：`registry` 的 blocked/unmeasured 不收 `outputs` 这条，**2026-10-21 已裁并撤回** —— 证据留在 `scripts/gate-registry.test.mjs:266-283` 的**注释**里，并由 ⑭（`:248`）/ ⑭b（`:263`）两臂钉住。两天后它又被当成"核心缺口"报上来。

> 根因不是谁记性差：**"已驳回"没有被记在一个会被查的地方。** 它只活在一条测试的注释里 —— 而注释不参与任何检索。

**建议**：`docs/REQUIREMENTS.md` 新增一节「已裁定不做」，固定**六**列：

| 提案原文（一句） | 驳回日期 | 驳回理由（一句） | 钉住它的夹具 / 判据 | 做什么会破坏它 | 重开条件 |

★ **第六列「做什么会破坏它」是本表的关键，不是补充说明。**

一条驳回如果只记"不做"，它挡不住**变形的重提** —— 下一个人换个角度再来一次，表里查不到，因为他的措辞不一样。而记下"**做什么会破坏它**"，就能在**行为层面**挡住：

```
⑭b 的写法就是范式（scripts/gate-registry.test.mjs:263-320）：
  ①「blocked 时 outputs 必须深等于 {}」          ← 说"不做"
  ②「通过时同一批字段必须进 outputs」            ← 说"做什么会破坏它"
```

第 ② 臂的作用不是重复第 ① 臂，而是**堵死一条恒绿的实现方式**：如果只断言"恒不收"，那么"把 outputs 整个废掉"也能通过。⇒ **只记"不做"的驳回会被绕过去；记了"做什么会破坏它"的驳回绕不过去。**

**五条硬要求：**

1. **固定列，不许自由格式。** 自由格式的裁定表三个月后没人读得懂 —— 同 §21.5 的教训。
2. **"钉住它的夹具"必填。** 一条驳回若没有任何测试钉住，它**一定会再回来**。⑭ / ⑭b 就是正样本：不只记了"不做"，还把"为什么不做"和"反向半边"都钉在一臂里。
3. ★ **"做什么会破坏它"必填，且必须是一条可执行的反向断言。** 不接受"注意别破坏"这类话 —— 那句话没有执行点。只有"不做"没有"破坏条件"的驳回，等于没驳回（见上文第 ② 臂）。
4. **"重开条件"必填。** 让下一个人知道"什么变了就可以再提"。"永不"可以写，但要说清凭什么是永不。
5. ★ **进排期前必须查这张表，且这件事要机械化。** 建议在 `scripts/requirements-claims.mjs` 一系里加一条核对：新提案文本与表中"提案原文"做**关键字重合**，命中即报 `疑似已驳回`。

**为什么第 5 条不能靠自觉**（本仓已有先例）：t77 把对照对数据放进 `scripts/fixtures/falsification-pairs.json`，那份 JSON **从未被提交** ⇒ 于是腐烂了，两次普查都写着早已退役的判据（`scripts/gate-falsification-pairs.test.mjs:47-52` 逐字记着这件事）。

> **一张不被机器查的表，就是一张会腐烂的表。** 这与本文 §1.3 记录的是同一条：结论会过期，只有能被重跑的东西不会。

| | C（已选） |
|---|---|
| ✅ 解决 | 「陈旧性无人声明」—— 读到 `tag < 当前 revisions.length` ⇒ 可判"这份裁决来自上一版契约" |

##### ③ 次序成立（所以不需要新时钟）

```

amend-task.ts:71   Object.assign(task, result.task)   ← task.revisions 此刻已是新长度

```

##### ④ 陈旧必须**三态**，不许合成一个布尔

`rejectOnContractGates` 的成功返回是（`src/tools/shared/entities.ts:5691`）：

```ts

```

⇒ **`amend` 可能跳过 contract 求值**（`amend-task.ts:109` 的 `if (amendContractSurface !== undefined)`）：契约改了、`revisions` 长了，而 `contract` 的 tag 没长。

| 情形 | 含义 | 补救动作 |
|---|---|---|
| `tag === 当前` | 新 | 无 |
| `tag < 当前` **且该次 amend 无求值记录** | ★ **未重检**（改了契约没再查） | 去补求值，或去查为什么没求值 |
| `tag < 当前`（曾重检） | **陈旧** | 重跑 contract |

★ 三者**补救动作不同**（前者去接通路、后者去重跑），合成一个布尔就会让"这条路断了"与"该重跑了"同形 —— 本仓最忌的那种合流。

**★★ 关键：这一支今天不执行。** 当前树走 **spy 分支**（实测日志 `臂9 ▸ spy 分支（主实例空闲槽位 = evidence）`，判据是"主实例上还有空槽位"）；四槽被占满才切**保真分支**。⇒ 它与原版那颗雷**同一时刻激活**，只是从"臂变红"退化成"**一条从没跑过的分支变红**"。

#### ★★★ 更正 3（我的判断，不是他的）：这一支**替一个待裁定问题先做了决定**

`src/readouts.ts:111` 逐字：

> `now`：没有证据表明四条线需要**同一个钟**；先不放，需要时再加（**同样要裁定**）

⇒ 臂 9 保真分支要求"同一 context 两次调用值相等"，**等价于禁止 provider 读墙钟**。而"`ReadoutContext` 要不要给 `now`"是一个**明确挂着的待裁定项**。

**⇒ 夹具在一个未裁定的契约问题上先替契约做了决定。** 这正是"夹具替契约做承诺"——夹具不该承担这个。

| 方案 | 内容 | 代价 / 前提 |
|---|---|---|
| **A** | 把"provider 不得依赖时间（同 context ⇒ 同值）"写进契约，并**同时裁定 `now` 不进 context** | 便宜，一条契约文字；代价是永久禁止读数带时间戳 |
| **B** | `now` 变成**组装入参**：快照采样一次、把同一个 `now` 传给两次调用 | ⚠️ **不是"context 加一格"**，见下 |
| **C** | 臂 9 比键集 + 允许一份**显式声明的易变字段清单** | 最弱，且"易变清单"本身要维护 |

★★ **B 不是 A/C 的平行选项 —— 单独改 context 不成立（readout-architect 指出，我复核代码后确认）：**

臂 9 做的是**两次独立调用**：

```ts
const expectLive = await at(false, root)        // 第一次：直接调 collectReadouts
const live = await snapshotOf(root)             // 第二次：走快照，内部再调一次
```

⇒ 即便 `now` 进了 `ReadoutContext`，**两次调用会各自采样一次** ⇒ 数值仍不同 ⇒ **仍红**。

⇒ 夹具实际裁定的不是"`now` 不进 context"，而是"**时间不得影响读数**"。
⇒ B 要成立，前提是 `now` 由**快照组装层采样一次并传给两次调用**（而不是 context 里多一格）—— 那比"加一格"大得多，且要动 `assembleTeamSnapshot` 的签名。
⇒ **实际候选收敛为 A 或 C。** 若有人选 B，他会在改完 context 后发现仍然红。

★ **我不拍板**（这是契约取舍）。但**必须选一个**：现状是"夹具已经选了 A，而契约上写着'要裁定'"。

##### ★★★ 它必须记成「未裁的契约」，不是「未修的 bug」（一字之差，决定它会不会被记下来）

有人会把它归类为"一个未修的断言缺陷"，那会导向"改断言就完事"。**那个归类是错的，理由如下：**

```
若它是「未修的 bug」⇒「修」的动作就是改断言
                    ⇒ 而改断言 = 裁定"provider 不必确定"
                    ⇒ ★ 这个裁定发生了，却不会被记成裁定
```

⇒ **"修 bug"这个动作本身完成了一次契约裁定，而它不会出现在任何裁定记录里。** 这正是本仓 §23.3 要防的那件事：**决定发生了，但没人知道它是个决定。**

⇒ 所以它必须进"待裁"队列，而不是进"待修"队列。**这两个字的差别不是措辞讲究，它决定这个决定会不会被记下来。**

★ 顺带：这也解释了为什么 §23.3 那张"已裁定不做"的表要机械化 —— 如果它只靠人记，那么"修一个 bug 顺手做的裁定"永远不会被写进表里。

#### 新增 4：M7 / M8 的守卫状态，以及两者在"测不了"时含义**相反**

夹具头部的变异表逐字：

```
M7  snapshot 里 historic 恒 false   ⇒ 臂 9（spy 分支）红
M8  snapshot 里 stateRoot 传空串    ⇒ 臂 9（spy 分支）红
```

**这一格我改过两次，逐次记下来（因为每次都比上一次更坏）：**

| 我写过的说法 | 为什么被推翻 |
|---|---|
| ~~「M8 悬空（owner 交接给空位）」~~ | 错：守卫存在，只是有条件 |
| ~~「M8 是条件性守卫」~~ | ★ **仍然错，且错得关键**：条件不是"provider 读不读盘"，而是"**夹具的 root 里有没有 `team.json`**" |
| **「M8 在真实 provider 写法下恒免检」** | ← 当前结论 |

##### ★★★ 根因：夹具的 root 是一份**空** durable 根

```
夹具 makeRoot：
  mkdtempSync(…)                         ← 临时根
  mkdirSync(join(root,'t1','inbox'))     ← 只造 inbox
  return root                            ← ★ 不写 team.json（grep -c team.json ⇒ 0）

readTeam：readFile(join(stateRoot, teamId, 'team.json'))   ← src/state.ts:632
          ENOENT ⇒ return undefined                        ← :640-641
```

⇒ 任何**真实写法**的 provider（`readTeam(ctx.stateRoot, ctx.teamId)`）在这个 root 上**都拿到 `undefined`** —— 无论 `stateRoot` 是对的还是空串：

| provider 写法 | 正确 root 与空 stateRoot 的读数 | M8 变异能否被抓 |
|---|---|---|
| `readTeam(…)` 后取 `.tasks.length`（抛 TypeError） | 同一条错误 | ❌ **9/9 绿** |
| `readTeam(…)`，`undefined` 时返回 `{unmeasured:'no team.json at that root'}`（**最规范的写法**） | 同一句 `unmeasured` | ❌ **9/9 绿** |
| `readFile(join(stateRoot,…))` 让它抛 ENOENT（**消息里带完整路径**） | 两份不同（路径不同） | ✅ 8 pass / 1 fail |
| 硬编码路径 / 不读盘 | 恒定 | ❌ 抓不到 |

★★ **越是写得好（读不到就返回 `unmeasured` 而不抛），越抓不到。** 因为 `unmeasured` 消息里没有 `stateRoot`，两格退化成同一句话 ⇒ 差分判别力 = 0 ⇒ 打印"stateRoot 无 ⇒ 测不了" ⇒ **免检**。

⇒ 所以不是"有时能抓有时不能"，是**在真实 provider 写法下恒不能抓**。

##### ★ 修法：补数据，不是找 owner（一行）

```ts
// 在 makeRoot 里加一行
writeFileSync(join(root, 't1', 'team.json'),
  JSON.stringify({ id: 't1', name: 'probe-team', phase: 'running', members: [], tasks: [], taskSeq: 0 }))
```

readout-architect 四种组合实测：**基线仍 9 pass（无副作用）／M8 变异下 8 pass / 1 fail（抓到了）**；臂 9 自述从 `stateRoot 无（测不了）` 变成 `stateRoot 有（已对拍）`。

★ **这条改了我对 owner 表的结论**：M8 不需要"owner 交接"，需要**先补数据**。
★ **但"补数据之后恒有效"这句话我说过头了，就地更正**：它只在"**至少一条 provider 合法地读团队盘**"时成立。若四条线合法地都不读（`backends` 探环境、`templates` 读配置、`pairing` 读判据表），补了 `team.json` 仍然无判别力。

⇒ **所以 M8 的 owner 只能是第三样东西：`readoutContextOf(team, stateRoot, options)` 纯函数。**

| 方案 | 内容 | 判断 |
|---|---|---|
| **A** | `makeRoot` 写 `team.json` | ✅ **必要**（空 durable 根就是坏夹具），但**不充分** |
| **B** | 指定某条线的 provider 读 `stateRoot` 并在读数里暴露它 | ❌ **测试驱动生产**，见下 |
| **C** | 抽 `readoutContextOf` 纯函数，臂直接断言它的输出 | ✅ **唯一不依赖 provider 行为的 owner** |

★★ **为什么 B 要拒绝**：M8 要证的是"**快照把正确的 `stateRoot` 传下去了**"，这件事与 provider 读不读它**无关**。用 provider 当探针，是用"有没有人受影响"反推"传下去的值对不对"—— 间接证据，且会被合法的实现选择推翻（本轮反复踩的就是这个：**同一夹具，换一种合法写法就从"抓到"变"抓不到"**）。

★ 更具体的反例：`{ root: context.stateRoot.length }` 能让两格不同，**是因为它把 `stateRoot` 本身当成了读数**，不是因为读数真的来自那个目录。这种字段对 UI 无意义。
★ 而"线 C 探的是环境能力，本来就要知道在哪个环境"这个理由**用了 `stateRoot` 代替 `workspace`** —— 而 `src/readouts.ts` 明确把 `workspace` 排除在 context 外（"它是显示名，测量不需要它"）。⇒ **"在哪个环境探"这件事，今天在 context 里没有对应那一格。**

★ ★ **一句原则**：**夹具的 root 应该是一份真的、可读的 durable 根，而不是空目录。** 空目录会让"读不到"与"读的地方不对"同形 —— 而这正是本仓记账最久的形态。

##### ★★★ 再深一层：光"有 team.json"不够，**投影的那一维必须非空**

readout-architect 2026-10-24 又找到一层（748 版夹具实测）。当前 `teamState('t1')` 是 **`tasks: []`**。于是**即使 provider 真的读盘**，只要它的产出是"任务条数"（很自然的写法）：

```
readTeam(正确 root) => team 存在，tasks.length = 0
readTeam('')        => undefined，兜底 ?? 0    = 0
⇒ 两格读数完全相同 ⇒ 差分判别力 0 ⇒ 打印"测不了" ⇒ M8 漏检
```

实测：`tasks: []` + `{ tasks: team?.tasks.length ?? 0 }` + M8 变异 ⇒ **10 pass / 0 fail（漏检）**；
把 `tasks` 换成 **1 条合法 task**（其余一字不改）⇒ 基线仍 10 pass，同一变异 ⇒ **抓到**，臂 9 自述 `stateRoot 无` → `stateRoot 有（已对拍）`。

⇒ **判据比"写一份 team.json"再准一格：**

> **夹具的 durable 根不仅要"有数据"，还要在 provider 投影的那一维上"非空"。**
> 空数组让「读到 0 条」与「读不到 → 兜底 0」**同值** —— 这和空目录是**同一个形态，只是深了一层**。

★★ 而它与本仓既有的纪律是**同一条**：`confidenceOf` 对缺席计数返回 `undefined` 而不填 0（`src/confidence.ts:121`），理由是"补零会让'不知道'伪装成中立的读数"。
⇒ **那是取数侧不许编零；这里是夹具侧不许让"零"与"缺席"同值。同一个陷阱，两层。**

★ 建议：`teamState` 里放 1 条合法 task（`{ id:'k1', subject:'probe-task', status:'pending', dependencies:[], createdAt:1000, updatedAt:1000, attempt:0 }`，`taskSeq: 1`）。它同时让"任务相关读数"在夹具里有非零基线，**不只是为 M8**。

##### ★★★ 第四类证据：源码级"调用点实参"断言（补臂 10 的盲区）

`readoutContextOf` 抽出来之后，臂 10 钉的是"**这个函数算得对**"。但 `src/snapshot.ts:497-499` 自己已经逐字记下了它的盲区：

> MEASURED（2026-10-24）：把本函数的**调用参数**改成 `readoutContextOf(state.id, '', …)`（即真的把空串传下去），夹具的 `readoutContextOf` 臂**照样绿** —— 因为它断言的是 `readoutContextOf('/a/b') === '/a/b'`，看不见"谁在用它、用什么参数调它"。

⇒ **函数对 ≠ 调用对。** 需要第四类证据：**断言调用点把 `stateRoot` 形参传了进去。**

本仓已有同型先例，而且那条先例的注释记的正是同一个坑（`scripts/gate-dispatch-point-applicability.test.mjs:106-112`）：

> ⚠️ MEASURED（我第一版写错了，被定向突变 D 抓出来）：第一版是 `/update:\s*\{\s*changedPaths:/` —— ★ 而它**只钉"那一格在不在"**，不钉"它接到哪儿" ⇒ 臂仍然绿。
> ⇒ 修法：钉**绑定本身** —— `changedPaths` 右侧必须读 `input.`
> ★ 那正是本队最贵的那种形状：**测试很绿，而它测的是"形状在"，不是"接线对"。**

##### ★★ 但直接 `readFileSync('src/snapshot.ts')` 会被本仓自己的判据打红

`scripts/gate-source-reading-convention.test.mjs` 是**专门查这件事的判据**，它的核心问句（逐字）：

> 那个夹具读这个文件，是为了【从它的文本里找某个东西】，还是为了【它本身】？
> · 前者 ⇒ **该走统一口径**（它关心"生产的代码里有没有这件事"，而落点会随重构移动）

而"调用点第二格是不是 `stateRoot`"**显然是前者**。核查：`snapshot` 在该判据的白名单（`ALLOWED_DIRECT_READS`）里出现 **0 次**。

⇒ **硬编码 `src/snapshot.ts` 的实现会当场红**，而它防的正是本仓记录过两次的真实事故（`t39` 拆 `tools.ts` ⇒ 15 个夹具在旧位置找；`t70` 拆 `update-task` ⇒ 8 个）。

##### 正确的写法：`src/**` 普查 + "恰好一处"

照抄同文件臂 2 已经用过的手法（不写死文件名，扫全 `src/**`）：

```
普查：谁调用了 collectReadouts(readoutContextOf(...))
① 必须【恰好一处】  ← 两处 ⇒ 有一处没被这条断言覆盖（同臂 2 对"恰好一处 import"的理由）
② 那一处的第二格实参必须是 stateRoot 形参本身，不是 ''、不是别的变量
```

★ 两点是我加的，readout-architect 的草案里没有：
1. **"恰好一处"**：一处以上时，这条断言只覆盖它匹配到的那一处，其余静默。**"通过"会变成"至少这一处对了"** —— 与本仓"`at least one` vs `exactly one`"那条一贯区分同源。
2. **不写死文件名**：落点会随重构移动。**"快照组装"这件事今天在 `snapshot.ts`，明天可能在别的文件** —— 那时硬编码的断言会在旧位置找不到，红得莫名其妙（`t39`/`t70` 的第二次发生）。

##### 四类证据的分工（没有一类能单独覆盖）

| 证据 | 钉什么 | 无条件？ | 盲区 |
|---|---|---|---|
| **臂 10** | `readoutContextOf` 的输出三格算得对 | ✅ | **快照有没有用它、用什么参数调** |
| **新：源码普查** | 调用点第二格是 `stateRoot` 形参，且**恰好一处** | ✅ 与 provider 无关 | 只在源码文本层 —— **不是运行时证据** |
| **臂 9 spy 支** | 快照**真把** context 交给了 provider（运行时） | 仅"有空槽"时 | 四线全落后不适用 |
| **臂 9 保真支** | 转发不吞不改形 + 差分 | ⚠️ 条件性 | provider 不读那一格时"测不了" |

★ **四类各钉一段，这才是"三态纪律"该有的形状**：不是找一个"全都能测"的臂，是**把"测不了"说清楚归谁**。

##### M7 与 M8 在"无判别力"时结论相反（保留，这是本节最该记的一条）

新版对两格都做了差分（`historicDiscriminating` / `rootDiscriminating`），无判别力就打印"**测不了，不假装覆盖**"。机制本身是对的、诚实的。**但两格的"测不了"含义不同：**

| 格 | 无判别力的含义 | 结论 |
|---|---|---|
| **M7** `historic` | 四条线都不读它 ⇒ 传错**对该线输出无影响** ⇒ 变形**无害** | ✅ "测不了" **可接受**（差分的正确语义） |
| **M8** `stateRoot` | 该臂对"错目录"这一变异**零覆盖** | ❌ "测不了" **不是免检信号** |

★ **为什么 M8 不能只打印"测不了"**：它无法区分两件性质相反的事 ——
1. provider **合法地**不读盘（例如 `backends` 探的是环境能力，本来就不读团队 durable 状态）；
2. provider **该读盘而没读**（bug）—— 于是四格读数不是从真盘投影出来的。

⇒ **两者在读数上同形。** 而 (2) 的后果是"数字全对、全来自错的地方"，UI 一片正常。

⇒ **建议**：补上 `team.json` 之后，若 M8 **仍然**无判别力，那就只剩情形 1 或 2 —— **此时应给橙/警告而不是"测不了"**。给了 warning 才有 owner；打印"测不了"等于给了一个可以合法无视的理由。


##### 可以一般化的判据（差分检验的边界）

```
变异的是【配置项】（视图开关、标记位）⇒ 无判别力 = 该配置对输出无害 ⇒ 免检合理
变异的是【数据来源】（从哪读、读谁）  ⇒ 无判别力 = 没有来源           ⇒ 免检是 bug
```

★ M7 是配置项，M8 是数据来源。**同一个差分机制，两种性质不能共用一种出口。**

★ readout-architect 给了个能永久钉住的建议：把 snapshot 侧 context 的构造提成**导出的纯函数**（`readoutContextOf(team, stateRoot, options)`），臂直接断言它的输出，与"有无空槽可 spy"无关。**我认为这是对的落点**，它把不变量从"某条分支"移到"一个可直测的函数"。

| **M8 `stateRoot` 空串能被发现** | 臂 9 spy 分支 | ❌ **恒免检**（夹具 root 无 `team.json`） | ★ **修法是补数据，不是找 owner**：`makeRoot` 写一份 `team.json` 即恒有效 | ⚠️ **分不清"合法不读盘"与"该读未读"** ⇒ 补数据后仍无判别力就给**橙/警告** |

★ 这张表的用法：**"稳定"那五行已经解决，不用再管；要看的是后三行 —— 它们今天绿，且落地那天不一定红。**

★★ 第五列是这张表的重点：**"未覆盖"有三种性质 —— 无害、未知、有罪。** 今天 M7/M8 共用一个"测不了"出口，等于把"无害"和"有罪"打印成同一句话。

★★ **M8 那一行的性质已从"找 owner"改成"补数据"**：根因不在谁负责，而在夹具的 root 是一份**空** durable 根 ⇒ 真实 provider 读什么都拿到 `undefined` ⇒ 差分恒零。**补一份 `team.json` 之后，这条不变量不再需要任何 owner 交接。** 详见"新增 4"。
