# 并行的瓶颈：`lib/git-artifact-stamp.json`（2026-10-16）

> **用户要求**「把可以并行的任务并行掉嘛。」
> ★ 而队长在派第二个任务时被闸门拦下:
> ```
> Error: inScope overlaps t91 at lib/git-artifact-stamp.json;
>        serialize these tasks or split the paths
> ```

---

## 1. ★★★ 瓶颈是**单个文件**,而它是构建产物

```
$ python3 -c "import json; d=json.load(open('lib/git-artifact-stamp.json')); print(list(d.keys()))"
  ['schema', 'source', 'output', 'commit']
```

⇒ ★★ **它是构建产物** —— **任何跑 `pnpm build` 的任务都会重写它。**
⇒ ★★★ **所以"真并行"的唯一形状是:【不跑 build 的任务】。**

## 2. ★★ 而那个约束比它看起来更宽

```
★ 任何改 src/ 的任务 ⇒ 必须 build ⇒ 写 stamp  ⇒ 不能并行
★ 而任何【跑全量 test:gates】的任务也会读 build 产物
⇒ ★★ 所以能并行的只剩:【不碰 src/ 也不跑 build】的任务
```

**本会话真正并行过的那一对（t87 / t88）:**
```
t87: src/tools* · src/quality-gates.ts · lib/**     ← 改代码，写 stamp
t88: .agent-teams/** · docs/                        ← ★ 只写数据，不跑 build
⇒ ★★ 无重叠 ⇒ 真并行 ✅
```

## 3. ★★★ 而它现在是**系统性的**

```
★ 每一个"改代码"的任务都写同一个文件
⇒ ★★ 而本仓的设计是【一个任务一个 worktree，各自 build】
   ⇒ 两个同时 build ⇒ 两个都改 stamp ⇒ 合并时必冲突
```

★ **而闸门的选择是"拦下并要求串行"** —— 那是**安全的**,但**代价是并行度=1**。

## 4. ★ 三条可能的出路（而我不建议现在改）

| # | 出路 | 代价 |
|---|---|---|
| **①** | ★ **stamp 不进版本控制**（gitignore）| ⚠️ 它是**构建新鲜度的判据**（本会话用过多次）⇒ 忽略它就失去那个读数 |
| **②** | ★ **stamp 按 worktree 分**（每树一份）| ⚠️ 那**改变它的语义** —— 它现在是"整仓的构建状态" |
| **③** | ★★ **接受串行** —— 它就是"改代码要 build"的必然 | ✅ **零风险**,而代价是**并行只对"纯数据任务"有效 |

⇒ ★★★ **我建议 ③** —— 理由:
```
· ①② 都改了 stamp 的【语义】，而它是本会话反复依赖的读数
  （"stamp ≠ HEAD" 抓到过三次 stale build）
· 而"能并行的任务"本来就少:本会话 40+ 个任务里，纯数据的只有 2 个
⇒ ★★ 所以为了并行而改 stamp，收益小、风险大
```

## 5. ★★ 所以"尽量并行"的准确边界

```
✅ 可以并行:① 纯数据任务（只写 .agent-teams / docs）
           ② 互不依赖且【都不改代码】的任务
❌ 不能并行:任何改 src/ 的任务（都要 build ⇒ 都写 stamp）

⇒ ★★ 而那意味着:【改代码的任务本质上是串行的】——
   不是流程设计得不好，而是"一个仓一份构建产物"的直接后果
```

★ **而若要真正提高并行度,该动的是【构建产物与 worktree 的关系】,
不是 stamp 这个文件** —— 那是一个更大的工程（且会改本仓的构建契约）。
