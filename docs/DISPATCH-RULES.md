> **建立：2026-10-09。** 触发：用户问「本来你可以排一个并发比较高的 DAG，
> 但因为我们加了条件和判据，最后变成了一条串行的长链」。
>
> **这份文件是【派工时的检查表】，不是设计文档。**

## 1. 三条规则

### 规则 1：依赖只能来自两个来源

```
① 真写域冲突（两个任务改同一个文件/同一路径）
     ⇒ 必须串行（★ 或者拆文件，见规则 3）
② 真前置（B 要【读】A 产出的东西，且 A 没产出 B 就无法开工）
     ⇒ A 先
```

**★ 其余一切都不许建边**，包括（而这些我都用过）：

```
✗ "验证应该在实现之后"          ⇒ 见规则 2
✗ "审查要等全部完成"            ⇒ 见规则 2
✗ "看起来有先后顺序"            ⇒ 顺序不是前置
✗ "同一个成员做了 A，那 B 等等"  ⇒ 成员不是依赖，【写域】才是
✗ "把相关的事放一起"            ⇒ 相关不是前置
```

**⇒ 判据（写边时问自己）**：

> **「把 A 删掉，B 还能开工吗？」**
> **能 ⇒ 不该有这条边。**

---

### 规则 2：验证与审查**不是屏障**，是**配对**

```
✗ 现在（屏障式）: t5/t6 依赖 14-15 条 ⇒ 它们最后才跑，而那时没有别的活
✓ 应该（配对式）: 对每一个交付，验证【它自己】那一条
```

**★ 而"改坏别处"是【整体】的性质** ⇒ 所以它确实需要一条整树任务 ——
**而那条不该是【每一条】的前置。**

**⇒ 采用 (丙)：配对验证 + 一条整树验证。**

```
pair(i) : impl(i) → verify(i)     ← 成对，尽早、并行
final   : 全部 → verify-tree       ← 一条，最后
```

**★ 依据**：用户 `REQUIREMENTS.md` §6.1 ——
*"每次都需要迭代出一个稳定的基线出来"*、*"看原本是好的代码和功能有没有被改坏"*。
**⇒ "改坏别处"靠那条 `verify-tree`；而"这个交付对不对"靠配对的那条。**

---

### 规则 3：写域冲突时，**先看能不能拆文件**，再考虑串行

```
我昨晚做的:  "共享装配点 ⇒ 串行"（3 次）
而更该先问:  "能不能让两个人改不同文件？"
```

**★ 判据的顺序**：

```
① 能不能拆成不同文件？      ⇒ 拆（两个任务各改各的）
② 能不能各加一行、由一条合并任务统一落？ ⇒ 能 ⇒ 并行 + 一条收口
③ 都不行                    ⇒ 才串行
```

**⇒ 而"串行"是最后手段，不是第一反应。**

## 3. ★ 一条与"并发"直接相关的实测约束

```
主树 node_modules:        1.6 G
每个 worktree 的真实拷贝:  579 M（独立 inode ⇒ 各自一份）
```

**⇒ 并发的上限可能不是成员数，是磁盘。而它是可以腾的。**

**★ 而它的根因是一条【没有调用方】的机制**：
`provisionWorktreeDependencies`（`src/worktree.ts:247`）为"唯一来源地注入依赖"而写，
**而全仓没有生产调用方** ⇒ 每个成员在 worktree 里各自 `pnpm install`。

**⇒ 已派 t24 接上它。** 接上之后：
```
✓ "装什么"有唯一来源（由 missingIgnored 喂）
✓ 不再各装各的（一致性）
✗ 而磁盘仍是 579M × N（因为复制而非软链 —— 那是有理由的决定）
```

### ★★ 而"按需注入"的候选集比它该有的更大 —— 实测

```
ignoredTopLevel(主树) ⇒ .DS_Store, .agent-teams, .pnpm-store, node_modules

  .DS_Store        12K
  .agent-teams     4.2G   ← ★ 本仓自己的运行时状态（含所有 worktree 自己！）
  .pnpm-store      1.1G   ← 共享包仓
  node_modules     1.6G
  ─────────────────────────
  合计            ~6.9G / 棵
```

**⇒ 照"候选即清单"接上，第一棵就爆盘。**
**⇒ 所以「唯一来源」要再往前一格**：`候选 ⇒ 【筛过的清单】⇒ 注入`，
**而那一筛必须说出理由**（否则静默的 filter 与"没东西要过滤"同形）。

### ★ 而磁盘是可以腾的（实测）

```
回收前: 可用 8.1 G · worktrees 占 4.2 G
跑 node scripts/worktree-reclaim.mjs --apply ⇒ 删 32 个
回收后: ★ 可用 9.5 G · worktrees 占 2.3 G
⇒ (丙) 要的 4-6 并发（2.3-3.5 G）⇒ 富余
```

**★ 而那个工具的判据是保守的、且带理由**：
```
它删: 产物已被主树吸收的（--is-ancestor 成立 + 无未提交唯一改动）
它留: 「内容在任何提交里都不存在」的一律保留（unique-work / not-absorbed）
```
**⇒ 它不会删掉"只在工作树里、没 commit"的东西** —— 而那正是本队丢过一次的东西。

## 4. ★ 一条与"已知失败清单"有关的规则（2026-10-09 裁定 t18）

**背景**：一条夹具的红，可否进"已知失败清单"？仓里有**先例**说可以
（`verify-task-atomicity.test.mjs` 那条：作者与独立验证者都确认过"它红，而那是对的"），
而"不许自指"那条规则又说不行。**两条规则方向相反。**

**⇒ 裁定（一般形式）**：

> **一条红可以进清单的唯一条件：它已经被【处理过】—— 修好了、或明确裁定为不需要修。**
> **⇒ 一条【还没被处理过】的红，无论它是存量还是新机制报的，都不该进清单。**

**★ 而它解释了那个"冲突"其实不冲突**：

```
先例那条  : 它【被两个人确认过】⇒ 已被处理 ⇒ 可 pin
自指那条  : 防的是【空间的】自指（谁写的）
本裁定    : 防的是【时间的】未处理（改了也没人管）
```

**★ 而它最贵的形态**：

> **一个"已知失败"清单，只能收【与任何改动都无关的存量】。**
> **一旦它收进一个【某个机制自己的缺口】，那个缺口就永久免疫了 ——
>   因为清单的语义是"不必再看"。**

**⇒ 所以"新机制的首次报警"必须留在清单外面**：它会在机制修好后**自动消失**，
而把它 pin 掉 = **把第一次报警消音**。

**⇒ 所以并发的物理上限要按磁盘算**，而那不是可以靠"加成员"解决的。

## 5. ★★★ 为什么团队会「停」——而它不是等成员（2026-10-09 实测）

### 5.1 现象

用户看到 Team 页面：**进行中 1 · 等待依赖 21**

```
22 条 pending · 卡依赖 21 · 真可开工 1
```

### 5.2 ★ 根因一：`failed` 不满足依赖，而它的【产物已经在主树】

```
t20 failed · t12 failed · t18 failed · t23 failed · t24 failed · t25 failed
★ 而它们的交付【全部已并入主树】（commits: 9cb583a / 395192f / d01394d / 7742a27 / …）

⇒ 而 9 条 pending 因为【依赖这些 failed】而永远开不了工：
   t2 ← t20 · t5/t6 ← t12 · t17 ← t18,t20 · t19 ← t18 · t21 ← t20
   t22 ← t18 · t26 ← t20 · t29 ← t23
```

**★★ 而"failed"在这里表达的是【记录形态】，不是【事实形态】**：
```
事实: 产物已并入主树、已 commit、已验证 ⇒ 前置【已满足】
记录: status=failed（因为那个环让它交不上 completed）
⇒ ★ 而依赖判定读的是【记录】，于是把它读成了"前置没满足"
```

### 5.3 ★ 判据

> **依赖问的应该是「前置的【产物】存不存在」，
> 而不是「它的【记录】是不是 completed」。**

**★ 而当两者不一致时（failed 记录 + 已并入的产物），依赖必须按【产物】判。**

### 5.4 ★★ 根因二：消息派工**不会建 worktree**

```
captain 用 send_message 派活 ⇒ 调度器不介入 ⇒ createTaskWorktree 不跑
⇒ 成员没有工作目录 ⇒ 无法开工（而它会如实报出）
★ 而 needsWorktree 只在【调度器自己派发】时触发 —— 那是 onWorktree 的唯一路径
⇒ ★ 派工必须走 reassign_task，不是 send_message
```

### 5.5 ★ 关于「成员定时探活」

**用户问：「我记得我不是做了成员定时探活吗」**

**答**：探活（`wait_agent` / 状态变化通知）解决的是 **「成员报告回来了，叫醒我」**。
**而这一次团队停住的原因不是"我没被叫醒"** —— 是：
```
① 四个成员全部 idle（他们确实没有活可做）
② 而 21 条 pending 全部卡在 failed 依赖上
⇒ ★ 没有"报告会回来"，因为【没有任何成员在跑】
⇒ 探活在这种情况下返回 noProgress —— 那是它的正确行为，而不是它的失效
```

**★★ 判据（记进派工规则）**：

> **「等成员汇报」与「没人可汇报」必须分开看。**
> ⇒ 在 yield 之前，必须算一次 **ready 数** —— 若 ready === 0 而 pending > 0，
>   那不是"在等"，那是【被依赖锁死】，而锁死的东西要靠人解。

### 5.6 ★ 检查表补充（加进 §2）

```
□ 算 ready 数：ready = pending ∩ (依赖全 completed)
   ★ 若 ready === 0 而 pending > 0 ⇒ 去查"卡在谁身上"，别 yield
□ ★ 有没有 pending 卡在【failed】上？⇒ 它们的产物在不在主树？
   ★ 在 ⇒ 依赖该按【产物】判，而不是按【记录】判
□ ★ 派工走 reassign_task（有调度器建树），不是 send_message（不建树）
```

## 6. ★★★ 团队形态：临时 Worker + 成员可派 subagent（2026-10-09 用户裁定 A+C）

### 6.1 用户的原意（`REQUIREMENTS`）

> **Worker**：临时拉起的 sub agent，干净上下文，只注入它需要的部分。
> **Reviewer**：同样在那条 worktree 上临时拉起，只负责检验那个临时 Worker 的工作。
> **Integrator**：合并解决多条 worktree 的合并。

### 6.2 ★ 而实测的当前形态（与用户原意不同）

```
成员是【持久】的 —— 由 startContinuable 起（src/members.ts:628）
  ctx.subagents.startContinuable({ parent: captain, persona, … })
  ⇒ 会话被保留、可被再次唤醒 ⇒ 上下文【累积】

⇒ 于是三个 worker 各自持有一条任务链，而它们的上下文跨轮累积
```

**★★★ 而它的代价今晚已经以具体故障出现**（全部真实）：

```
① 「我上一轮改过一次却【没落盘】」              ← pipeline-author
② 「我四次报『产物在 worktree 里冻结着』，从未 commit」 ← wire-author
③ 「我在前几轮拿那条坏掉的突变臂当过证据」        ← pipeline-author
④ 「我上一轮把臂 4 裁定为『会转绿』，而前提从未被验证」 ← ★ captain 自己
⑤ 三次「同一个问题改根因」（slice(3)→相对路径→.trim()） ← verifier
```

**★ 共同形状**：
> **一个持久的上下文，会让【上一轮的结论】与【本轮的事实】并存 ——
> 而它没有标注哪一条已经过期。**

### 6.3 ★★ 而"临时 worker"需要先回答一个问题

> **「链条的连续性」存在哪里？**

```
现在:  存在【成员的内存】里  ⇒ 所以它们隔几轮会引用过期的结论（①②③ 就是它的产出）
改成临时: 它必须存在【外部】
```

**★ 而好消息：那三样今晚都已经在盘上**：
```
契约 ⇒ team.json 里每个 task 的 objective/acceptance/inScope/verify
台账 ⇒ team.json 的 status/output/attempt
判决 ⇒ .agent-teams/judgements/ + docs/*.md
```

### 6.4 ★ C 的开关（实测定位）

// src/index.ts:131

// src/tools.ts:1676

**★★ 而它是【宿主配置】，不是本仓代码 ⇒ 改它不进本仓的判据面，也不需 build。**

### 6.6 ★★★ 而 A 与 C 合起来是什么形状（用户裁定 A+C）

```
Worker    : 临时 subagent（干净上下文，只注入【它的契约 + 相关读数】）
Reviewer  : 临时 subagent（在那条 worktree 上，只验那个 Worker 的工作）
★ 而【由谁拉起它们】= 持久成员或 captain（C 打开了那条路）
Integrator: ★ 还没有建 —— 而它才是【持有跨 worktree 连续性】的那个角色
```

**★ 而"链条的连续性"由三样外部记忆承担**：
```
契约（team.json 的 task 字段） + 台账（status/output/attempt） + 判决（.agent-teams/judgements/）
```

### 6.7 ★ 落地的次序（不做大爆炸）

```
① 先打开 memberMaxDepth=1（一条宿主配置）⇒ 成员能派 subagent ⇒ 立刻可用于【并发的活】
② 而"worker 改成临时"是【派发规则】的改动，不是代码改动 ——
   它要求每次派发时【注入契约而不注入历史】
③ ★ 而 Integrator 是【新角色】—— 它需要一个明确的职责边界（见 §6.8）
```

### 6.8 ★ Integrator 的职责（待定，但边界可写）

**它不该是"又一个 worker"** —— 它的对象是**多条 worktree 之间的关系**：
```
· 谁与谁改了同一个文件（写域冲突）
· 谁的产物已并入主树、谁还没有
· 而"并入"这个动作由谁做（现在: captain 手工）
⇒ ★ 而它正好能替代"captain 手工并入"这件事 ——

## 7. ★★★ 失败计数不可读为证据 —— 只有集合比对算（2026-10-09 实测汇总）

### 7.1 同一份代码，不同时刻的失败数

```
captain 今晚量到:  fail 7 / 13 / 16 / 17 / 22 / 33
pipeline-author :  fail 47 / 14 / 14   ← ★ 同一份代码、同一条命令、连跑三次
decompose-author:  tests 837–1106 之间摆动
wire-author     :  fail 13（安静）/ 26（队友 build 中）
verifier        :  fail 24 / 20（stash 前后）
```

**★★★ 而 `pipeline-author` 把它写成了一句最准的**：

> **「一个能从 47 掉到 14 的失败计数，不能被当成『改进了』或『退步了』来读。
>  ⇒ 只有【集合比对】算证据。」**

### 7.2 ★ 而根因是【并发 build 清空 `lib/`】

```
多个成员同时跑 pnpm build ⇒ clean-build 阶段清 lib/ ⇒
而另一个成员正在跑的夹具 import 不到模块 ⇒ 报 ERR_MODULE_NOT_FOUND
⇒ ★ 那些红是【构建中间态】，不是真红 —— 而它们与真红在计数上同形
```

**★ 而判别法（`wire-author` 给的，可机械判）**：
```
碰撞/中间态 ⇒ 报文含 ERR_MODULE_NOT_FOUND / Cannot find module lib/
真断言失败  ⇒ 报文含 AssertionError
★ 两者【可在同一次输出里直接分开】，不必靠"重跑一次看看"
```

### 7.3 ★★ 而由此得出的读法（写进本文件，作为派工规则）

```
□ 不许把 fail 计数当证据（它随队友活动摆动）
□ ★ 证据 = 【集合比对】：本树失败的【集合】 vs 基线失败的【集合】
   —— 交集为空 ⇒ 零新增失败（那才是可读的结论）
□ 而"同一条命令连跑三次给出不同计数"这件事本身，是一条【关于装置的读数】：
   它说明这个套件的计数不可用于判定
```

### 7.4 ★ 而今晚它至少误导过三次

```

## 8. ★★★ 任务生命周期与交接格式（用户 2026-10-09 定）

### 8.1 用户定的形状（逐条）

> **派发的事情还是交给队长来做**（captain 派工，成员不自行领）
> **临时 worker 做完之后不应该直接把上下文提交给队长** ⇒ 要有一个**完成的状态**
> ⇒ 由**临时 reviewer** 审核
> ⇒ 审核完之后 worker 若需要改 ⇒ **改** ⇒ **还是由刚才那个临时 reviewer 审核**
> ⇒ 最后没问题了才把上下文提交给 **integrator**
> ⇒ ★ **提交多少上下文也得设计，得有固定的提交格式**
> **给临时 worker 注入的上下文先按之前说的来**（契约 + 相关读数），后续再优化

### 8.2 ★ 现有协议与它的差（实测）

**已有**（`src/index.ts` 的 captain protocol §8）：
```
requirements → implementation → verification → review → integration
失败 review ⇒ 自动加 repair + 下一轮 review（并改下游依赖）
```

**而用户要的、协议里【没有】的五件**：
```
① worker 完成 ⇒ 一个【完成的状态】（不直接交上下文给 captain）
② reviewer 是【临时拉起】的（不是持久成员）
③ ★ 改完 ⇒ 【同一个 reviewer】再审（不是新起一个）
④ 通过之后才交给 integrator
⑤ ★ 交接有【固定格式】，且要定【交多少上下文】
```

### 8.3 ★★★ 交接格式（设计）

**三个交接点，每个一个固定形状**。★ 原则：**只交"事实与读数"，不交"推理过程"**
—— 因为推理过程是**上下文**，而它能被压缩成结论；而事实不能被压缩。

#### (A) worker → reviewer（完成的状态）

```
{
  task:        <task id>
  attempt:     <attempt id>          ← 防串（stale attempt 会被拒）
  status:      completed | failed
  objective:   <逐字，来自契约>       ← ★ 复述，不解释
  changedPaths: [<路径>]              ← ★ 事实，不是描述
  commandsRun: [{ command, status, exitCode, evidence }]
  acceptanceResults: [{ criterion, status, evidence }]
  evidence_note: <可选，只写"我看到了什么">
  ★ 而不交: 推理过程 / 我考虑过什么 / 与我无关的历史
}
```

**★ 为什么 `changedPaths` 是事实而"我改了什么"不是**：
```
"我改了分档逻辑"     ⇒ 描述，可被两种实现满足
["scripts/friction-triage.mjs"] ⇒ 事实，可被核
```

#### (B) reviewer → worker（审的结果）

```
{
  reviewedTaskId: <被审的 task>
  reviewedAttempt: <被审的 attempt>   ← ★ 必须指名，否则改过之后再审会审错版本
  verdict:      pass | needs_revision | reject
  findings: [{ id, severity, problem, requiredFix, file?, line? }]
  ★ needs_revision / reject ⇒ findings 【必须有】，且每条要有 requiredFix
  ★ pass ⇒ 不要求 findings
}
```

**★★ 而 `reviewedAttempt` 是这一格里最要紧的字段**：
```
用户要的是【同一个 reviewer 再审同一件工作】
⇒ 而"同一件工作"必须可指认 ⇒ 否则改过之后，reviewer 会审【新版本】而以为在审旧版本
★ 而那正是今晚反复出现的那条：一个指认，若不带【版本】，会指向错的对象
```

#### (C) reviewer → integrator（通过之后）

```
{
  task:        <task id>
  attempt:     <通过的那一次 attempt>
  verdict:     pass
  changedPaths: [<路径>]              ← ★ integrator 唯一需要的输入（它判写域冲突）
  baseRevision: <这次改动基于哪个版本>  ← ★ 否则 integrator 无法判"能不能并"
  commandsRun: [<最后那一次>]
  ★ 而不交: findings（已关）、reviewer 的推理、worker 的上下文
}
```

**★★ 为什么 integrator 只要 `changedPaths` + `baseRevision`**：
```
它的工作 = 判【多条 worktree 之间的关系】
  · 谁与谁改了同一个文件  ⇒ 只需要 changedPaths
  · 能不能按顺序并        ⇒ 只需要 baseRevision（★ 今晚我手工并时踩过三次）
⇒ ★ 其余的东西对它都是噪声
```

### 8.4 ★★ 三条硬规则

```
① ★ 同一个 reviewer 再审（用户明确要求）⇒ 所以 reviewer 必须【跨轮存活】
   ⇒ 而"临时"指它的【上下文干净】，不指它的【生命只有一轮】
   ★ 这是一个必须说清的区别（否则"临时 reviewer"会被实现成"每轮新起一个"）

② ★ 改完之后再审，必须【指名 attempt】
   ⇒ 否则"审的是哪一版"无法回答（今晚那条：契约必须指名对象【与版本】）

③ ★ worker 与 reviewer 的上下文【不互相进入】
   ⇒ worker 不读 findings 之外的 reviewer 推理；reviewer 不读 worker 的过程
   ⇒ 而两者【都从契约读 objective/acceptance】
```

### 8.5 ★ 而它与现有机制的关系

| 用户要的 | 现有机制 | 差 |
|---|---|---|
| 完成的状态 | `update_task(status=completed)` | ✓ 有 |
| reviewer 审 | `kind=review` + `reviewedTaskId` | ✓ 有 |
| 改完再审 | `kind=repair` + `sourceFindingIds` | ✓ 有 |
| 交给 integrator | `kind=integration` | ✓ 有 |
| ★ 交接格式 | ★ **没有** | **本条设计** |
| ★ 同一个 reviewer 再审 | ★ **没有**（协议只说"下一轮 review"） | **需明确** |
| ★ 临时 worker/reviewer | ★ 现在是【持久成员】 | **A+C 那一半** |

## 12. ★★★ 代理读数：门读的不是它想确认的东西（`pipeline-author` 的判据，2026-10-09）

### 12.1 判据（逐字采纳）

> **当【让门绿】与【遵守纪律】方向相反时：
> 先问「这道门读的是什么、它代理的是什么」
> ⇒ 若门读的是一个【代理】，而代理在被代理对象没变时也会变
>  ⇒ ★ 那是门的问题，不是纪律的问题 —— 而修门，不修纪律。**

### 12.2 ★★ 而这条判据把今晚**所有**的缺陷统一了

```
代理（门读的）           被代理的（它想确认的）        失真方向
─────────────────────────────────────────────────────────────────
"工作区脏不脏"          "本次交付改了什么"          ① 误算别人的（别人动过 ⇒ 算进我）
                                                   ② 漏算自己的（已 commit ⇒ 算出去）
"HEAD 前进过没有"       "你手上的代码旧没旧"        复述：任何提交都触发
"命令的退出码"          "那一步有没有真的执行"      ★ 静默不执行也退 0
"字段存在与否"          "那位判据有没有在守"        读一个不存在的字段 ⇒ 恒真
"记录里 attempt 加没加" "那次派发有没有生效"        悬挂 handoffId ⇒ 永不累加
"fixture 的值"          "装载器交不交得出"          夹具复刻产品形状 ⇒ 产品改了它不变
"dirty"                 "交付存在不存在"            已 commit ⇒ 不 dirty ⇒ 判"没有交付"
⇒ ★ 七条，而每一条都是【代理在对象没变时也会变】
```

### 12.3 ★★★ 而"两个方向都失真"是同一个成因

**`pipeline-author` 在 t9 上给出的最准的一条**：
```

   ① 别人（或你）在这次会话期间的改动，会被算进【我】的 changedPaths
   ② 而我自己已 commit 的改动，会被算【出去】
⇒ ★ 同一个实现，两个方向都错 —— 而 ① 与 ② 的成因是同一个：
   它拿【工作区状态】代理【本次改动】，而那个代理在【有别人动过】或【已提交】时都失真。
```

**★★ 而它的一般形式**：
> **代理读数在它所代理的东西没变时也会变 —— 而两个方向的失真在读数上同形
> （都表现为"这个数不对"），而它们的修法【相反】：一个是收窄，一个是放宽。**

### 12.4 ★★ 而"独立选出同一边"本身是一个读数

```
t9 的格(pipeline-author): "让门绿" vs "不越界"      ⇒ 选不越界
t4 的格(wire-author)    : "让门绿" vs "遵守条款②"  ⇒ 选条款②
t12/t18 同 wire-author  ⇒ 同一边
⇒ ★ 两人在【不同的格】上独立选了同一边
⇒ ★ 而那不是"两个人保守"，是【那两条纪律在遇到这几道门时必然冲突】
   ⇒ ★ 即：冲突在【纪律】这一侧，不在执行者。
```

**★★★ 而这条推论的操作价值**：
```
当多个独立执行者在同一类冲突上做出同一个选择 ⇒
  · 若那是"保守" ⇒ 它是性格，不可推广
  · 若是"必然" ⇒ 它是结构，而【结构该被修】
⇒ ★ 判据: 看他们选的【理由】是否同源。
   t9 的理由 = "改别人的文件会让两次改动混进同一条台账"
   t4 的理由 = "uncommit 会再冒一次丢产物的险"
   ⇒ 两条理由不同，而它们【指向同一件事】: 让"谁改了什么"保持可指认。
   ⇒ ★ 而那正是那条纪律在守的东西 —— 而门在否定它。
```

  （实测唯一必要的场合：两个交付物改同一个文件、需要取并集 —— 如 t4 与 t12 都改 status.ts）
  ⇒ 而那时必须在提交信息里写明【为什么手工】

★ 而"手工落盘"的代价不是风格问题：它让回收对那棵树【永久】答"未吸收"，
  于是那棵树永远留在盘上，而它与"这份工作还没合并"在读数上同形。

### 40.4 回收判据本身也要改（已立项 t34）

**判据只看 patch-id ⇒ 它对手工落盘【永远】答未吸收。**

**⇒ 修法：让它也能按【文件内容】判"已吸收"。**

**★ 而护栏一个字不动**：判据自己的历史记着 —— **只按祖先判会删掉 7 个"内容不在任何提交里"的文件。**
**⇒ 加内容比对，不许放宽"保住唯一产物"那一半。**
