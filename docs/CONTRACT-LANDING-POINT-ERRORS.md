## 5. ★★★ 第二次取回事故（2026-10-16 深夜,同一形态的第三次）

**我又差点抹掉产出,而这次是【我自己的取回命令】造成的。**

### 经过

```
★ t97 的产出【未提交】（它在我 amend 后还在重跑,而它的会话失败了）
★★ 而我用了一个【错的取回命令】:
   git -C "$W" show ":0:$f" > "$f"     ← ★ 索引路径语法，不是 git show 的路径
⇒ ★★★ 结果:那些文件被【清空】——
   `git show` 对不存在的对象报错,而【重定向已经创建了空文件】
```

**实测证据:**
```
$ wc -l src/quality-gates.ts          ⇒  2532
$ wc -l <worktree>/src/quality-gates.ts ⇒ 2685
$ grep -c artifactBindingOf src/quality-gates.ts ⇒ ★ 0（worktree 里是 2）
```

### ★★ 根因:同一形态的第三次

```
① 早先:for f in $(git diff --name-only A HEAD); do git show "HEAD:$f" > "$f"; done
   ⇒ ★ 截断了不在那棵树里的文件
② 上一轮:git show "HEAD:$f" > "$f" 指向【早于该任务提交】的 HEAD
   ⇒ ★ 用旧版覆盖新版
③ ★★ 本轮:git show ":0:$f" ⇒ 语法错 ⇒ 而【重定向先创建了空文件】
⇒ ★★★ 三次都是同一件事:「命令失败」与「文件是空的/旧的」是【同一个结果】
```

★★ **而三次的共同动作是 `> "$f"`** —— **它在命令失败之前就已经执行了。**

### ★ 处置

```
★ 从 worktree【直接 cp】恢复（那些文件未提交,所以 worktree 是唯一副本）
★ 验证:artifactBindingOf 6 处回来了 · snapshotReviewedArtifacts 在 · tsc=0 · build OK
```

### ★★★ 而这里有一条比前两次更值钱的教训

```
★ 前两次我加的是【防线】（先核 is-new、先核主干有没有）
★★ 而本轮证明:防线【不能防住"重定向先于失败"】
⇒ ★★★ 所以正确的做法是【不用 `> file` 这种写法】——
   ★ 改成 `cp`（原子、且失败则不产生文件）
   ★★ 或者:写之前先确认源【存在】（git cat-file -e）
```

★ **而我已改用自己的续用做法:`cp "$W/$f" "$f"`** ——
**它失败时【不产生半成品】,而那正是三次事故共同的缺口。**
