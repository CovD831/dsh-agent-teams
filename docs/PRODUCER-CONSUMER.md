# 供给必须有消费（S1 判据）

> **一句话**：一个没有调用方的产出，与没有那个产出在观测上完全相同。
>
> 判据本体：`scripts/gate-producer-consumer.test.mjs`（5 臂，随 `pnpm test:gates` 跑）。
> ★ 这份文档解释**它在判什么、凭什么那么判、以及它判不了什么**。

---

## 1. 它来自两次实测

| 实例 | 产出是什么 | 谁本应消费它 | 实际发生了什么 |
|---|---|---|---|
| **t41** | `workspaceAndWorktreeChangedPaths`（`src/harness-compat.ts:302`） | 生产代码里的某个调用点 | 写好了、**夹具里调用 33 次**、而**生产里零调用** |
| **t54** | `discriminatingFiles` → `newTestFiles`（注入进 ctx） | 唯一读它的门（`completion.r5`） | 那条门不再对 `repair` 生效 ⇒ **证据被生产出来而没人消费** |

★ 两个实例的共同点不是"代码写错了"，而是：**供给那一侧一切正常**（函数对、值对、夹具全绿），
坏的只是**没有任何地方读它**。

---

## 2. ★★ 核心口径：夹具调用**不算**消费者

这是本判据最要紧的一条，而它来自 t41 的具体形状：

```
workspaceAndWorktreeChangedPaths 的调用点【全在夹具里】
  ⇒ 若把夹具调用算作消费者 ⇒ 这条判据【抓不到 t41】
  ⇒ 不算                      ⇒ 它抓到
```

⇒ 所以分成两个**分开计数**的口径：

```
生产消费者 = src/ 下的读取点
夹具消费者 = scripts/ 下的读取点（单独计数、单独成态）
```

★ 而那个区分是**可机械判定的**（调用点在 `scripts/` 下 vs 在 `src/` 下）——
  它不是一条靠人记得执行的纪律。

### 为什么"只有夹具消费"要单独成一态

因为它与"完全无消费"**责任不同**：

| 形态 | 它看起来像什么 | 真实的补救动作 |
|---|---|---|
| 只有夹具消费 | **在测试里被使用** ⇒ 看起来是活的 | 接一个生产调用点，或删掉它（连同它的夹具） |
| 完全无消费 | 一眼就是死代码 | 删掉 |

★ 把两者合成一句"没有消费者"，会让**最危险的那一类**（t41 那种）
  混进"一眼就是死代码"里 —— 而前者才藏得久。

---

## 3. 三态 + 附条件（写在判据里，不靠使用的人记得）

用户 2026-10-08 的原话：

> 「也不是说在特定条件下起效的就不能加，只是需要把这些特定条件顺便加上去。」

⇒ 本判据的附条件**写在代码里**（`OUT_OF_SCAN_RANGE`）：

```
src/client/**    —— 单独打包的客户端 bundle（见 tsconfig.client.json 的 include）
                  ⇒ 它的导出由 bundler 消费，而不是由 import 消费
                  ⇒ 消费点【不在可扫范围内】 ⇒ 判 unmeasured
```

四态因此两两不同形：

| 态 | 含义 | 是不是缺陷 |
|---|---|---|
| `consumed` | 生产里有读取点 | 否 |
| `fixtureOnly` | **只有**夹具读它 | ★ 是（t41 的形状） |
| `unconsumed` | 完全没有读取点 | 是（死代码） |
| `unmeasured` | 生产点或消费点在可扫范围之外 | **不知道** —— 不是缺陷，也不是清白 |

★ 把 `unmeasured` 并进 `unconsumed` 会制造一批**永远修不掉的噪音**
  （你会去"修"一个消费点只是看不见的东西）—— 而那正是教人忽略门禁的老路。
★ 反过来把它并进 `consumed`，则是把"没测到"并进"通过"。

## 4. 全仓读数（**到 2026-10-08 为止**）

```
全仓 413 份模块级产出：
  合格（生产有消费）        319
  ★ 不合格·只有夹具消费      16      ← t41 的形状
  ★ 不合格·完全无消费        12      ← 死代码
  判不了（可扫范围之外）     67      ← 主要是 src/client/**
```

★ 这些数字是**读数，不是不变量**：判据对前两类只用**上限**（禁止退化），
  不用等值 —— 否则一次诚实的清理会让它无故变红。

**第二类产出（运行时数据）**：检查了 **15** 个声明了 `requires` 的判据模块，
「声明了却在源码里读不到」的格：**0**。

### ★ 而这组数字被修正过一次（记下来，因为它正是本判据的主题）

第一次跑出来的数是 `324 / 12 / 10 / 67`。而那**是错的** —— 装置当时把
**注释**也算成了消费点。最刺眼的一处：

```
src/tools/update-task.ts 里有一句注释：
    a0f6504   t41 接上了 `workspaceAndWorktreeChangedPaths(workspace)` ✓
⇒ 装置读成"它被接上了"，于是那个函数报【生产消费 2 次】
⇒ 而它真实的调用点是 0（那两句都在注释里）
```

★ 一个**记录"它没有被接上"的注释**，被读成了「它被接上了」。
⇒ 剥掉注释之后：`生产消费 0 次 · 夹具消费 11 次 ⇒ fixtureOnly` ——
  它一直是 t41 那个形状，只是判据先前看不见。

★ 这不是一个"精度问题"：**那 5 份差额正是本判据要抓的东西**，
  而它们在修正前被算进了"合格"。⇒ 见判据源码里 `stripComments` 上那段记录。

## 5. ★ 它判不了什么（这一节与 §4 同等重要）

1. **消费点是否"真的用到了那个值"** —— 本判据只认"名字在 `src/` 下出现过"。
   一个 `import { x }` 而从不使用 `x` 的文件，在本判据眼里就是消费者。
2. **动态消费**（字符串拼出来的属性名、`eval`、反射）—— 看不见。
3. **`src/client/**` 内部**的消费关系 —— 整个目录被判 `unmeasured`（附条件）。
4. **type/interface 导出** —— 运行期不存在，本判据不判它们（那 195 个不在 413 里）。
5. **第二类产出只是近似**：它用"声明了 `requires` 却没在自己的源码里读"
   来近似"值被算出来而没人读"。★ 而一个格被**别的文件**读（调用方注入它）
   在本判据里**不算**被读 —— 那正是 t54 的形状（调用方一直在注入，
   而**读它的门**不再适用）。

★ 第 5 条尤其要说清：本判据的"第二类"是**一个可扫描的近似**，
  它对 t54 那种"门不再适用"的形状**只能覆盖一部分** ——
  剩下那一部分需要别的东西（例如"声明了却全被 appliesTo 挡掉"）。

## 6. 怎么用（如果有人被它拦下）

```
判成 fixtureOnly  ⇒ 问："这是不是一个真的该在生产里被调用的东西？"
                     是 ⇒ 接一个生产调用点（或明确删掉它 + 它的夹具）
                     否 ⇒ 它可能只是给夹具用的测试辅助 ⇒ 那它该搬到 scripts/ 下，
                          或者显式记进"允许清单"（而那是要写理由的）
判成 unconsumed   ⇒ 问："它还有用吗？"  没有 ⇒ 删掉
判成 unmeasured   ⇒ ★ 什么都不用做。它说的是"我看不见"，不是"它有问题"
```

★ 最后一行是这份文档最重要的一句提醒：**四态里只有两态是缺陷。**
