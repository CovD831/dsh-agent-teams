## 一、★ 先说一个方法论缺陷：`JSON.parse` 静默跳过了 12 条

这是本报告最重要的一处更正。**起点读数的 372 不是语料量，是"读得出来的"量。**

```
$ ls .agent-teams/frictions/f-*.json | wc -l
384

$ node -e "…对每个文件试 JSON.parse，失败就 catch{}…"
解析成功 = 372 · 静默跳过 = 12
```

**这 12 个文件不是"没有"，是"坏了"** —— 每个都是一份**合法的 JSON 头**后面跟着**一段垃圾尾巴**：

```
$ node -e "…找到第一个顶层 JSON 值结束的偏移…"
f-0152  headParses=true  headBytes=13138  trailingBytes=2650  trailingStart="\n810, 2815, 2820, 2825, …"
f-0158  headParses=true  headBytes=16217  trailingBytes=11121 trailingStart="\nion\": {\n        \"__absent\": \""
f-0161  headParses=true  headBytes=32748  trailingBytes=1297  trailingStart="\n16, 16230, 16235, …"
f-0167  headParses=true  headBytes=12787  trailingBytes=2650  trailingStart="\n191, 2196, 2201, …"
…（共 12 个，全部 headParses=true）
```

★ **这 12 个 id 恰好全部是空拒绝记录**：
```
f-0152 f-0158 f-0161 f-0167 f-0172 f-0180 f-0183 f-0190 f-0216 f-0220 f-0241 f-0244
   → 12/12 的 title === "update_task rejected: "（冒号后为空）
```

★★★ **一般形式**（这正是本仓反复记账的形态）：**一个 `try { JSON.parse } catch {}` 把"文件坏了"与"文件不在"读成了同一件事。**
而两者的处置相反 —— 一个要修数据，一个什么都不用做。
**⇒ 「372」这个数字本身，就是那次静默跳过留下的读数。**

**可复跑（带恢复的读数器，本报告全程用它）：**

★ 我**没有**修改任何语料文件（本任务 out of scope）；恢复只在**读**的时候做，且**逐条标注** `_exact:false`。

## 三、每条判据拦了多少（★ 必须分两代看，因为归因标记换过一次载体）

### 3.1 为什么必须分两代看

语料里判据的归因标记**换过一次载体**，是**同一个字段演进的两代形态**，**不是两个并列的面**：

| 代 | 形式 | 时间范围 | 条数 |
|---|---|---|---|
| **v1 标题文本** `[gate.id]` | 写在 `title` 里 | 2026-10-07 15:29 → 10-08 12:08 | **77**（**仅标题**，无结构化字段） |
| **v2 结构化字段** `auto.gate` | JSON 字段 | 2026-10-08 13:58 → 10-15 01:42 | 110 |

★★ **口径括注（`76` 与 `77` 的关系，写清楚以免并列时被读成矛盾）：**
- **`77`** = 全语料里「**仅标题**（无 `auto.gate`）且标题含 `[gate.id]`」的记录数 —— **这是本报告的正确口径**。
- **`76`** = **同一个量在旧的数字盲区正则下**的读数（初版用的 `/\[([a-z]+\.[a-z-]+)\]/`，末段不含数字）。
  ⇒ 两者**不是**「v1 时间窗口 vs 全语料」的差别：实测把窗口截到 v2 起点之前，该量**仍是 77**
  （最后一条仅标题记录是 `2026-10-08 12:08:45`，本就在 v1 窗口内）。
  ⇒ **差的那 1 条是 `f-0100`**：它的 `[completion.r5]` 里 `5` 是数字，旧正则**读不到**它
  （实测旧正则 = 76、`[a-z0-9-]+` = 77，delta 恰好 1 条，就是它）。
  ★ 这与 §4 修掉的是**同一个数字盲区**，此处一并更正。

★★★ **关键：v2 期间标题标记【仍在】—— 两代在记录级是【嵌套】的，不是「不相交」。**
```
$ node -e "…有 auto.gate 的记录，其 title 是否也带 [gate.id]？…"
records with auto.gate                = 110
...of those, ALSO carry a title [id]  = 110     ← ★ 100% 重叠
```
⇒ 所以**不能**说「两个面不相交，故 110 + 76 可以直接相加」。那个算式会把**同一个模型算错**：
`76` 本身**已经是扣掉重叠后的余数**（只差它是**用有数字盲区的正则**算出来的 ⇒ 真值 **77**，见上）。

```
$ node -e "…逐日统计两代分别在场多少…"
2026-10-05 | auto.gate   0 | title-only   0
2026-10-06 | auto.gate   0 | title-only   0
2026-10-07 | auto.gate   0 | title-only  32
2026-10-08 | auto.gate  17 | title-only  45     ← 交接日（10-08 12:08 后不再出现「仅标题」）
2026-10-09 | auto.gate  61 | title-only   0     ← 之后 v2 记录【全部】带结构化字段
2026-10-10 | auto.gate  20 | title-only   0
2026-10-11 | auto.gate   4 | title-only   0
2026-10-14 | auto.gate   2 | title-only   0
2026-10-15 | auto.gate   6 | title-only   0
```
★ 该列合计 **32 + 45 = 77**，与上表的 **77** 一致。
（初版此列写 `44`，合计 76 —— 那正是数字盲区少算的 `f-0100`。）

⇒ ★★ **正确的读法是「记录级并集」**：
```
attributable = #{ r : r.auto.gate  ∨  title(r) 含 [gate.id] }   ← 一条记录只计一次
             = 187 / 384 = 48.7%
```
**★ 不是 110+76（= 186）** —— 那个数既不是记录数、也不是逐 id 之和，只是两个错误恰好抵消。
★★ 而**绝不能只报其中一代还说那是全部**（只按 `auto.gate` ⇒ 110，会漏掉 v1 的全部与 v2 里标签写在标题上的那些）。

★★ **t20 对「76 vs 77」的口径更正（这是本轮唯一实质改动，且它推翻了一种想当然的解释）：**
- **想当然的解释**（曾考虑采纳）：「76 = v1 时间窗口内的口径，77 = 全语料仅标题的口径」。
- **实测：这个解释是错的。** 把窗口截到 v2 起点（10-08 13:58）之前，该量**仍是 77** ——
  因为**最后一条仅标题记录就是 `2026-10-08 12:08:45`，本已在 v1 窗口之内**。窗口**不改变**这个数。
- **真正的成因**：`76` 是**同一个量在旧数字盲区正则下的读数**（`[a-z-]+` 不含数字）；
  差的**恰好 1 条是 `f-0100`**，它的 `[completion.r5]` 里 `5` 是数字。
  ```
  $ node -e "…同一批记录，两个正则…"
  旧正则 [a-z-]+      ⇒ 10-08 = 44，合计 76
  新正则 [a-z0-9-]+   ⇒ 10-08 = 45，合计 77     ← 差的那条 = f-0100
  ```
⇒ ★ 所以本节写的是**实测到的成因**，不是被建议的那个；两者若不一致，以本节的复跑命令为准。
