# 模块重划：自净化 · 实施 · 评估器（2026-10-16）

> **用户裁定（逐字）**
> 「1. **自净化模块**的运作:我们的自净化模块**只针对本项目**（即插件本身）做改进。
>  它负责做**采集**、做**处理**,最后应该会产出某种**结论**,即对被吸收进来的内容,
>  给出"**是否需要修改**"以及"**以什么样的形态去做修改**"的结论。
>
>  2. **评估器模块**的作用:
>  (a) **评估自净化成果** —— 自净化模块产出结论并完成改进之后,
>     或许需要调用专门的评估器模块,去评估**是否产生了收益**。
>  (b) **评估开发改动** —— 在项目开发过程中,我们做的一些改动,
>     可能也需要评估器去评估其**收益**。
>
>  3. **架构上的思考**:从整个架构上来说,目前我们修改的内容好像**已经不限于自净化模块**了……
>  虽然目前项目里或许还没有我需要的一个形态,但在我的想法里面,
>  确实应该有这么一个"**评估器模块**"。或者说,我们目前做的这个,
>  **可能不能被称为一个"自净化模块",因为它不包含"改完之后产生收益"这样一个完整的闭环**。
>  ★ 目前做的可能只是一个**信息采集和初步处理的模块**。
>
>  但是,在它产出一定东西之后,就需要**交给某个具体的、掌管实施并且评估收益的模块**,
>  **在那个模块的监督下**,去具体运行。」

## 0. ★★★ 裁定:用户是对的,而源码证实

### 实测 `src/evolution/` 的全部导出


**⇒ 六个导出里:3 个形状 · 2 个采集 · 1 个入口。**

```

❌ 没有实施（改 prompt / profile）
❌ 没有收益（前后比较）

```

★ **而"收益"的地基 `confidence.ts` —— `readSedimentFlywheel` 仍【零调用方】。**

⇒ ★★★ **所以准确的结论是:**
```
★ 现在这个模块 = 【信息采集 + 初步处理】
★★ 它【不是】自净化模块 —— 因为"自净化"要求"改完产生收益"的闭环
⇒ ★ 用户提出的改名是对的:应该叫【采集与处理模块】
```

## 1. ★★★ 重划之后的三个模块（各管一段）

```
┌────────────────────────────────────────────────────────────────────┐
│  ① 采集与处理模块（src/evolution/ —— 现状，名字该改）                │
│     职责：采集信号 · 该不该采 · 分类                                │
│     ★ 产出：【结论】——「是否需要修改」+「以什么形态改」              │
│     ★ 不碰：不改任何东西，不评估收益                                 │
└────────────────────────────────────────────────────────────────────┘
                              │ 结论（一份提案）
                              ▼
┌────────────────────────────────────────────────────────────────────┐
│  ② 实施模块（★ 不存在）                                            │
│     职责：拿结论 → 真的改（prompt / profile / 判据阈值）             │
│     ★ 在【评估器的监督下】运行                                      │
│     ★ 而循环 B（collection 判据 / 验证命令 / 阈值）它只能提议        │
└────────────────────────────────────────────────────────────────────┘
                              │ 改动
                              ▼
┌────────────────────────────────────────────────────────────────────┐
│  ③ 评估器模块（★ 不存在 —— 而这是用户新提的）                        │
│     职责：衡量【收益】                                              │
│     (a) 评估①的成果（自净化改完有没有用）                           │
│     (b) ★★ 评估【开发改动】（不只自净化 —— 任何改动都能用它）        │
│     ★ 而它【独立的理由】：单次判据结构上回答不了"趋势"               │
└────────────────────────────────────────────────────────────────────┘
```

### ★★★ 而 ③ 独立成一个模块的**技术理由**（不只是组织理由）

```
① 21 条判据  ⇒ 回答「这次改动【合规】吗」  ⇒ 单次、当下、机械
③ 评估器    ⇒ 回答「这次改动【有收益】吗」⇒ ★ 前后【两个窗口】、趋势
⇒ ★★ 单次判据【结构上】回答不了趋势 —— 所以它必须独立，不能塞进任何一条判据
```

★ **而用户 (2b) 那句把这个模块的价值放大了:**
> 「在项目开发过程中,我们做的一些改动,可能也需要评估器去评估其收益。」

⇒ ★★ **即:评估器的输入不只来自自净化,也来自【任何一次开发改动】。**
★★ **所以它的接口该以【改动】为单位,而不是以【信号】为单位。**

## 2. ★★ 于是"改动"是一等公民（本裁定最重要的实现后果）

### 2.1 现在的形状（以信号为单位）

```ts
EvolutionSignal { kind, source, message, scene, index, routing?, ... }
```

### 2.2 ★★★ 该有的形状:一个**改动**对象

```ts
/** ★★★ 一次【改动】—— 它是评估器模块的一等公民，不来自自净化也可以有 */
export interface ChangeRecord {
  readonly id: string
  readonly at: number
  /** ★ 改了什么（可指：文件路径 / profile 键 / 判据 id） */
  readonly subject: string
  /** ★ 这次改动的【依据】—— 自净化给的提案，或一次普通开发改动 */
  readonly basis: { readonly from: 'evolution' | 'development'; readonly ref?: string }
  /** ★ 它【声称】要解决什么（一句话，且可核） */
  readonly intent: string
  /** ★★ 用来判断收益的【靶】：哪个 (component, kind) 桶该下降 */
  readonly target?: { readonly component: string; readonly kind: readonly string[] }
  /** ★ 改动前的窗口 */
  readonly before: { readonly from: number; readonly to: number; readonly count: number }
}
```

★★ **而 `target` 是关键**:它把"收益"变成**可算的** ——
**没有它,收益就只能靠感觉。**

### 2.3 ★★ 而 `EffectReading` 是它的输出

```ts
export interface EffectReading {
  readonly changeId: string
  readonly before: { from: number; to: number; count: number }
  readonly after:  { from: number; to: number; count: number }
  /** ★★★ 三态 —— 'unmeasured' 必须存在 */
  readonly verdict: 'improved' | 'unchanged' | 'unmeasured'
  readonly why?: string
}
```

★★ **`unmeasured` 必须存在的理由:**
```
若改动前那个桶【本来就没有记录】⇒ ★ 无从说它下降了
而「无从比较」与「没有下降」在报告里同形 ⇒ ★ 那正是本仓记账最久的形态
```

## 3. ★★ 而"监督下运行"（用户那句）的落法

> 「需要交给某个具体的、掌管实施并且评估收益的模块,**在那个模块的监督下**,去具体运行。」

### 3.1 ★★ 而它正好是**已有的三层**（EverOS PromptSlot）

```
L1 代码里的默认（★ 只有人能改）
      ↑ 晋升需 verified
L2 profile 覆盖（cordis.patch.yml）★ 改它不动代码、不必 build、不影响稳定版
      ↑ 可用
L3 单次覆盖
```

⇒ ★★★ **"监督"= 晋升闸:**
```
实施模块改 L2 ⇒ ★ 立即可用（不动稳定版）
评估器读前后窗口 ⇒ 若 verdict === 'improved' ⇒ ★ 才允许晋升 L1
                              ⇒ 若 'unchanged' ⇒ ★ 不晋升（并留档）
                              ⇒ 若 'unmeasured' ⇒ ★ 也不晋升（判不了 ≠ 有效）
```

★★★ **而那正是用户最早那句"我不放心改完立马生效,是因为我不放心修改后的效果"的落法** ——
**"不放心"被换成了"一个可读的 verdict"。**

### 3.2 ★★ 而循环 B 的边界不变

```
★ 循环 A（实施模块）能自动改:prompt · profile · 阈值
★★ 循环 B（★ 评估器模块辖下）:collection 判据 · 验证命令 · confidence 阈值
   ⇒ ★★ 只能提议，不能自改
```

★★ **而它现在有了新理由:评估器是【监督者】——
若实施模块能改评估器的判据,它就是**改自己的考卷**（STOP 的 `secret_utility` 那条）。**

## 4. ★★ 落地顺序（按依赖，不跳步）

| # | 做什么 | 模块 | 依赖 |
|---|---|---|---|
| **①** | ★ **改名 + 划界**:`src/evolution/` → 明确它只到"结论" | ① | 无 |

★ **而 ①②③ 都【不互相依赖】⇒ 可以并行。**
★★ **而 ④⑤ 必须先有 ③ —— 否则"实施"没有收益读数,就是盲改。**
