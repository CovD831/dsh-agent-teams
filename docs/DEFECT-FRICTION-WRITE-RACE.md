# 缺陷：卡点台账有 **12/384 条读不回来** —— 因为它不是原子写（2026-10-16）

> **怎么发现的**：t88 补录时，队长独立复算 `redundancy`，
> 结果**读台账时 JSON.parse 抛错** ⇒ 追下去发现这个缺陷。
> ★ **此前没有任何检查发现过它**（包括 384 条自己的那个 reader）。

---

## 1. 现象

```
.agent-teams/frictions/  384 个文件
★ 12 个是【坏 JSON】（3.1%）
   f-0152 f-0158 f-0161 f-0167 f-0172 f-0180
   f-0183 f-0190 f-0216 f-0220 f-0241 f-0244
```

**坏法（同一个形态）:**
```
f-0152: 一个完整 JSON 结束（}\n}）之后，又接了：
        810, 2815, 2820, 2825, 2830, ...
f-0158: 一个完整 JSON 结束之后，又接了：
        ion": { "__absent": "function" }, "readF" ...
```

⇒ ★★ **即:【一次完整写入】+【另一次写入从中间开始】被拼在同一个文件里。**

---

## 2. 根因（两处，缺一不可）

### ① id 分配不是原子的

```ts
// src/tools/shared/entities.ts:3833-3839
let max = 0
for (const name of await readdir(frictionDir)) {
  const matched = /^f-(\d+)\.json$/.exec(name)
  if (matched === null) continue
  max = Math.max(max, Number(matched[1]))
}
// ⇒ 两次【并发】调用读到同一个 max ⇒ ★ 同一个 id
```

★★ **而那段注释逐字说了这个风险:**
> 「id 必须**单调且不与既有撞车**……用时间戳当 id 会让"同一秒内的两条"撞车,
>  而**撞车后一条覆盖另一条** —— **被覆盖掉的卡点与"没发生过"在台账里同形**。」

⇒ ★ **它防的是【时间戳】,没防【并发】。**

### ② 写入不是原子的

```ts
// src/tools/shared/entities.ts:4083
await writeFile(join(frictionDir, `${id}.json`), `${JSON.stringify(record, null, 2)}\n`, 'utf8')
// ★ 没有 temp + rename ⇒ 两次写同一路径会【交错】
```

### ③ 而调用是【旁路不 await】的

```ts
void recordFriction({ ... })     // ★ 三处调用点全是 void
```
★ 那本身是**对的设计**（拒绝路径必须立刻抛出,不许等写台账）——
⇒ **但它让两次写【真的可能并发】。**

---

## 3. ★★ 为什么这是一个**真缺陷**,而不是数据损坏

```
· 读不回来的记录 ⇒ ★ 它记录的卡点【等于没记】
· 而"记了但读不回来"与"没发生"在台账里【同形】 —— ★ 正是那段注释警告的形态
· ★ 更糟:「384 条」这个数一直是对的，而【其中 12 条是死的】
```

⇒ ★★★ **那与"没采"vs"采了没用"是同一个形态。
而它出现在【我们刚给这个形态命名】的同一批数据里。**

---

## 4. 修法（三处，而第 ③ 处最容易被漏）

| # | 修什么 | 怎么修 |
|---|---|---|
| **①** | **原子写** | temp 文件 + `rename`（rename 在同一文件系统上是原子的）|
| **②** | **id 分配** | ★ 用 `wx` 标志（`O_EXCL`）:创建失败 ⇒ 换 id 重试（**把分配与占用合成一步**）|
| **③** | ★★ **一条能读到"读不回来"的检查** | 拓普时**逐个 parse**,坏文件**报出而不是跳过** —— 否则下一次还是没人知道 |

★ **而 ③ 是本任务最值钱的一条** —— 因为**这个缺陷被发现的唯一原因是偶然**:
队长**恰好**要复算一个数,而那个数**恰好**要遍历台账。
**⇒ 如果没人做那件事,它会一直存在。**

---

## 5. 反向半边（必须）

**A**：并发两次 `recordFriction` ⇒ ★ **两个文件都是合法 JSON**（修前至少一个坏）
**B**：★ **故意造一个坏文件 ⇒ 新检查必须报出它**（而不是静默跳过）
**C**：★ **拒绝路径的行为不变** —— 台账写入仍是旁路（`void`）,不许因为"要原子"而变成 await

---

## 6. ★ 而那 12 个坏文件怎么办

```
选项 ① 修:从文件内容里【恢复】第一次写入的那份（它完整地在前半段）
选项 ② 留:标记为坏，让新检查报出
选项 ③ 删:★ 不许（"软归档不硬删"是本仓纪律）
```

★ **我建议 ① + ②**:
**能恢复的恢复（前半段是完整 JSON）,并留下一条"它曾经是坏的"的记录。**

## 7. ★★★ 更正：尾巴是【残片】,不是"第二份完整写入"（t90 实测）

★ **本文 §1 与规格原来写的是**「**两次完整写入首尾相接**」——
**而 t90 实测推翻了这个定性。**

```
实测（用队长动手前的备份验证，3 个样本）:
  f-0152: 尾巴 2650 B ·以 "\n810, 2815, 2820, 2825, " 开头  ⇒ ★ 尾巴【不能独立 parse】
  f-0158: 尾巴 11121 B ·以 "\nion\": {\n  \"__abse" 开头        ⇒ ★ 不能独立 parse
  f-0161: 尾巴 1297 B ·以 "\n16, 16230, 16235, 16241" 开头   ⇒ ★ 不能独立 parse
```

⇒ ★★ **准确的描述是:**
```
第二份写入【被截断/交错】——它的【头部】丢在第一份的覆盖区里，
只剩【尾部残片】
```

★★ **为什么这个更正重要:**
```
· 按"第二份记录"记 ⇒ 读的人会以为【尾巴本身可用】（它不可用）
· 按"残片"记      ⇒ 读者知道它只是一次中断的痕迹
⇒ ★★ 两者在报告里差别很大:"一条记录受损"与"一次写入被打断"
```

★ **而它不影响恢复**（第一份是完整的）—— **只影响"尾巴是什么"的定性。**

★ **t90 的处置**:尾巴**按残片记**,并**逐条留档 + 全文存盘**
（34,927 字节,含每文件字节数 + `sha256[:16]` + 开头预览 + **全部尾巴的逐字 JSON**,**自包含**）。
