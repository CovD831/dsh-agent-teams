## 3. ★★★ 设计:三层投影（照用户早先裁定的「通用投影 + 配置驱动」）

### 3.1 而首要问题是**接口**,不是界面

```
★★ 现状:插件里【没有】"一个模块如何把自己的读数交给 UI"的约定
⇒ ★★★ 所以每个新模块都要【手写一条路】到 snapshot.ts
   —— 而那就是"collection 做完了却看不见"的机制原因
```

### ★★ 建议的形状（一个投影接口）

```ts
/** ★★★ 任何模块把自己的读数交给 UI 的唯一入口 */
export interface UiProjection {
  /** 这个投影的稳定 id（UI 用它做 key 与折叠状态）*/
  readonly id: string
  /** ★ 一段人读的标题（后端给，UI 不硬编码）*/
  readonly title: string
  /** ★ 它在界面上的【层】—— 决定默认展开还是收起 */
  readonly layer: 'runtime' | 'gate' | 'collection' | 'evaluation'
  /** ★★ 读数本身：一组具名的【三态】项 */
  readonly readings: readonly {
    readonly name: string
    /** ★ 三态:值 · 判不了(undefined) · 不适用 */
    readonly value: string | number | undefined
    readonly state: 'ok' | 'unmeasured' | 'absent'
  }[]
}
```

★★★ **而它成立的三个理由:**
```
① ★ 与既有 21 条判据同构（三态 + 具名 + 可显示）
② ★★ 而 layer 决定了「默认精简层 + 点开完整层」（用户早先裁定 (丙)）
③ ★★★ 而"新模块的读数看不见"这件事【结构上不会再发生】——
   因为加投影只需实现一个接口,不需要改 snapshot.ts
```

### 3.2 ★★ 而四个层对应本会话造的四样东西

| 层 | 内容 | 现状 |
|---|---|---|
| **runtime** | 成员 · 任务 · 依赖 · 进度 | ✅ **已有**（现在的界面）|
| **gate** | 21 条判据的裁决 | ⚠️ 有 `gateEvaluation`,★ 但 `gateCatalog` 没接 |
| **collection** | redundancy · coverage · refused | ❌ **0 次** |
| **evaluation** | EffectReading（前后窗口）| ❌ **0 次** |

⇒ ★★★ **所以 UI 重设计 = 把后三层接上,而**不是重画第一层**。**
**★ 而第一层（运行时）用户说"也可以打磨" —— 那是对的,但它是【第二位】的。**

## 5. ★ 所以下一步建议

| 顺序 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **①** | ★ **定 `UiProjection` 接口** | ★ 它是"新模块看不见"的机制解 |
| **②** | ★ **先把 collection 层接上** | ★ 它数据最全（385 条台账 + 读数函数都在）|
| **③** | 再接 evaluation 层 | ⚠️ 依赖 t99（S1 接线）|
| **④** | gate 层接 `gateCatalog` | ★ 小（实现了没接）|
| **⑤** | 打磨运行时层 | ★ 用户说"也可以打磨" ⇒ 放最后 |

★ **而 ① 是本设计里唯一"必须先定"的** ——
**因为 ②③④ 都依赖它,而它们各自不需要互相等待。**
