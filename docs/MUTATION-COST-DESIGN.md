## 1. 业界两个独立实现，收敛到同一组优化

### PIT（Java，pitest.org）

出处：<https://pitest.org/quickstart/incremental_analysis/>

它的 incremental analysis 列了 5 条可推导的复用，原文要点：

- 上次检测到**死循环**，而类没变 ⇒ 这个变异体仍然死循环；
- 上次**被杀**，且被测类与**杀死它的那个测试**都没变 ⇒ 仍然被杀；
- 上次**存活**、没有新测试覆盖它、且**覆盖它的测试都没变** ⇒ 必然仍然存活；
- 上次被杀、而类或杀死它的测试变了 ⇒ **把上次那个杀手测试优先跑**（since 1.14.4）；
- 一批同类变异体上次全存活、而类变了 ⇒ 可合成**元变异体**一起测（未实现）。

★ 它**诚实标注了代价**：除第 4 条外，这些优化都引入**潜在误差**，因为类的行为也由
依赖决定，而 PIT 只考虑最强的那类依赖（父类/外部类）。原文：
"this assumption seems reasonable, it is currently **unproven**"。

### StrykerJS（JS/TS，stryker-mutator.io）

出处：<https://stryker-mutator.io/docs/stryker-js/incremental/>

`--incremental` 把上次结果写进 `reports/stryker-incremental.json`，复用条件原文两条：

- 变异体 **Killed**；肇事的测试**仍存在且没变**；
- 变异体 **未 Killed**；**没有新测试覆盖它**，且**没有测试变过**。

并且它明说**其他加速手段**：**coverage analysis、hit limit counters、hot-reload**。

## 2. ★★★ 最重要的一条：Google 在生产里用**历史反馈**排序与抑制

出处：MuRS 论文摘要 <https://arxiv.org/abs/2306.09130>

Google 的变异测试服务把 **diff-based mutation testing**（**只变异改动行**）接入
**代码评审**，并持续收集开发者反馈。要点：

- 它对**"没用的变异体"**有**抑制规则**（suppression rules）—— 即**持续收到负面反馈的那些**；
- 手写抑制规则**很费工程时间**，于是 MuRS **按源码模式把变异体分组**，
  用**同一组里历史的开发者反馈**去**排序与抑制**未来的变异体；
- A/B 实测：负面反馈率 **11.45%（MuRS） vs 12.41%（基线）**，**统计显著**；
- 而且 MuRS **能自动复原手工写的抑制规则**。

★★ **这条直接支持用户的设计直觉**：用户说"要在 L3 不断**增加**，还要**维护**它，
不能让它太多" —— 而 Google 的答案正是**抑制规则 + 历史反馈**，不是"一律全跑"。

## 3. 等价变异体：公认的第一大障碍

出处：<https://en.wikipedia.org/wiki/Mutation_testing>（引 2014 年系统性综述）

原文要点：

- **等价变异体**（语义与原文相同、**永远杀不掉**）是**实用化的最大障碍**；
- "判断一个变异体是否等价所需的努力可能非常高，即使对小程序"；
- 2014 年的系统性综述识别出 **17 种相关技术**。

arXiv 上仍在活跃产出：`LLM for Equivalent Mutant Detection`、`Large Language Models for
Multi-Lingual Equivalent Mutant Detection`（两者摘要都指出 EMD 影响**成本与偏置**）。

⇒ ★ 而等价变异体**必须与"测试弱"分开**：它**永远存活**，而那不是测试的缺陷。

## 4. 由此得到的五条设计结论

| # | 结论 | 出处/读数 |
|---|---|---|
| **1** | **增量复用是标准做法**，而有**明确代价**（依赖变化未建模） | PIT / Stryker 都这么做，PIT 自己标注"unproven" |
| **2** | **diff-based（只变异改动行）是工业起点** | Google 服务即如此 |
| **3** | **抑制/排序要有历史依据**，不是拍脑袋 | MuRS 的 A/B 显著 |
| **4** | **等价变异体要单独处理**，不能算进"存活" | 综述：实用化最大障碍 |
| **5** | **覆盖率是加速的前置**（只测覆盖到的变异体） | Stryker 明列 coverage analysis 为首要手段 |

## 6. ★ 对用户那个问题的直接回答

**问：L3 每次全量跑是多少开销？它该有多少条？**

⇒ **今天 L3 = 0 条**（清单文件不存在）⇒ 开销 **0**。

⇒ 而**该有多少条**，正确的算法不是拍一个数，而是**预算**：

```
L3 预算条数 = (整链预算 20 min − L1/L2 实测耗时) / 每个变异体耗时
```

⇒ 而**"该删哪条"**照 MuRS 的做法：**按历史杀/存活记录**——

| 历史 | 读作 | 动作 |
|---|---|---|
| **恒被杀** | 这条契约无效，或已被别处覆盖 | **抑制** |
| **恒存活** | 测试没覆盖它（**或它是等价变异体**） | **补测试，或抑制** |

★ 而两条都需要**一个跨次的历史账本** —— 本仓**没有**，而 PIT 与 Stryker 的增量模式
**本质上就是这个账本**。⇒ 所以"加账本"同时解决**成本**与**维护**两件事。
