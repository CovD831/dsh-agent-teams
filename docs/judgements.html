一个计数读数里，有【三格】没写清就会被当成同一件事：在哪个集合里数、算不算注释/字符串、以及阈值

★ 什么会证伪它

若某次改动的声明里已经写明集合与词法口径（例如 inScope 已声明、且口径写在判据里），那这条不适用——那时读数只有一种解释。⇒ 判据是：这个读数能不能被【两个都合理】的口径各自算出一个数。

它从哪来
t94（absorb-dev 复核 captain 给的验收样本时发现）
captain 给了四条读数：parseKnownBaselineFailures 3→0 · baselineAbsent 2→0 · knownBaselineFailures 3→0 · skippedAll 16→0，并说『它们真的不在任何地方——我复核过』。absorb-dev 按 captain 自己的分栏口径复核，发现：(1) 那三个符号的【定义还在】backtest.ts（1/4/5 处），丢的是 tools 侧的引用——所以『哪里都没有』是错的；(2) skippedAll 的『16→0』是【单文件含注释】口径，而 tools 面纯代码口径是【24→8】，单文件纯代码又是另一个数——三个数字都『看起来对』，因为量的是不同的集合×不同的词法口径。
怎么复用
给出或读到任何一个计数时，问三句：在【哪个集合】里数的？算不算注释与字符串？以及它是计数、比例还是阈值？—— 三句里有一句答不出，那个数字就还不是读数。
状态含义
它经得住目前的反例 —— 而那不等于它被证明了。
备注
  • ★ 而它的危险在于：错的读数与对的读数【长得一样】（都是『某个符号从 N 变 0』），而两者都支持同一个结论。
  • ★ 而正确形态（absorb-dev 的建议，captain 采纳）：把集合与词法口径做成判据的【显式输入】，而不是隐含假设。
  • ★ 与 j-0003（代理读数在它所代理的东西没变时也会变）是同一族：那次是『读的量不对』，这次是『读的地方与口径没写』。
